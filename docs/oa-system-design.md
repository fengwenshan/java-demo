## 1. 项目背景与目标

建设一套公司内部使用的 OA 系统，替代当前分散的线下流程，实现组织、审批、考勤、协同、文档、行政等业务的线上化与统一管理。

**目标**

1. 统一组织架构与权限体系，一次建设，全系统复用
2. 线上化核心审批流程，审批过程可追溯、可统计
3. 与公司现有移动办公平台打通，实现免登、消息推送、待办提醒与移动端使用
4. 关键操作全部留痕，满足内部审计与等保合规要求

**明确不做的事（YAGNI）**

- 不自研即时通讯、不自研打卡硬件、不自研移动端原生 App（全部依托移动办公平台）
- 不自研工作流引擎（采用 Flowable）
- 一期不做薪资计算引擎（个税社保合规风险高，金额由财务核算）

## 3. 总体架构

### 3.1 架构形态

采用**单体多模块**。OA 系统的特征是并发量低、事务一致性强、跨模块关联多（组织、权限、审批贯穿所有业务），微服务在此场景下只会增加运维成本而不带来收益。

### 3.2 模块划分

```
oa (聚合工程)
├── oa-common        统一返回体、异常体系、工具类、常量与枚举
├── oa-framework     认证鉴权、数据权限拦截、操作审计、日志链路、Redis、文件存储、定时任务
├── oa-system        组织架构、部门、岗位、员工、项目组、账号、角色、菜单、字典、系统参数
├── oa-workflow      Flowable 集成、流程定义与部署、待办已办、审批人规则、流程表单
├── oa-attendance    班次排班、打卡同步、补卡、请假额度、加班出差、考勤统计、封账
├── oa-collab        公告、日程、会议、任务、消息中心、通讯录
├── oa-doc           文档空间、知识库、版本管理、在线预览、共享外链
├── oa-admin         固定资产、办公用品、车辆、访客
├── oa-report        报表引擎、预置报表、自定义报表、看板、导出
└── oa-boot          启动类、多环境配置、打包
```

**依赖方向**：`oa-boot` → 各业务模块 → `oa-framework` → `oa-common`。业务模块之间**禁止直接依赖**，需要跨模块调用时通过接口下沉到 `oa-framework` 或由 `oa-boot` 层组装。这条规则是防止单体腐化的关键。

### 3.3 技术栈

| 层次 | 选型 |
|---|---|
| 后端框架 | Spring Boot 3.3.5 |
| 持久层 | MyBatis 3.5.x + 手写 SQL（复用现有技术栈） |
| 数据库 | MySQL 9.x |
| 缓存 / 会话 / 分布式锁 | Redis |
| 工作流 | Flowable 7.x（需与 Spring Boot 3.x 匹配） |
| 认证 | Sa-Token 或 Spring Security + JWT（第 0 期第一周定稿） |
| 数据库版本管理 | Flyway |
| 文件存储 | MinIO（抽象接口，可切换 OSS） |
| 接口契约 | OpenAPI 3 |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus + Pinia |
| 部署 | Nginx + 应用 + MySQL + Redis + MinIO，Docker Compose 起步 |

## 4. 权限模型（核心设计）

> 本章是全系统最容易返工、风险最高的部分，所有业务模块都必须遵循本章规则。

### 4.1 组织模型

系统同时存在两种正交的组织维度，构成矩阵式管理：

| 维度 | 性质 | 说明 |
|---|---|---|
| 部门 | 纵向、常设 | 多级树结构，员工有主部门，可有兼职部门 |
| 项目组 | 横向、临时 | 有明确起止时间，成员在组内持有角色，项目结束需归档 |

两者交叉产生数据权限的两个来源。

### 4.2 认证

- 登录方式：账号密码、短信验证码、移动平台扫码/免登
- 密码 BCrypt 加密存储，强度策略校验，首次登录强制改密
- 登录失败锁定、图形验证码、防暴力破解
- token 续期、多端登录策略、强制下线
- 账号与移动平台 userId 绑定（免登前提）

### 4.3 功能权限

- 用户 → 角色 → 菜单/按钮 三级模型
- 前端路由与按钮由后端下发动态生成
- **后端逐接口做越权校验**，前端隐藏按钮仅作为体验优化，不作为安全手段

### 4.4 数据权限

**规则一：项目组是强隔离边界。** 项目组之间的数据默认互不可见。不属于任何共同项目组的两个用户，无法看到对方在项目组内的数据。

**规则二：组内可见范围由组内角色决定。**

| 组内角色 | 可见范围 | 标识 |
|---|---|---|
| 成员 | 仅自己创建/自己的数据 | `SELF` |
| 组长 / 组内管理员 | 本组全部人员的数据 | `GROUP` |

**规则三：不是所有模块都套项目组隔离。** 需要严格区分：

| 走项目组隔离（数据带 `project_id`） | 走部门权限（公司级数据） |
|---|---|
| 任务、工时、项目文档、项目费用/报销、项目会议纪要 | 组织架构、员工档案、公告、薪酬、培训、行政资产、系统配置 |

**规则四：数据的归属由服务端强制注入。** 业务表的 `project_id` 必须在服务层依据上下文写入并校验，**严禁接受前端传入的任意 `project_id`**。这是此类系统最高频的越权漏洞。

**规则五：归档不等于删除。** 项目组归档后，组内角色的数据权限立即失效，但历史数据保留，仅对具备全局数据权限的角色只读可见。

### 4.5 多部门任职与多角色人员规则

一名员工可以有多条任职记录（主部门 + 兼职部门），并因此在系统中持有多个角色；角色亦可来自项目组成员身份。

**可见范围计算规则：用户的数据可见范围 = 其所有角色各自可见范围的并集。**

并集的边界约束：**每个角色只能在其自身授权范围内贡献可见数据，并集不会突破任何单一角色的边界。**

举例，张三同时是「研发部主管」「项目组 A 组长」「项目组 B 成员」：

| | 可见 |
|---|---|
| 研发部主管 | 研发部及其下级部门的部门维度数据 |
| 项目组 A 组长 | 项目组 A 的全部数据 |
| 项目组 B 成员 | 项目组 B 中由张三创建的数据 |
| **合计** | 上述三者并集 |
| **不可见** | 项目组 C 的数据（张三未参与） |

**展示完整性要求：** 所有涉及人员的界面——员工档案、组织架构图、审批流转记录、报表——必须展示该员工的**全部任职与全部角色**，不得只显示主部门或单一角色。跨部门人员在审批人的眼中应能看出其真实的全部归属。

**权限实时收敛：** 员工调岗、离职、退出项目组或项目组归档时，对应角色立即失效，可见范围实时收敛，不保留历史权限。

### 4.6 全局数据权限通道

必须为高管、HR、财务、PMO 等角色保留跨部门/跨项目组的全局可见能力，否则系统无法产出汇总数据、无法实际使用。

- 通过独立的「全局数据权限」角色授予，与普通角色分离
- 所有使用全局权限的访问**必须记录审计日志**（谁、何时、查看了什么范围的什么数据）
- 默认不授予，按岗位申请审批后开通

### 4.7 实现要点

- 用户的数据权限上下文在登录时构建并缓存于 Redis：`可管理部门集合`、`全权项目组集合`、`仅自身项目组集合`；角色变更时主动失效缓存
- 提供 `@DataScope` 注解标注 Mapper 方法，声明该方法受哪些维度约束（`dept` / `project`）
- 通过 MyBatis Interceptor 在 SQL 末尾追加数据权限条件，**必须用括号包裹后再与其他条件 AND**，避免运算符优先级导致条件失效
- 条件形态（示意）：

```sql
AND (
      dept_id IN (我担任主管的部门及其下级部门)
   OR project_id IN (我在其中持组长/管理员角色的项目组)
   OR (project_id IN (我在其中仅持成员角色的项目组) AND creator_id = 当前用户ID)
)
```

- 导出 Excel、报表查询、批量接口**同样必须经过数据权限拦截**，这是最容易被忽略的数据泄露口

## 5. 功能清单

优先级与实施期的对应关系（与 §7 分期计划一致）：

| 优先级 | 对应期次 | 含义 |
|---|---|---|
| **P0** | 第 0 ~ 1 期 | 地基与审批主线，必须先完成 |
| **P1** | 第 2 期 | 形成日常可用闭环 |
| **P2** | 第 3 ~ 4 期 | 完整化与深化，可延后 |

### 5.1 平台地基（P0）

**工程与协作基建**

- git 仓库与分支策略（`main` / `develop` / `feature-*`）、PR 评审规则
- Maven 多模块骨架（见 §3.2）
- 统一返回体、全局异常处理、参数校验
- 统一日志与链路追踪（traceId）
- OpenAPI 接口契约先行，前后端按契约并行开发
- 多环境配置隔离（dev/test/prod），敏感配置外置，禁止明文入库入仓
- 数据库版本管理（Flyway），所有建表变更脚本化
- 代码规范与静态检查

**认证与账号**

- 账号密码 / 短信验证码 / 移动平台免登
- 密码策略、首次登录改密、登录失败锁定、验证码
- token 续期、多端登录策略、强制下线
- 账号与平台 userId 绑定

**组织架构**

- 部门树：多级、拖拽排序、合并、撤销、停用
- 岗位管理
- 员工档案：基本信息、任职信息（支持多部门兼职）、合同、证件、紧急联系人
- 登录账号与员工档案分离
- **组织变更历史**（生产环境必备）

**项目组**

- 项目组 CRUD、起止时间、状态（进行中 / 已归档）
- 成员管理与组内角色（组长 / 管理员 / 成员）
- 归档与权限自动失效

**权限**

- 功能权限：用户-角色-菜单/按钮，动态路由
- 数据权限：部门维度 + 项目组强隔离（见 §4）
- 全局数据权限通道与审计
- 越权校验拦截
- 权限缓存与刷新

**移动平台集成底座**

- SDK 封装：免登、组织同步、消息推送、待办卡片
- 通讯录同步（冲突以平台为准）
- 消息模板管理
- 回调签名校验、失败重试、幂等处理

**审计与运维底座**

- 操作日志：操作人、时间、IP、模块、变更前后值
- 登录日志（成功与失败）
- 数据字典、系统参数配置
- 定时任务管理（考勤统计、超时催办依赖此模块）
- 文件存储抽象（本地 / MinIO / OSS 可切换）

### 5.2 流程审批引擎（P0）

- **表单**：固定业务表单 + JSON Schema 动态表单双轨
- **审批人规则**：指定人、指定角色、部门主管、逐级上级、发起人自选、**项目组长**
- **节点类型**：会签、或签、依次审批、条件分支、并行网关
- **流程动作**：提交、同意、驳回（可驳回到指定节点）、撤回、加签、转办、委托代办
- **流程版本管理**：老单据继续执行其发起时的流程版本（**不做此条，上线后首次修改流程即出错**）
- 审批意见、附件、抄送
- 我的待办 / 已办 / 我发起的 / 抄送我的
- 超时自动提醒、超时自动通过、超时升级
- 流程与业务单据解耦：业务表仅保存流程实例 ID
- 流程效率统计：平均耗时、节点积压分析

### 5.3 组织人事（档案 P0 / 业务流程 P1）

> 员工档案、多部门任职、项目组归属属于权限的基础数据，随第 0 期落地；入职/转正/离职等业务流程在第 2 期实现。

- 员工档案维护，敏感字段（身份证、银行卡）加密存储 + 脱敏展示
- 员工生命周期状态机：待入职 / 试用期 / 正式 / 停薪留职 / 离职
- 入职流程：建档 → 账号开通 → 项目组分配 → 资产发放 → 试用期跟踪
- 转正、调岗、调薪、借调、离职
- 离职流程含**工作交接**与**权限自动回收**
- 花名册、组织架构图、人员变动记录
- 员工自助：查看个人档案、修改联系方式、申请在职证明

### 5.4 考勤管理（P1）

- 班次与排班：固定班、弹性班、多班次、跨天班
- 打卡：同步移动平台打卡数据（平台为权威数据源），补卡申请走审批流
- 请假：假期类型、额度管理；额度规则支持按工龄/入职时间自动计算、按月或按年发放、有效期与过期作废
- 加班申请、加班转调休
- 出差、外出登记
- 考勤统计：日报/月报、迟到早退旷工、异常明细，按**部门 + 项目组**双维度汇总
- 考勤封账：月度锁定，锁定后不可修改
- 节假日与调休日历维护
- 向薪酬模块导出考勤结果（**不在考勤模块内计算金额**）

### 5.5 协同办公（P1）

- 公告：草稿、发布范围（全员/部门/项目组）、置顶、附件、已读未读统计
- 日程：个人日程、共享日程、与移动平台日历同步
- 会议：会议室预订（冲突检测）、参会人回执、会议提醒、会议纪要
- 任务：任务分派、子任务、截止提醒、看板视图、与项目组绑定
- 消息中心：站内消息 + 平台推送、已读状态、免打扰
- 通讯录：按部门/项目组查询、组织架构图、员工名片

### 5.6 文档与知识库（P2）

- 空间划分：个人 / 部门 / **项目组（强隔离）** / 公共
- 文件上传下载：大文件分片、断点续传、类型与大小限制
- 在线预览：Office / PDF / 图片
- 版本管理：历史版本、回滚、版本对比
- 权限：按空间与按文件授权，**预览与下载分开控制**
- 全文检索（数据量增大后再引入 ES）
- 外链分享：有效期与提取码
- 回收站、彻底删除、操作留痕（含下载记录）
- 知识库：分类、收藏、点赞、常用置顶

### 5.7 行政后勤（P2）

- 固定资产：台账、领用/归还/调拨/报废、盘点、折旧（可选）
- 办公用品：库存、申领（走审批流）、出入库、库存预警
- 车辆管理：台账、用车申请与审批、归还记录、里程与油费
- 会议室：与协同办公会议模块共用
- 访客管理：预约、审批、登记

### 5.8 报表与数据看板（P2）

> 例外：首页待办/待阅看板属于基础体验，随第 2 期协同办公一同落地；完整的报表引擎与自定义报表在第 3 期实现。

- 报表引擎：统一查询条件、分页、Excel 导出（**导出必须走数据权限**）
- 预置报表：人员花名册、人员异动、考勤汇总、审批效率、费用统计、资产台账
- 自定义报表：字段选择 + 条件组合 + 保存为「我的报表」
- 看板：首页待办待阅、部门人员概览、审批待办统计、考勤异常提醒
- 定时报表：按周/月自动生成并推送至移动平台

### 5.9 HR 深化（P2）

- 薪酬：工资项配置、薪资档案、调薪记录、工资条发放与员工确认
  - **风险提示**：个税与社保计算合规要求极高，建议一期只做工资条查询，金额由财务核算后导入
- 培训：课程、报名、签到、学时统计
- 绩效：考核周期、指标库、自评/互评/上级评、结果归档与分布
- 招聘（可选）：招聘需求、简历库、面试流程

## 6. 非功能需求

### 6.1 安全与合规

- 密码策略、登录审计、敏感数据加密与脱敏、越权检测
- SQL 注入与 XSS 防护、接口限流、防重放
- 等保相关（若公司需过等保，以下为硬指标）：日志留存 ≥ 6 个月、关键操作可审计、权限最小化

### 6.2 数据备份与恢复

- MySQL 定时全量备份 + binlog 增量备份
- **必须实际演练恢复流程**，仅备份未演练等同于没有备份

### 6.3 部署与运维

- 部署拓扑：Nginx + 应用 + MySQL + Redis + MinIO

## 9. 关键设计决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 单体 vs 微服务 | 单体多模块 | OA 并发低、事务强、跨模块关联多；微服务只增加运维成本 |
| 自研 vs Flowable | Flowable 内嵌 | 自研审批流仅能支撑简单分支，会签/并行/加签/版本管理的隐性成本远超预期 |
| 项目组权限：并集 vs 强隔离 | 强隔离 | 业务要求项目间数据不得互相可见 |
| 多角色可见范围 | 并集（不突破单角色边界） | 跨部门人员需完整履职，同时保证不越权 |
| 打卡数据源 | 同步移动平台 | 无打卡设备，平台为权威数据源，避免重复建设 |
| 薪资计算 | 不自研，仅做工资条查询 | 个税社保合规风险高 |
| 交付顺序 | 路线 A：地基优先 + 试点线 | 8 域全做时返工成本远大于启动速度收益 |

## 11. 附：与现有工程的关系

本仓库当前包含 4 个学习模块（`01_servlet-demo` ~ `04_spring-boot-demo`），是现有技术栈的学习与验证过程，**不参与 OA 系统构建**。

OA 系统在本仓库内新增 `oa/` 聚合工程，与学习模块并存于同一 Maven 聚合下，但**互不依赖**（学习模块不引用 OA，OA 不引用学习模块）。可复用 `04_spring-boot-demo` 已验证的技术组合：Spring Boot 3.3.5 + MyBatis + MySQL + 内嵌 Tomcat。

**需要注意的一点**：本仓库为公开可见的可能性较高，而 OA 是公司内部生产系统，代码、数据库设计、业务规则通常不适合公开。建议满足以下任一条件后再将 OA 代码推送到本仓库，否则应为 OA 单独建立**私有**仓库：

- 仓库已设为 Private，且团队成员的访问权限经过收敛
- 或 OA 相关的敏感内容（表结构、业务规则、内部接口）不随本仓库发布
