# R00 组织与权限模型（地基定义）

> **这份文档不产出代码，也不产出接口。** 它定义整个 OA 的"坐标系"：组织怎么分层、人员怎么挂靠、角色和数据范围怎么算出来。
>
> 后面每份需求文档都引用它，不再重复定义。**改动这里的任何一条，都要评估已经写了哪些业务代码会受影响。**

---

## 1. 为什么必须先定

下面这些问题的答案，一旦定错并且已经写了业务代码，返工代价极大：

- 一个人同时属于多个公司、多个部门、多个小组，登录后到底能看哪些数据？
- 部门表里的"上级"包不包括公司？公司是单独一张表还是树上的一个节点？
- "小组"和"项目组"是一回事吗？
- 用户登录后的角色是从哪张表算出来的？点一下角色切换，数据会变吗？

这些问题互相咬合，必须一起回答。

## 2. 组织架构模型

### 2.1 一棵树，三种节点

**全公司的所有组织单元放在同一棵树里，用 `dept_type` 区分类型。**

```
dept_type:  1=公司   2=部门   3=小组

集团总部 .................................. 公司
 ├── 技术中心 .............................. 公司（子公司）
 │    ├── 研发部 ........................... 部门
 │    │    ├── 前端组 ...................... 小组
 │    │    └── 后端组 ...................... 小组
 │    └── 测试部 ........................... 部门
 └── 华东分公司 ............................ 公司
      └── 研发部 ........................... 部门   ← 与「技术中心/研发部」同名，合法
```

**为什么不给公司单独建一张表？**

| 方案 | 代价 |
|---|---|
| 公司独立表 `sys_company` + 部门表 `sys_dept` | 组织树被切成两半：查"某公司下所有部门"要 union 两张表；审批流跨公司要跨表递归；两份 CRUD 代码 |
| **公司作为树上的节点（采纳）** | 只需一个 `dept_type` 字段 |

公司确实有独立属性（统一社会信用代码、法人、注册地址）。**等真的需要时再加一张 1:1 的扩展表 `sys_company`，主键与 `sys_dept.id` 相同**。这是低成本的演进路径，不会返工。

**这一条直接决定了 R01 的部门表要加 `dept_type` 字段。** 不加的话，前端无法区分渲染，也没法校验层级。

### 2.2 层级规则

| 节点类型 | 上级允许是 |
|---|---|
| 公司 | 只能是 0（顶级） |
| 部门 | 公司 或 部门 |
| 小组 | 部门 或 小组 |

注意这**不是**严格的"公司→部门→小组"三层。真实的公司经常是「公司 → 部门 → 子部门 → 小组 → 子小组」，所以只限制**类型递进方向**，不限制层数。

### 2.3 跨公司同名的合法性

「技术中心/研发部」和「华东分公司/研发部」是两个不同的部门，`parent_id` 不同，**必须允许同时存在**。

所以"同级不能同名"这条规则里的"同级"指的是**同一个 `parent_id`**，不是"同一层"。R01 的唯一键 `uk_sys_dept_parent_name (parent_id, dept_name)` 正是这个语义。

### 2.4 小组 ≠ 项目组（重要，别混）

| | 小组 | 项目组 |
|---|---|---|
| 例子 | 前端组、后端组、测试组 | 「2026 双十一大促项目组」 |
| 生命周期 | 长期，随组织架构调整 | 临时，项目结束就解散 |
| 成员来源 | 本部门内 | **跨部门抽调** |
| 归属 | 组织树上的固定节点 | 独立实体 |
| 数据隔离 | 走常规数据权限 | **硬隔离**：非成员绝对不能看，即使他是公司总经理 |
| 表 | `sys_dept`（`dept_type=3`） | `sys_project_group` + `sys_project_member` |

**这是两个不同的东西。** 如果把它们合成一张表，将来要么项目组解散时污染组织架构，要么硬隔离规则无处安放。

## 3. 人员模型

### 3.1 三层分离

一个人、一个登录凭证、一段任职关系，是三件事，必须拆开：

```
sys_person（人员）        一个自然人。跨公司唯一，用身份证号或工号标识
    │
    ├── sys_account（账号）  登录凭证：用户名、密码、状态
    │                       一个人员可以有多个账号（如主账号 + 移动端免登绑定）
    │
    └── sys_appointment（任职）  ★ 全部权限的来源
             ├── person_id   谁
             ├── org_id      挂在组织树的哪个节点上（指向 sys_dept.id）
             ├── role_id     以什么角色
             └── position    岗位名称（"财务经理"，仅用于显示）
```

**为什么人员和账号要分开？**

- 人员是**业务对象**：他有工号、有入职日期、有上级、有考勤记录、会被写进审批单
- 账号是**技术凭证**：它会被停用、会被改密码、会被异地登录锁定

如果合成一张表，一个员工离职后账号被停用，他的历史审批记录就跟着查不到了——因为"人员"没了。

### 3.2 一个人可以有 N 段任职

这是回答"跨公司、跨部门、跨小组"的核心：

```
张三（一个人，一个账号）
  ├─ 任职1：技术中心（公司）        × 财务经理    × 数据范围=本节点及以下
  ├─ 任职2：华东分公司/研发部       × 研发部主管  × 数据范围=本节点及以下
  └─ 任职3：技术中心/研发部/前端组  × 组员        × 数据范围=仅自己
```

**一个人员能跨到哪些公司/部门/小组，完全由他有多少段任职决定。** 不需要任何"跨公司"的特殊字段或特殊逻辑——多公司能力是任职表天然具备的。

## 4. 权限模型

### 4.1 职责分离

| 概念 | 定义什么 | 存在哪 |
|---|---|---|
| 角色 | "能做什么"：菜单、按钮、接口权限 | `sys_role` + `sys_role_menu` |
| 任职 | "在哪个节点上、以什么角色" | `sys_appointment` |
| 数据范围 | "能看到多远" | `sys_role.data_scope` |

**数据范围定义在角色上，不定义在人员上。** 因为同一个人在不同岗位上看到的数据范围本来就不同——他当财务经理时要看整个公司，当组员时只看自己。

### 4.2 数据范围取值

| 取值 | 含义 | 生成的 SQL 条件 |
|---|---|---|
| `SELF` | 只看自己 | `create_by = 当前人员ID` |
| `NODE` | 只看本节点 | `org_id = 任职.org_id` |
| `SUBTREE` | 本节点及以下 | `org_id IN (本节点子树的所有 id)` |
| `ALL` | 全部 | 不加条件（**仅限超管**） |

`SUBTREE` 需要"某节点的所有后代 id"。R01 的表**暂时没有 `ancestors` 路径字段**，取子树要靠递归 CTE。等 R04 真正需要时再评估是加 `ancestors` 冗余列还是用递归查询——**现在加是过早优化**。

### 4.3 多任职时数据取并集 ★

**这是你明确提出的需求，也是整个权限模型里最需要小心的一条。**

规则：**登录后，把每段任职的数据范围各自算出结果，然后取并集。**

以 §3.2 的张三为例：

```
任职1（财务经理，SUBTREE）→ 技术中心整棵树的所有财务数据
任职2（研发部主管，SUBTREE）→ 华东分公司/研发部子树的数据
任职3（组员，SELF）        → 只有他自己创建的

可见范围 = 任职1的结果 ∪ 任职2的结果 ∪ 任职3的结果
```

**"所有角色的数据都要显示出来"就是这个意思。**

#### 实现上的关键约束

并集**不能**简单翻译成一句 `WHERE org_id IN (所有节点的 id)`，因为每段任职的**权限类型不同**：

- 任职1 是 `SUBTREE` → 看技术中心子树
- 任职3 是 `SELF` → 只看自己创建的，**和 org_id 无关**

正确做法是**逐段任职生成一个条件，再用 OR 拼起来**：

```sql
WHERE (
        org_id IN (技术中心子树)              -- 任职1
     OR org_id IN (华东分公司/研发部子树)      -- 任职2
     OR create_by = 张三                      -- 任职3
      )
```

**如果图省事把所有节点合并成一个 `IN` 列表，任职3 的 `SELF` 约束就丢了**——张三点开"我提交的"会看到别人的数据。这是最容易写错、也最难测出来的一处。

#### 并集的边界

并集只在**同一隔离域**内生效。项目组是独立隔离域：**再高的职位，不是项目组成员就看不了该项目组的数据**。所以拼接条件时，项目组类数据走单独的判定分支，不参与并集。

### 4.4 跨公司的天然隔离

"技术中心的人事总监能不能看到华东分公司的 HR 数据？"

答：**只有他在华东分公司也有任职才可以**。任职表就是那道闸门，不需要额外写"跨公司隔离"的逻辑。

## 5. 登录后发生什么（完整闭环）

```
1. 用户提交 用户名 + 密码
2. 校验 sys_account（存在、启用、密码匹配、未锁定）
3. 由 account.person_id 查出该人员的全部任职：
      SELECT a.org_id, d.dept_name, a.role_id, r.role_name, r.data_scope
      FROM sys_appointment a
      JOIN sys_dept  d ON d.id = a.org_id
      JOIN sys_role  r ON r.id = a.role_id
      WHERE a.person_id = ? AND a.status = 1
4. 返回给前端：
      - 人员基本信息
      - 角色列表（全部，用于展示）
      - 每段任职的 org_id + data_scope（用于前端展示当前身份）
      - 令牌
5. 后续每个请求：从令牌解析出人员，加载任职列表，缓存
6. 每个需要数据权限的查询：按 §4.3 的规则逐段生成条件并 OR 拼接
```

前端据此可以做两件事：

- **展示**：把全部角色列出来（"财务经理 / 研发部主管 / 组员"）
- **切换**：用户点某个角色时，前端只做**筛选展示**，数据权限始终是并集——**不做"切到某个角色就只给这个角色的数据"**。切换只是视图过滤，不是权限收窄。

## 6. 这些分别在哪份需求里实现

| 内容 | 需求 | 依赖 |
