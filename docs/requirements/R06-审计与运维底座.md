# R06 审计与运维底座

> **前置**：[R01](R01-部门管理.md)（traceId）、[R02](R02-人员与账号.md)（登录、令牌）、[R03](R03-任职与角色.md)、[R05](R05-项目组与硬隔离.md)。

## 0. 为什么第六个需求是它

前面五份文档里，有三笔欠账被反复记下，全都指向同一件事——**"发生了什么"没有被记录下来**：

| 欠账 | 出自 | 现状 |
|---|---|---|
| 权限变更没有留痕 | R03 | 谁给谁加了什么角色，查不到 |
| 项目组成员变更没有留痕 | R05 | 谁能把自己加进项目组，查不到 |
| 导出将来必须复用数据权限 | R04 | 现在没有导出功能，但**这是最容易绕过权限的地方** |

还有一件被反复推迟的决策：**到底删不删数据。**

R01 物理删除部门，R02 人员只离职不删除，R03 任职只结束不删除。每一份都单独做了一次判断，**但没有一条统一的原则**。新建表的人会问"我这张表该不该有 `deleted` 字段"，而答案必须现在就定下来——**晚一份文档，就多一张表要改。**

R06 把这两件事一起收口。

## 1. 业务需求

### 1.1 业务背景

出了事要能查。

**场景一**：某个员工的角色在周二下午被改过，他多出了"财务经理"。谁改的？什么时候？改了哪一段？

**场景二**：一份客户原始资料出现在某个不该看到它的人的屏幕上。他怎么看到的？他是被加进项目组的，还是权限配置出了问题？

**场景三**：系统在凌晨开始报错。是代码发布导致的，还是有人改了数据？

三个场景都指向"**审计日志**"。而目前系统里一条都没有。

### 1.2 需求描述

1. **操作日志**：记录谁在什么时候、对什么、做了什么，包括**被拒绝的尝试**
2. **敏感操作必须留痕**：权限变更、任职变更、项目组成员变更、人员状态变更、账号操作
3. **登录日志**：谁在什么时候、从哪个 IP 登录成功或失败
4. **日志里不能出现密码和令牌**——包括请求参数里的
5. **统一的删除策略**，写进文档，新建表时照着做
6. **数据卫生**：定期找出孤儿数据、清理过期令牌
7. **运维清单**：健康检查、备份、**恢复演练**

### 1.3 验收标准

- [ ] 给某人授予一个角色后，能查到一条日志：谁、何时、给谁、授了什么
- [ ] **尝试停用最后一个超管被拒绝**，这个**失败的尝试也有日志**
- [ ] 登录失败有日志，且日志里能区分"用户名不存在"和"密码错误"
- [ ] **登录接口的响应里区分不出来**（R02 的 A6 仍然成立）
- [ ] 改一次密码，然后**扫描整张日志表，搜不到新密码的明文**
- [ ] 日志表**查不到任何 UPDATE / DELETE 的入口**（只有查询接口）
- [ ] 能跑一次孤儿数据体检，输出"任职指向已删除人员"这类问题
- [ ] 过期令牌被自动清理，`sys_token` 行数不随时间无限增长
- [ ] `/actuator/health` 能反映数据库连通性
- [ ] 备份脚本存在，**并且在测试环境成功恢复过一次**（有记录）

## 2. 需求解构

### 2.1 先定删除策略

**这是本需求最先要做的事**，因为它影响所有表，而且是纯决策、不写代码。

#### 结论：不引入全局 `deleted` 字段

很多项目的做法是每张表加一个 `deleted TINYINT`。**本系统不这么做。**

**`deleted` 字段的代价**：

1. **每一条查询都必须记得加 `deleted = 0`。** 漏一条就是脏数据或数据泄露——**而且是静默的**。手写 SQL、MyBatis-Plus 的自动填充、联表查询，每一处都可能漏
2. **唯一键全部要重新设计。** "部门编码唯一"在有 `deleted` 之后变成"未删除的部门编码唯一"，MySQL 的唯一索引表达不了这个，要靠生成列或者应用层校验
3. **它换来的能力很少被真正使用。** 说是为了"能恢复误删"，但实际上，**恢复误删靠的是备份**——一个被 `deleted = 1` 标记的行，业务上已经和删掉没区别了，你几乎不会去恢复它

**"要么不删，要么真删"，中间状态只在极少数场景有价值。**

#### 三分类策略

| 类别 | 策略 | 本系统的表 |
|---|---|---|
| **审计与日志** | **只增**，不提供改和删的接口 | `sys_operation_log`、`sys_login_log` |
| **有业务历史的** | **永不删除**，用状态或时间区间表达"不再有效" | `sys_person`（离职）、`sys_appointment`（结束）、`sys_project_member`（离开） |
| **纯配置的** | **物理删除**，但删之前必须校验"没有活引用" | `sys_dept`、`sys_role`、`sys_account` |

**"有业务历史"和"纯配置"怎么分？**

问一个问题：**"这条记录被删掉之后，还能不能回答一个业务问题？"**

- 人员被删了 → "张三 2023 年在这家公司吗？" 答不上来 → **不能删**
- 任职被删了 → "张三去年是哪个部门的？" 答不上来 → **不能删**
- 部门被删了 → "2023 年有没有测试部？" 答不上来。**但部门是配置，业务问题应该问人和任职** → 可以删，**前提是它下面没有有效任职**（R03 的 B11）

**这个判断标准比"这张表重不重要"有用得多**，因为它问的是"删了之后什么信息永久丢失"。

#### 什么时候 `deleted` 是对的

**当"删除"是产品功能，而不是数据策略的时候。**

比如：用户自己写的一份草稿，界面上有"删除"按钮，也提供"回收站"。

这时用 `deleted_at DATETIME NULL` 比布尔值好——**时间戳能回答"什么时候删的"，布尔值不能**。再配一个生成列解决唯一键问题：

```sql
deleted_at DATETIME(3) NULL,
-- 未删除时参与唯一键，删除后为 NULL（NULL 不参与唯一性）
active_key VARCHAR(64) GENERATED ALWAYS AS
    (IF(deleted_at IS NULL, CONCAT(dept_code), NULL)) STORED,
UNIQUE KEY uk_dept_code_active (active_key)
```

**R06 不做这个**——现在没有"用户可删除的内容"。**但记下这个模式**，等做文档协作时用得上。

### 2.2 操作日志

#### 表结构

```sql
sys_operation_log
- id             BIGINT UNSIGNED AUTO_INCREMENT
- trace_id       VARCHAR(32)     -- 关联 R01 的 traceId，能把一次请求的多条日志串起来
- person_id      BIGINT UNSIGNED -- 操作人，未登录时为 NULL
- person_name    VARCHAR(50)     -- ★ 冗余，不靠 join
- module         VARCHAR(50)     -- 如 system.person
- action         VARCHAR(50)     -- 如 change-status
- description    VARCHAR(500)    -- 人能读懂的描述
- http_method    VARCHAR(10)
- request_uri    VARCHAR(500)
- request_param  TEXT            -- ★ 已脱敏
- success        TINYINT         -- 1 成功 / 0 失败
- result_code    INT             -- 业务返回码
- error_message  VARCHAR(1000)   -- 失败时的异常摘要
- ip             VARCHAR(45)
- user_agent     VARCHAR(500)
- cost_ms        INT
- create_time    DATETIME(3)     -- 毫秒精度，同一次请求的多条日志要能排序
```

索引：`idx_log_person (person_id, create_time)`、`idx_log_create (create_time)`、`idx_log_module (module, create_time)`、`idx_log_trace (trace_id)`

**★ `person_name` 冗余存储，不 join `sys_person`。**

因为人员**会改名**。三年后查日志，"张三"当时叫什么，日志应该反映**当时**的情况。join 出来的永远是现在的名字。

**这是审计日志和业务查询的本质区别**：审计日志要还原**当时的事实**，不是**现在的视图**。

同样的道理适用于任何会变的字段——**日志要存快照，不要存引用**。

**★ `create_time` 用毫秒精度。**

同一次请求可能产生多条日志（比如"变更角色权限"同时影响多条），秒级精度下排序不稳定。

#### 写入时机：独立事务

**这是本需求里最重要的一个设计决定。**

直觉答案是"日志必须和业务操作在同一个事务里，保证要么都有要么都没有"。**本系统不这么做，日志用 `REQUIRES_NEW` 独立事务写。**

理由：**失败操作的日志，比成功操作的日志更有审计价值。**

- "谁试图停用最后一个超级管理员，被系统拒绝了" ← **这是最有价值的记录**
- "谁成功登录了" ← 有用，但远不如上一条

如果日志和业务同事务，那么业务抛异常回滚时，**日志也被一起回滚——最有价值的那条记录恰恰被抹掉了**。

代价：**"操作成功"和"有日志"不是原子的**，极端情况下（业务提交成功、日志写入失败）会丢一条日志。

**为什么可以接受**：

1. 日志和业务写的是**同一个数据库**，同一时刻只挂一边的可能性极低
2. 日志写入失败会**抛异常 + 打 ERROR 日志 + 触发告警**，不会静默
3. 反过来（同事务）的代价是**系统性地丢失所有失败记录**——这是确定会发生的，不是极端情况

**"确定的损失"比"极端情况下的损失"更值得避免。**

#### `@AuditLog` 注解

```java
@AuditLog(
    module = "system.person",
    action = "change-status",
    description = "'把人员【' + #personId + '】的状态改为 ' + #request.status"
)
```

- 标在 **Controller 的写方法**上（`POST` / `PUT` / `DELETE`）
- `description` 支持 **SpEL**，能取到方法参数
- **SpEL 表达式解析结果要缓存**（按方法维度缓存 `Expression` 对象），不要每次请求重新 parse

**为什么 `description` 要支持 SpEL 而不是写死一段文字？**

因为"变更人员状态"这种描述等于没说——**日志的价值全在"对谁"和"变成什么"**。只有静态描述的日志，查起来还得再去反解 `request_param` 里的 id。

SpEL 的代价是一次表达式解析（已缓存），换来的是**日志直接可读**。

#### 敏感参数脱敏

**必须在写入前过滤**，不能指望"我们不会传密码"。

规则：

1. 字段名匹配（不区分大小写）`password`、`oldPassword`、`newPassword`、`token`、`secret`、`authorization`、`credential` → 值替换为 `***`
2. 递归处理嵌套对象和数组
3. `request_param` 有长度上限（比如 4000 字符），超长截断并标注

**第 3 条容易被忽略**：一个批量导入接口的请求体可能有几 MB，直接写进 `TEXT` 列会让日志表爆炸。

#### 日志的访问

- **只有查询接口，没有修改和删除接口**
- 查询需要权限码 `system:log:list`
- 删除只能通过 DBA 直接操作数据库（**这本身应该被数据库审计记录**）

**"日志表没有删除接口"是一条纪律，不是技术限制。**

### 2.3 登录日志

```sql
sys_login_log
- id           BIGINT UNSIGNED AUTO_INCREMENT
- username     VARCHAR(50)   -- ★ 尝试登录的用户名，可能根本不存在
- person_id    BIGINT UNSIGNED NULL
- success      TINYINT
- fail_reason  VARCHAR(30) NULL   -- USER_NOT_FOUND / BAD_CREDENTIALS /
                                 -- ACCOUNT_DISABLED / PERSON_LEFT / TOKEN_EXPIRED
- ip           VARCHAR(45)
- user_agent   VARCHAR(500)
- create_time  DATETIME(3)
```

索引：`idx_login_username (username, create_time)`、`idx_login_ip (ip, create_time)`、`idx_login_person (person_id, create_time)`

#### ★ 日志里区分原因，API 响应里不区分

这是本文档里一个漂亮的小设计点。

R02 的 A6 要求：**用户名不存在和密码错误，必须返回完全相同的响应**，否则能筛出真实账号。

但那说的是**给用户看的响应**。**日志是给管理员看的**，那里必须区分——因为：

- "同一个 IP 在 5 分钟内试了 300 个不同的、都不存在的用户名" ← **这是账号枚举攻击的典型特征**，日志不区分就发现不了
- "同一个账号被从 10 个不同 IP 尝试密码" ← 撞库特征

**对用户不区分，对日志区分。** 这不是自相矛盾，因为两者的读者和用途完全不同。

> **注意**：`fail_reason` 里的 `USER_NOT_FOUND` 让日志本身成了敏感数据。所以 `system:log:list` 这个权限码要谨慎授予——
> **能看登录日志的人，能看到公司里有哪些用户名是真实存在的。**

### 2.4 数据卫生

不用外键的代价（R03 §2.1 明确记录过）：**可能出现孤儿数据。**

#### 孤儿数据体检

一张体检项清单：

| 检查项 | SQL 形态 |
|---|---|
| 任职指向不存在的人员 | `sys_appointment.person_id NOT IN (SELECT id FROM sys_person)` |
| 任职指向不存在的组织节点 | 同上，对 `org_id`（**排除 `org_id = 0` 的全局任职**） |
| 任职指向不存在的角色 | 同上，对 `role_id` |
| 项目组成员指向不存在的组/人员 | 对 `sys_project_member` |
| 项目资料指向不存在的组 | 对 `sys_project_doc` |
| 令牌指向不存在的人员 | 对 `sys_token` |
| 部门的 `parent_id` 指向不存在的节点 | 对 `sys_dept` |
| 组织树里有环 | 沿 `parent_id` 走，超过最大深度即判定为环 |

**★ 体检结果只报告，不自动修复。**

理由：自动修复有两个方向，**两个都错**：

- **自动删除孤儿行** → 万一"不存在的人员"是因为数据正在迁移中，你就把好数据删了
- **自动跳过不报告** → 报告永远不清零，很快就没人看了

**正确做法：报告 + 人工确认 + 手工脚本修。** 体检任务的价值是**让你知道**，不是**替你决定**。

输出方式：写进 `sys_operation_log`（`module = maintenance`）+ 打 WARN 日志。有问题的行数不为 0 时应该触发告警。

#### 过期令牌清理

R02 的 `sys_token` 表会**无限增长**——每登录一次加一行，从来没有删除。

```
每天凌晨清理：expires_at < NOW() - INTERVAL 7 DAY
```

**保留 7 天缓冲**，而不是立刻删。因为：

- 排查问题时，需要看"这个令牌什么时候过期的"
- 用户投诉"我怎么突然要重新登录了"，有历史可查

**清理任务必须幂等、可重复执行**，且**要有日志**（删了多少行）。

#### 日志保留期

| 日志 | 保留期 | 到期处理 |
|---|---|---|
| `sys_operation_log` | 1 年 | 导出 CSV 归档后删除 |
| `sys_login_log` | 6 个月 | 同上 |
| `sys_token` | 过期后 7 天 | 直接删除 |

**R06 只实现令牌清理。** 日志归档涉及冷存储和合规确认，**先定义策略、加好 `create_time` 索引**，等实际有了合规要求再做。

> **为什么先做令牌清理？** 因为它的增长是**确定的、线性的**——只要有用户在用，表就会一直涨。而日志表的增长速度取决于业务量，短期压力小。
> **先解决确定会出问题的那个。**

### 2.5 分层与包结构

```
com.wenshan.oa
├── framework/audit/                  ← 新增
│   ├── AuditLog.java                 注解
│   ├── AuditLogAspect.java           切面，REQUIRES_NEW 写日志
│   ├── AuditLogRecord.java           日志内容的值对象
│   └── SensitiveDataMasker.java      脱敏（纯函数，好测）
├── common/permission/Permission.java 改：加 system:log:list 等
├── system/
│   ├── log/                          ← 新增
│   │   ├── controller/LogController.java        只读接口
│   │   ├── service/LogService.java + impl
│   │   ├── mapper/ + entity/ + dto/
│   │   └── entity/SysOperationLog.java、SysLoginLog.java
│   └── maintenance/                  ← 新增
│       ├── DataIntegrityChecker.java           孤儿体检
│       ├── TokenCleanupJob.java                过期令牌清理
│       └── MaintenanceController.java          手动触发（需要权限码）
```

**`SensitiveDataMasker` 做成纯静态函数**——输入一个对象，输出脱敏后的字符串。**不依赖 Spring、不依赖数据库**，因此可以纯单元测试。

这和 R04 的 `DataScopeHelper` 是同一个思路：**把安全关键的逻辑从框架里剥出来，让它可测。**

**`DataIntegrityChecker` 的检查项用配置驱动**，不要把 8 条 SQL 硬编码在一个方法里。

```
List<IntegrityCheck> checks = List.of(
    new IntegrityCheck("任职指向不存在的人员",
        "SELECT COUNT(*) FROM sys_appointment a LEFT JOIN sys_person p ON p.id = a.person_id WHERE p.id IS NULL",
        "SELECT a.id FROM sys_appointment a LEFT JOIN sys_person p ON p.id = a.person_id WHERE p.id IS NULL LIMIT 100"),
    ...
);
```

加检查项时只加一行，不用改方法体。

### 2.6 接口契约

| 方法 | 路径 | 权限码 | 说明 |
|---|---|---|---|
| GET | `/api/system/logs/operations` | `system:log:list` | 操作日志分页查询 |
| GET | `/api/system/logs/operations/{id}` | `system:log:list` | 详情（含完整 `request_param`） |
| GET | `/api/system/logs/logins` | `system:log:list` | 登录日志分页查询 |
| GET | `/api/system/maintenance/integrity` | `system:maintenance:run` | 跑一次孤儿体检，返回问题列表 |
| POST | `/api/system/maintenance/token-cleanup` | `system:maintenance:run` | 手动触发令牌清理 |

**没有 `PUT` / `DELETE`。** 见 §2.2 的纪律。

查询过滤条件（操作日志）：`personId`、`module`、`action`、`success`、`traceId`、`startTime`、`endTime`。

**`traceId` 过滤很有用**：一次请求产生的多条日志能一起捞出来（R01 的 traceId 到这里才发挥全部价值）。

#### 新增权限码

```
system:log:list
system:maintenance:run
```

**`system:maintenance:run` 要谨慎授予**——手动触发体检是重查询，在数据量大时会影响性能。

### 2.7 业务规则

**本需求不新增业务错误码**（日志是只读的，体检是查询）。

---

**E1｜所有写接口必须同时有 `@RequiresPermission` 和 `@AuditLog`**

这是 R03 的"注解覆盖率测试"的直接扩展。**同一条测试，多断言一个注解。**

```
遍历所有 Controller：
  对每个 @PostMapping / @PutMapping / @DeleteMapping 方法：
    断言有 @RequiresPermission
    断言有 @AuditLog        ← R06 新增
```

**为什么这条规则值得用测试钉住？** 因为漏记审计日志的后果和漏加权限注解一样——**静默**。系统照常工作，只是某一天你需要查"这是谁改的"的时候，发现没有记录。

**而且你没法在事后补记。** 权限漏加可以补，日志漏记就是永久缺失。

---

**E2｜审计日志用独立事务写（`REQUIRES_NEW`）**

见 §2.2。**失败了也要有记录**，这是审计日志的主要价值。

---

**E3｜日志里不能出现密码、令牌、密钥——包括嵌套结构里的**

必须有测试。测试方法：

```
1. 调一次修改密码的接口
2. 查最近一条 sys_operation_log
3. 断言 request_param 里不含新密码的明文
4. 再全表扫一遍：SELECT COUNT(*) FROM sys_operation_log WHERE request_param LIKE '%' || :newPassword || '%'
   期望 0
```

**第 4 步是关键**——它检查的是**所有日志**，而不只是刚写的那条。因为脱敏可能只在某些路径上生效，全表扫描能发现漏网。

**这个测试要真的写，不要只在文档里说。** 密码泄进日志表是最常见的生产事故之一，而且**一旦写进去，它会跟着备份一起被复制到各处**。

---

**E4｜日志表只增，不提供修改和删除的接口**

代码上不写 `update` / `delete` 的 Mapper 方法。**没有方法，就没有人会不小心调用它。**

比"约定不要删"强得多。

---

**E5｜日志冗余存快照，不存引用**

`person_name` 冗余存。理由见 §2.2：人员会改名，审计日志要还原**当时**的事实。

**同样的纪律适用于任何会变的字段。** 将来日志里如果记"部门名"，也要冗余存。

---

**E6｜登录失败的原因：日志里区分，API 响应里不区分**

见 §2.3。

---

**E7｜删除策略按 §2.1 的三分类执行**

新建表时必须先归类，再决定有没有删除接口。

**"有业务历史"的判定标准**：删掉之后，会永久丢失一个业务问题的答案。

---

**E8｜不引入全局 `deleted` 字段**

见 §2.1。需要"回收站"类功能时，用 `deleted_at` 时间戳 + 生成列维护唯一键，不要用布尔值。

---

**E9｜孤儿数据只报告，不自动修复**

见 §2.4。自动修复的两个方向都是错的。

---

**E10｜过期令牌必须清理，清理任务必须幂等**

R02 的 `sys_token` 会线性增长。清理条件 `expires_at < NOW() - INTERVAL 7 DAY`。

**幂等**意味着重复执行结果相同——用 `DELETE ... WHERE expires_at < ...` 天然幂等，但要**确认它不会因为一次执行太久而锁表**。数据量大时应该分批删（`LIMIT 1000` 循环）。

---

**E11｜备份必须演练过，否则不算备份**

见 §2.8。

### 2.8 运维清单

**这部分不是代码需求，但不做的话前面所有工作都可能在一次事故里归零。**

#### 健康检查

`/actuator/health` 已经在 R01 打通。R06 要确认它**真的检查了数据库**：

```properties
management.endpoint.health.show-details=when-authorized
management.health.db.enabled=true
```

**为什么这条重要？** 因为一个只返回 `{"status":"UP"}` 的健康检查**会在数据库挂掉的时候依然返回 UP**——如果它没有配置数据库检查项。监控系统看到 UP，没人知道服务已经不可用了。

#### 备份

- 每天凌晨全量 `mysqldump`，压缩后保留 30 天
- 备份文件**不能和应用放在同一台机器上**（机器挂了，备份跟着挂）
- 备份完成后**校验文件非空且能解压**（空文件是静默失败）

#### ★ 恢复演练

**没有演练过的备份，等于没有备份。**

每季度在测试环境做一次：

```bash
mysql -h 127.0.0.1 -u root -p oa_restore < backup-2026-01-15.sql
# 然后验证：
#   1. 表数量对不对
#   2. flyway_schema_history 的最新版本，和应用启动时要求的版本是否一致
#   3. 抽查几条关键数据（比如超管的任职还在不在）
```

**第 2 条是恢复流程里最容易出事的地方。**

Flyway 的迁移脚本是**跟着代码走**的。如果代码已经到 V8，而备份是 V5 时刻的，恢复之后：

- 应用启动 → Flyway 检查 `flyway_schema_history` 发现是 V5 → **自动执行 V6、V7、V8 的迁移**
- **这通常是好事**，但如果 V6 的迁移脚本写了"如果表已存在就报错"，或者 V7 是一次数据订正（不是结构变更），重放可能产生错误的结果

**规则：恢复旧备份后，先看 `flyway_schema_history`，再决定是让 Flyway 自动补，还是手工对齐版本。**

#### 日志文件轮转

R01 已经配了 logback。确认：

- 单个文件不超过 100MB
- 保留 30 天
- **应用日志和审计日志分开文件**——审计日志的保留期更长，且不应该被应用日志的轮转策略冲掉

#### 定时任务清单

| 任务 | 频率 | 失败后果 |
|---|---|---|
| 过期令牌清理 | 每天 03:00 | 表无限增长，最终拖慢登录 |
| 孤儿数据体检 | 每天 04:00 | 没人知道数据在腐烂 |
| 数据库备份 | 每天 02:00 | **灾难时无法恢复** |
| 恢复演练 | 每季度 | 以为有备份，实际不能用 |

---

### 2.9 本需求明确不做的事

- **不做日志的归档与冷存储** —— 只定义保留期策略并加好索引。等有合规要求再做
- **不做实时告警** —— 体检和清理的失败现在只打 ERROR 日志。接入监控告警是运维侧的事
- **不做日志的完整性保护**（防篡改哈希链）—— 有权限的人能改数据库里的日志。**记一个待办**：如果审计要求"日志不可篡改"，需要哈希链或写入独立的存储
- **不做字段级的变更前后值对比** —— 日志记的是请求参数，不是"改前是什么、改后是什么"。真正的数据变更审计需要 CDC 或者每张表的变更历史表，成本高得多。**现在不做，但要知道这个缺口**
- **不做"谁看了这条日志"的二次审计** —— 有点过度设计
- **不做数据导出** —— R04 记的待办仍然挂在那里
- **不做数据库层面的权限隔离** —— 应用用的还是 root 账号。生产环境应该用最小权限账号

### Step 2：`SensitiveDataMasker`（纯函数，先写它）

**目标**：脱敏逻辑可测、与框架无关。

**产物**：`framework/audit/SensitiveDataMasker.java`

**为什么先写它？** 因为它是 R06 里**唯一一条"写错了就是安全事故"**的逻辑，而它恰好是最容易写成纯函数的。先把它测透，后面的切面就简单了。

**契约**

```
String mask(Object value)      // 任意对象 → 脱敏后的 JSON 字符串，超长截断
```

**必须覆盖的用例**

| 输入 | 期望 |
|---|---|
| `{"username":"zs","password":"abc123"}` | `password` 的值变成 `***` |
| 嵌套 `{"user":{"pwd"...}}` | 递归处理 |
| 数组 `[{"password":"a"},{"password":"b"}]` | 两个都脱敏 |
| 字段名大小写混写 `PassWord` | 仍然脱敏（**大小写不敏感匹配**） |
| `null` | 返回 `null` 或 `"null"`，不抛异常 |
| 超过 4000 字符 | 截断并标注 `...[truncated]` |
| **对象序列化失败**（循环引用） | **不抛异常**，返回 `[serialize-failed]` |

**最后一条是重点**：脱敏是日志路径上的代码。**如果它抛异常，会把一次正常的业务请求变成失败**——因为日志写不出去。

**日志路径上的代码永远不该让请求失败。** 这是本步骤最重要的一条设计约束。

---

### Step 3：`sys_operation_log` + `@AuditLog` + 切面

**目标**：写接口自动产生日志。

**产物**：`V6__init_audit_log.sql`、`AuditLog` 注解、`AuditLogAspect`

**切面要点**

```
@Around("@annotation(auditLog)")
Object around(ProceedingJoinPoint pjp, AuditLog auditLog) {
    long start = ...;
    try {
        Object result = pjp.proceed();
        record(..., success = true, resultCode = 从 result 里取);
        return result;
    } catch (Throwable t) {
        record(..., success = false, errorMessage = t.getMessage());
        throw t;                       // ★ 必须原样抛出
    } finally {
        // 计算 cost_ms
    }
}
```

**三个容易写错的地方**

1. **异常必须原样抛出** —— 吞掉异常会让业务失败变成"看起来成功了"
2. **`record` 自己在独立事务里** —— `@Transactional(propagation = REQUIRES_NEW)`。**注意：切面里的自调用不会走代理**，所以 `record` 必须放在**另一个 Spring Bean** 里（`AuditLogWriter`），不能是切面的私有方法。这是 Spring AOP 最经典的坑
3. **`record` 自己抛异常时不能再抛出去** —— 见 Step 2 的约束。`record` 内部要 catch 所有异常，只打 ERROR 日志

**第 2 条是本步骤最容易卡住的地方。** 现象是"日志写进去了，但业务回滚时日志也跟着回滚了"，或者"业务报错时日志没了"——因为 `REQUIRES_NEW` 根本没生效。

**`resultCode` 从哪来？** 如果 Controller 返回统一的 `Result<T>`，从 `result.getCode()` 取。如果返回的不是 `Result`（比如文件下载），记为 `null`。

**完成的标志**

```bash
# 调一次写接口
curl -X PUT http://127.0.0.1:8090/api/system/persons/1/status \
  -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' -d '{"status":0}'

# 查日志
mysql -h 127.0.0.1 -u root -p123456 oa -e \
  "SELECT person_name, module, action, description, success FROM sys_operation_log ORDER BY id DESC LIMIT 1"
# 期望：能看到操作人姓名和可读的描述
```

### Step 5：`sys_login_log` 接入登录

**目标**：登录成功和失败都有记录。

**产物**：`V6` 迁移里加表、改 `AuthServiceImpl.login`

**实现要点**

- **成功和失败都要记**——包括"用户不存在"这种没有任何 `person_id` 的情况
- `fail_reason` 用枚举值，不要写自由文本（自由文本会变成 `"密码错"` / `"密码错误"` / `"pwd wrong"` 三种）
- **写登录日志同样不能影响登录本身**：日志写失败不能让用户登不进来
- `username` 要**原样记录尝试的值**，不要先 trim 或转小写——攻击者试的可能就是 `" admin"` 这种变体

**★ 验证 R02 的 A6 没有被破坏**

```bash
  -H 'Content-Type: application/json' -d '{"username":"nobody","password":"x"}'
# 密码错误
curl -s -X POST http://127.0.0.1:8090/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"zhangsan","password":"wrong"}'

# 两个响应的 code 和 message 必须【完全一致】
```

然后查日志，两条的 `fail_reason` **必须不同**（`USER_NOT_FOUND` vs `BAD_CREDENTIALS`）。

**这两条一起验证，才说明 E6 做对了。** 只测一条都说明不了问题。

### Step 6：数据卫生

**目标**：孤儿体检 + 令牌清理。

**产物**：`DataIntegrityChecker`、`TokenCleanupJob`、`MaintenanceController`

**实现顺序**

1. 先写 `IntegrityCheck` 值对象和 8 个检查项（配置驱动）
2. `DataIntegrityChecker.run()` 返回 `List<IntegrityCheckResult>`（检查名 + 问题条数 + 前 100 条 id）
3. `TokenCleanupJob`（分批删）
4. 定时任务注册
5. 手动触发接口

**令牌清理的分批写法**

```sql
DELETE FROM sys_token WHERE expires_at < NOW() - INTERVAL 7 DAY LIMIT 1000
```

循环执行直到影响行数为 0，每批之间 sleep 100ms。

**为什么要分批？** 一次删 100 万行会：
- 长时间持有锁，登录接口被阻塞
- 产生巨大的 binlog
- 撑爆 undo log

**这是"上线后才会遇到"的典型问题**——开发环境只有几十行，`DELETE` 秒回。**所以代码要一次写对，不能等出了问题再改。**

**完成的标志**

```bash
# 手工插入一条过期令牌
mysql ... -e "INSERT INTO sys_token (person_id, token_hash, expires_at, create_time) VALUES (1,'x', NOW() - INTERVAL 30 DAY, NOW())"

# 手动触发行清理
curl -X POST http://127.0.0.1:8090/api/system/maintenance/token-cleanup -H "Authorization: Bearer $ADMIN"
# 期望：返回删除行数 ≥ 1

# 跑孤儿体检
curl -s http://127.0.0.1:8090/api/system/maintenance/integrity -H "Authorization: Bearer $ADMIN" | python3 -m json.tool
# 期望：所有检查项 count 都是 0
```

**再做一次"制造问题"的验证**：手工插一条 `person_id = 99999` 的任职（**绕过 Service，直接写库**），再跑体检 → 应该报告 1 条。

**这一步必须真的做。** 体检代码最典型的 bug 是"SQL 写错了，永远返回 0"——**看起来一切正常，实际上什么都没检查**。

**目标**：健康检查、备份、恢复演练。

**产物**：备份脚本、恢复步骤文档、演练记录

**验证方法**：

## 5. 完成后你会得到什么

**能力上**：你补上了"**系统知道自己身上发生了什么**"这个能力。

前面五份文档做的都是"让系统正确工作"。R06 做的是"**让系统能够被怀疑和追问**"。这两件事的技术难度差不多，但后者的价值只在出事的时候才体现——**而它必须提前做，因为日志不能事后补记。**

你还第一次处理了**"确定性损失 vs 极端情况损失"**的权衡（E2 的日志事务）。直觉答案（同事务）会导致**系统性**地丢掉所有失败记录；而反直觉的答案（独立事务）只在一个几乎不可能同时发生的场景下丢日志。**选那个你知道会怎么坏的方案。**

**你现在拥有的完整地基**：

```
R00 组织与权限模型      —— 坐标系统
R01 部门管理            —— 组织树
R02 人员与账号          —— 人、认证
R03 任职与角色          —— 授权、鉴权
R04 数据权限落地        —— 行级数据可见性
R05 项目组与硬隔离      —— 隔离域
R06 审计与运维底座      —— 可追溯、可运维
```

**接下来是业务域**：考勤、请假审批、文档协作、报表。

**它们全部建立在这套地基上**，而且每一份新需求都必须回答地基定下的三个问题：

1. **新表的删除策略是什么？**（§2.1 的三分类）
2. **`org_id` 怎么定？**（R04 §C13：不能默认"Service 会填"）
3. **要不要记审计日志？**（E1：写接口必须有 `@AuditLog`）

**第四个问题在 R05 之后也要问**：**这张表属于哪个隔离域？**（组织域、项目组域，还是能跨域）
