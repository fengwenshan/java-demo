## 0. 为什么第二个需求是它

R01 建好了"坐标系"，但里面一个人都没有。R02 回答一个最基本的问题：**谁在用这个系统。**

它同时是你第一次碰**安全**。前面写的都是 CRUD 和树，写错了功能不对；R02 写错了，密码泄露、越权登录、下线不掉——性质完全不同。

R02 的终点是：**用账号密码登录，拿到令牌，带着令牌访问受保护接口，系统知道你是谁。**

## 1. 业务需求

### 1.1 业务背景

HR 现在有两份东西：一份 Excel 人员名册，一份各种系统的账号表。两边对不上——

- 人离职了，账号还在
- 人调岗了，名册改了，账号还是老的
- 有人离职半年还能登录

### 1.2 需求描述

1. 维护人员档案：工号、姓名、手机号、邮箱、入职日期
2. 人员有在职 / 离职两种状态
3. 每个人员开通一个登录账号（**一人一号**）
4. 人员离职时，账号立即失效，**正在登录的会话要立刻踢下线**
5. 管理员可以重置别人的密码
6. 人员能用自己的账号密码登录，拿到一个令牌
7. 带着令牌能访问受保护接口，系统知道"现在是谁在操作"
8. 人员列表要能分页、按工号/姓名搜索、按状态筛选

### 1.3 验收标准

- [ ] 能新建人员并同时开通账号
- [ ] 工号、手机号、用户名三者都不能重复（提示具体是哪个重复了）
- [ ] 数据库里的密码字段**看起来是一串乱码**，不是 `123456`
- [ ] 用正确的用户名密码能登录，拿到令牌
- [ ] 用错误的密码登录，提示"用户名或密码错误"——**不能提示"用户不存在"**
- [ ] 不带令牌访问 `/api/system/persons`，返回 401
- [ ] 带有效令牌访问同一个接口，返回数据
- [ ] **把某人置为离职后，他手里的令牌立刻失效**（下一个请求就 401）
- [ ] 人员列表分页正确，总数和页数对得上
- [ ] 上面每一条都有自动化测试

## 2. 需求解构

### 2.1 数据模型

三张表：**人员**（业务对象）、**账号**（登录凭证）、**令牌**（会话）。

#### `sys_person` 人员

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `person_no` | VARCHAR(30) NOT NULL | 工号，全局唯一 |
| `person_name` | VARCHAR(30) NOT NULL | 姓名 |
| `phone` | VARCHAR(20) NOT NULL | 手机号，全局唯一（将来短信登录要用） |
| `email` | VARCHAR(100) NULL | 邮箱 |
| `hire_date` | DATE NOT NULL | 入职日期 |
| `status` | TINYINT NOT NULL DEFAULT 1 | 1 在职 / 0 离职 |
| `create_time` / `update_time` | DATETIME | 同 R01 |

唯一键：`uk_sys_person_no (person_no)`、`uk_sys_person_phone (phone)`

> **没有 `org_id` 字段，这是刻意的。** 一个人属于哪个部门，由 R03 的任职表表达。
> 现在为了"人员列表能显示部门"而加一个 `org_id`，等 R03 做完就要删——而且那时已经有一批数据了。
> **一个人员能跨多家公司、多个部门，任何"单个 org_id"的表达都是错的。**

> **没有删除接口。** 人员不物理删除，也不逻辑删除，只有"离职"。
> 理由：人员会被历史审批单、考勤记录引用。删了人，那些单据就断链了。
> **HR 系统里没有删除员工这个操作**——只有离职。

#### `sys_account` 账号

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `person_id` | BIGINT UNSIGNED NOT NULL | 所属人员 |
| `username` | VARCHAR(50) NOT NULL | 登录名，全局唯一 |
| `password` | VARCHAR(100) NOT NULL | **密码哈希**，不是明文 |
| `status` | TINYINT NOT NULL DEFAULT 1 | 1 正常 / 0 停用 |
| `last_login_time` | DATETIME NULL | 最后登录时间 |
| `create_time` / `update_time` | DATETIME | 同 R01 |

唯一键：`uk_sys_account_person (person_id)`（**一人一号**，R00 §7 已确认）、`uk_sys_account_username (username)`

> `password` 长度给 100：BCrypt 输出 60 字符，PBKDF2 编码后更长。**别按"密码最长 20 位"去定字段长度**，存的不是密码本身。

#### `sys_token` 令牌

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `person_id` | BIGINT UNSIGNED NOT NULL | 令牌属于谁 |
| `token_hash` | CHAR(64) NOT NULL | **令牌的 SHA-256 十六进制**，不是令牌原文 |
| `expire_time` | DATETIME NOT NULL | 过期时间 |
| `create_time` | DATETIME | 签发时间 |

唯一键：`uk_sys_token_hash (token_hash)`；索引 `idx_sys_token_person (person_id)`

**为什么令牌也要哈希存储？**

令牌就是"已经验证过的密码"——拿着它就能操作。如果数据库泄露时存的是原文，攻击者不需要破解任何密码，直接拿令牌就能登录所有人的账号。

存 SHA-256 后，泄露的是一堆哈希，**没法反推出令牌**。而校验时我们只需要对传来的令牌做一次 SHA-256 再比对，不需要还原原文。

> **注意**：密码用 BCrypt（有意设计得慢），令牌用 SHA-256（快哈希）。
> 因为令牌是**随机生成的 256 位**，没有"猜"的可能，不需要慢哈希；密码是人选的，必须慢。
> **别把这两个用反。**

#### 为什么不用 JWT

选项是 JWT（无状态）或数据库令牌（有状态）。**本系统选数据库令牌**：

| | JWT | 数据库令牌（采纳） |
|---|---|---|
| 离职后立即失效 | **做不到**（签发即有效，只能等过期） | 删掉那行就失效 |
| 停用账号立即踢下线 | 做不到 | 删掉该人所有令牌 |
| "退出登录" | 假动作，只能前端删本地 | 真删，立即失效 |
| 额外依赖 | 需要 JWT 库 | **零** |
| 代价 | — | 每个请求多一次主键查询 |

对一个**内部 OA**（几百人）来说，"离职员工必须立刻登不进来"是硬需求，"无状态水平扩展"是伪需求。**多一次主键查询换即时下线能力，这笔买卖划算。**

如果将来真的要无状态，再换 JWT 也不迟——`AuthService` 的接口不变，只换实现。

### 2.3 接口契约

#### 认证

| 方法 | 路径 | 用途 | 需要登录 |
|---|---|---|---|
| POST | `/api/auth/login` | 登录，返回令牌 | 否 |
| GET | `/api/auth/me` | 当前登录人信息 | 是 |

**没有 logout 接口。** 数据库令牌方案下 logout 很简单（删除令牌行），但：

> 真实的前端会在本地清令牌。服务端删不删都能达到"用户退出"的效果。
> **故意不做**，是因为它需要前端配合（清本地 + 调接口），而当前阶段没有前端。
> 等有前端了，在 R03 补一个 `POST /api/auth/logout` 删当前令牌即可——**表结构已经支持，不需要改表**。

登录请求与响应：

```
POST /api/auth/login
{ "username": "zhangsan", "password": "初始密码" }

200 OK
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "token": "8f3c1a2b...",        // 原始令牌，只在这里出现这一次
    "expiresIn": 7200,             // 秒
    "person": {
      "id": 1, "personNo": "E001", "personName": "张三",
      "phone": "138****8000", "email": null, "status": 1
    }
  }
}
```

> R03 会在这个响应里**追加** `roles` 和 `appointments` 两个字段。现在不用留空位，加了不算破坏性变更。

#### 人员管理

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/system/persons` | 分页列表，支持 `keyword`（工号/姓名/手机号模糊）、`status` |
| GET | `/api/system/persons/{id}` | 详情 |
| POST | `/api/system/persons` | 新增（**必须同时带账号信息**） |
| PUT | `/api/system/persons/{id}` | 修改（不含工号、用户名） |
| PUT | `/api/system/persons/{id}/status` | 离职 / 复职 |

**没有 DELETE。** 见 §2.1。

#### 账号管理

| 方法 | 路径 | 用途 |
|---|---|---|
| PUT | `/api/system/accounts/{id}/password/reset` | 管理员重置密码 |
| PUT | `/api/system/accounts/{id}/status` | 停用 / 启用账号 |

**用户名不允许修改**，所以没有对应接口。理由：用户名是登录凭据，改了以后当事人不知道，而且它是**对外身份标识**（出现在日志、审计、对接系统里）。要改只能新开账号。

#### 分页对象

```
common/result/PageQuery.java     record PageQuery(int pageNum, int pageSize, String sortField)
common/result/PageResult.java    record PageResult<T>(int pageNum, int pageSize, long total, int totalPages, List<T> records)
```

- `pageNum` 从 1 开始；`pageNum < 1` 兜底为 1
- `pageSize < 1` 兜底为 10；`pageSize > 200` 截断为 200（**防止一次拉全表**）
- `PageResult.of(query, total, records)` 算出 `totalPages`

**分页参数非法不要抛异常**——它们来自前端 URL，抛异常就是 500。静默兜底。

分页查询要两条 SQL：一条 `COUNT(*)`，一条带 `LIMIT #{offset}, #{pageSize}` 的查询。

> 不引入 PageHelper。它靠拦截器改写 SQL，出了问题很难排查；你自己写两条 SQL，`LIMIT` 怎么算的全在眼前。

#### Service 契约

```
// person
PageResult<PersonVO> page(PersonQuery query)
PersonVO            getById(Long id)
PersonVO            create(PersonCreateRequest request)   // 事务：插人员 + 插账号
PersonVO            update(Long id, PersonUpdateRequest request)
void                changeStatus(Long id, Integer status) // 事务：改人员 + 停用账号 + 删令牌

// account
void resetPassword(Long accountId, String newPassword)
void changeStatus(Long accountId, Integer status)         // 停用时删令牌

// auth
LoginResponse login(LoginRequest request)
```

**`/api/auth/me` 不调 Service。** 拦截器已经把当前登录人放进 `CurrentUserContext` 了，Controller 直接 `CurrentUserContext.get()` 返回即可——**再查一次数据库是多余的**。

**查询对象怎么带分页参数**：`PageQuery` 是 record，不能被继承，所以 `PersonQuery` 自己带上分页字段，内部再转成 `PageQuery`：

```
record PersonQuery(String keyword, Integer status, int pageNum, int pageSize) {
    PageQuery paging() { return new PageQuery(pageNum, pageSize, null); }
}
```

`PageResult.of(query.paging(), total, records)` 组装返回。Mapper 的 `selectPage` 直接用 `#{offset}` 和 `#{pageSize}`，其中 `offset` 由 `paging().offset()` 算好后作为参数传入（**MyBatis 的 `#{}` 不会替你算 `offset`**）。

### 2.4 本需求要回头改动 R01 的三个地方

这是增量开发的正常现象——**但改动必须是"加东西"，不是"改设计"**。如果某份新需求要求你把旧表推倒重来，说明前面的设计错了。

| 类 | 改动 | 为什么 |
|---|---|---|
| `BizException` | 增加一个 `httpStatus` 字段（默认 400），加对应的构造器 | A6/A7 要求登录失败返回 **HTTP 401**，而 R01 的处理器把所有业务异常都映射成 400 |
| `GlobalExceptionHandler` | 处理 `BizException` 时用 `ex.getHttpStatus()` 决定状态码 | 同上 |
| `GlobalExceptionHandler` | `DuplicateKeyException` 的约束名映射表加上 `uk_sys_person_no`、`uk_sys_person_phone`、`uk_sys_account_username` | A1/A2/A3 |

`BizException` 里存 `int httpStatus` 而不是 Spring 的 `HttpStatus` 枚举——**`common` 包不应该依赖web框架**。将来拆模块时，`oa-common` 要保持零框架依赖。

### 2.5 业务规则（逐条编号）

错误码：**1100 段给人员与账号**，避免和 R01 的 1001~1010 混在一起。

| 码 | 含义 | HTTP |
|---|---|---|
| 1101 | 人员不存在 | 400 |
| 1102 | 工号已存在 | 400 |
| 1103 | 手机号已存在 | 400 |
| 1104 | 用户名已存在 | 400 |
| 1105 | 账号不存在 | 400 |
| 1106 | 用户名或密码错误 | **401** |
| 1107 | 账号已停用 | **401** |
| 1108 | 人员已离职 | 400 |
| 401 | 未登录 / 令牌无效或已过期 | **401** |

---

**A1｜工号唯一**（1102）

**A2｜手机号唯一**（1103）

**A3｜用户名唯一**（1104）

以上三条都要靠**数据库唯一键兜底**（理由同 R01 R1）。并发时抛 `DuplicateKeyException`，按约束名翻译成对应业务码——**R01 的全局异常处理已经做了这件事，这次要把 `sys_person` / `sys_account` 的约束名加进映射表**。

---

**A4｜新增人员必须同时开通账号**

`PersonCreateRequest` 里带 `username` + `initPassword`。人员表和账号表在**同一个事务**里插入，任何一个失败都回滚。

> **为什么不做成两步（先建人、再开通账号）？**
> 中间态没有意义——OA 里不会存在"有人员档案但没账号"的正常员工。
> 更重要的是：两步操作会产生**孤儿人员**（建了人，开通账号失败了），而一人一号的唯一键会让这个孤儿永远开不了账号。

---

**A5｜密码必须哈希存储**

- 用 **BCrypt**（`BCryptPasswordEncoder`，来自 `spring-security-crypto` 这一个 jar，**不需要引入整个 Spring Security 框架**）
- 绝不用 MD5 / SHA-1 / SHA-256 存密码

**为什么不能用 SHA-256 存密码？** 因为**快**。一张显卡每秒能算几十亿次 SHA-256，8 位密码几小时就跑完了。BCrypt 故意设计得慢（每次约 100ms），还能调难度；它自带随机盐，同一个密码每次哈希结果都不同——彩虹表直接失效。

> 如果依赖解析有问题，JDK 自带 PBKDF2（`SecretKeyFactory` + `PBKDF2WithHmacSHA256`，迭代 10 万次以上）也是合格方案，零依赖。
> **两条路都行，唯独不能存明文、不能存 MD5。**

- 验证密码用 `matches(原始密码, 哈希)`，**不要自己写字符串比较**
- 日志里**永远不要打印密码字段**（包括 `LoginRequest` 的 toString）

---

**A6｜登录失败不能暴露"用户是否存在"**

用户名不存在 → 1106「用户名或密码错误」
密码错误 → 1106「用户名或密码错误」（**同一个码、同一句提示**）

否则攻击者可以拿一份用户名字典，逐个试出哪些账号真实存在，然后再针对性地爆破密码。

---

**A7｜账号停用的提示，必须在密码验证通过之后**

顺序很重要：

```
1. 按用户名查账号 → 查不到 → 1106「用户名或密码错误」
2. 校验密码      → 不匹配 → 1106「用户名或密码错误」
3. 到这里说明密码是对的，才检查账号状态 → 停用 → 1107「账号已停用，请联系管理员」
```

如果把第 3 步提到前面，就等于告诉任何一个人"这个用户名存在且被停用了"——又回到了 A6 要防的信息泄露。

**这条同时也是对用户的尊重**：密码打错了提示"账号已停用"会让人困惑。

---

**A8｜登录成功要更新 `last_login_time`**

用于排查"这个账号是不是异常时间登录的"。**注意**：这是个写操作，要和查询分开，别让只读的登录校验把事务搞脏。

---

**A9｜令牌的有效期与内容**

- 有效期 **2 小时**（`expiresIn` 返回秒数）
- 令牌 = **32 字节安全随机数**的 Base64URL 编码（用 `SecureRandom`，**不要用 `UUID.randomUUID()`**——UUID v4 只有 122 位随机性，且部分实现可预测）
- 数据库只存 `SHA-256(令牌)` 的十六进制

**为什么不用 UUID？** 生成 100 万个 UUID，理论上会有重复（虽然概率极低）；更重要的是 UUID 的设计目标是"唯一"，不是"不可猜测"。生成会话令牌要用密码学安全的随机源。

---

**A10｜令牌校验的完整流程**

每个受保护请求：

```
1. 从请求头 Authorization: Bearer <token> 取令牌   → 没有 → 401
2. SHA-256 令牌，按 token_hash 查 sys_token        → 查不到 → 401
3. 检查 expire_time                                 → 已过期 → 401（并删掉这行）
4. 按 person_id 查人员和账号
5. 人员 status=0（离职）→ 401
   账号 status=0（停用）→ 401
6. 把当前登录人放进 CurrentUserContext
```

第 5 步是**双保险**：正常情况下离职/停用会主动删令牌（A11），但万一漏删了（比如有人直接改数据库），这一步兜住。**安全校验不能只依赖"上游会做对"。**

---

**A11｜离职 / 停用账号时，必须删除该人的所有令牌**

这是本需求最核心的一条。三个触发点：

| 触发 | 动作 |
|---|---|
| 人员置为离职 | 停用账号 + **删除该人全部令牌** |
| 账号停用 | **删除该人全部令牌** |
| 管理员重置密码 | **删除该人全部令牌**（密码改了，旧会话必须失效） |

三个动作都要在**同一个事务**里。漏了删令牌，就会出现"人已经离职了但还能继续操作"——这是 R02 里最严重的一类 bug，而且**很难被发现**，因为你测的时候是用新令牌测的。

**验收方法**：登录拿到令牌 → 把该人置为离职 → **用同一个令牌**再调接口 → 必须 401。

---

**A12｜修改人员不允许改工号**

工号是人员的外部标识（出现在考勤机、工资表、对接系统里）。允许改会造成对不上的问题。`PersonUpdateRequest` 里**根本不要有这个字段**——从入参上堵死，比在 Service 里判断更可靠。

---

**A13｜离职人员不能被修改、不能被重置密码**

人员 `status=0` 时，修改接口、重置密码接口、停用账号接口全部拒绝（1108）。

> 例外：**允许把离职人员改回在职**（复职）。所以 `changeStatus` 不受 A13 限制。

---

**A14｜不能把最后一个管理员停用**

本需求还没有角色，所以无法判断谁是管理员。**记为 R03 的待办**：`sys_role` 建好后，要加"系统性保护"，防止把唯一的超管停用导致没人能管理系统。

现在不实现，但**写进 §2.6**，别忘了。

### 2.6 本需求明确不做的事

- **不做任职、角色、数据权限** —— R03。`sys_person` 上**不加** `org_id`，见 §2.1
- **不做"有在职人员不能删部门"** —— 人员还没挂到组织上（那是任职表的事），R03 做完再加回 R01 的这条规则
- **不做 refresh token / 令牌自动续期** —— 过期就重新登录。续期机制只有在真的嫌烦时才加
- **不做登录失败次数锁定** —— R03 或安全加固需求。现在只记录 `last_login_time`
- **不做验证码**
- **不做修改密码（本人改自己的）** —— 只有管理员重置。本人改密需要一个"旧密码校验"的接口，等有前端页面时一起做
- **不做首次登录强制改密** —— 需要在 `sys_account` 加一个 `password_changed` 标记，且要有前端配合，放到安全加固
- **不做操作日志** —— 谁改了谁，由审计需求统一处理
- **不做单点登录、第三方免登** —— R06 移动平台集成

### Step 1：三张表

**产物**：`V2__init_person_account_token.sql`

**建完必须手工验证唯一键**：

```sql
-- 这两条应该成功
INSERT INTO sys_person (person_no, person_name, phone, hire_date) VALUES ('E001', '张三', '13800000001', '2024-01-01');
INSERT INTO sys_account (person_id, username, password) VALUES (1, 'zhangsan', 'placeholder');

-- 这三条必须全部失败
INSERT INTO sys_person (person_no, person_name, phone, hire_date) VALUES ('E001', '李四', '13800000002', '2024-01-01'); -- 工号重复
```

**第三条是最容易做错的**（`sys_account.person_id` 上的唯一键）。这条不过，一人一号就是空话。

**顺便**：把 `sys_person`、`sys_account` 的唯一约束名登记进 R01 里写的 `DuplicateKeyException` 翻译映射表。

### Step 3：人员档案 CRUD

**目标**：人员的增删改查（无删除）+ 分页列表可用。

**产物**：`system/person/` 下全套 + `SysPersonMapper`

**Mapper 契约**

```
int            insert(SysPerson person)
int            updateById(SysPerson person)
int            updateStatus(Long id, Integer status)
SysPerson      selectById(Long id)
SysPerson      selectByPersonNo(String personNo)
SysPerson      selectByPhone(String phone)
List<SysPerson> selectPage(PersonQuery query)     // 带 LIMIT
long           countByQuery(PersonQuery query)    // 不带 LIMIT
```

**`selectPage` 和 `countByQuery` 的 WHERE 条件必须完全一致**，否则会出现"列表显示 15 条但总数说 100 条"这种灵异现象。

> 想避免重复？把 WHERE 片段抽成一个 `<sql>` 片段引用。**用注解 SQL 做不到**，所以这个 Mapper 用 XML 写（`resources/mapper/SysPersonMapper.xml`）——这是你第一次需要 XML，理由是真实的。

**动态条件**：`keyword` 为空时不加条件，非空时模糊匹配工号/姓名/手机号。用 `<if test="keyword != null and keyword != ''">`。

> ⚠️ **模糊查询要转义 `%` 和 `_`**。用户在搜索框里输入 `%`，不加处理会匹配所有记录。用 `CONCAT('%', #{keyword}, '%')` 传参本身是安全的（防注入），但通配符语义还在——如果介意，把输入的 `%` 替换成 `\%`。

**`PersonVO` 里不要有密码字段**。这不是"记得别加"，而是——`PersonVO` 和 `AccountVO` 是**两个不同的类**，物理上就不可能串。

**完成的标志**：建 3 个人，翻页查询总数正确，按姓名搜"张"能搜到。

### Step 4：账号与状态联动

**目标**：密码哈希、账号开通、重置密码、停用启用、**删令牌**。

**产物**：`PasswordEncoder`、`system/account/` 全套、`SysTokenMapper`

**实现顺序**

1. `PasswordEncoder`（封装 BCrypt 的 `encode` / `matches`）+ 单测
2. `SysAccountService.create` —— 在 `SysPersonService.create` 的同一个事务里调用
3. `resetPassword` —— 改哈希 + **删该人全部令牌**
4. `changeStatus` —— 改状态 + **删该人全部令牌**
5. `SysPersonService.changeStatus` —— 改人员状态 + 停用账号 + **删令牌**

**`PasswordEncoder` 的单测必须包含这两条**：

- `matches(原文, encode(原文))` 为 true
- `encode(同一个原文)` 两次，**结果不相同**（证明盐是随机的），但两次 `matches` 都为 true

**第二个断言是重点。** 如果两次结果相同，说明你用的不是 BCrypt 而是某种固定盐的哈希——那彩虹表就能用。

**一个必须理解的点**：`@Transactional` 加在 Service 的公开方法上。上面三个动作里，删令牌是 `SysTokenMapper.deleteByPersonId(personId)`，它必须在和主操作同一个事务里。如果你把它挪到另一个 `@Transactional` 方法里并且是**同类内部调用**，事务不会生效（Spring AOP 代理机制）——这是 R01 提过的坑，这里第一次真的会踩到。

**完成的标志**

```bash
# 数据库里看到的密码是一串 $2a$10$... 的乱码
docker exec mysql mysql -uroot -p123456 oa -e "SELECT id, username, password FROM sys_account;"
```

### Step 5：登录接口

**目标**：`POST /api/auth/login` 能签发令牌。

**产物**：`system/auth/` 全套

**实现顺序**

1. `SysTokenMapper`：`insert` / `selectByHash` / `deleteByPersonId` / `deleteByHash` / `deleteExpired`
2. 令牌生成工具：`SecureRandom` 32 字节 → Base64URL；`SHA-256` 工具类
3. `AuthService.login`：按 §2.5 A6 → A7 → A8 → A9 的顺序实现
4. `AuthController.login`

**这一段的顺序不能乱**。A6/A7 讲的就是顺序——先验密码，再报停用。

**容易写错的地方**

- 令牌生成用 `SecureRandom`，**不是** `UUID.randomUUID()`，也不是 `new Random()`
- SHA-256 的输出是 `byte[]`，转十六进制时注意补零：`String.format("%02x", b)`，漏了 `%02x` 的 `0` 会出现长度不一致的哈希
- `expiresIn` 返回的是**秒**，不是毫秒
- 登录接口本身要放行（不加拦截），否则死锁

**完成的标志**

```bash
curl -X POST http://127.0.0.1:8090/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"初始密码"}'
# 返回里能看到 token

# 密码错误：401 + code 1106，且提示是"用户名或密码错误"
curl -X POST http://127.0.0.1:8090/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"zhangsan","password":"错的"}'

# 不存在的用户名：必须返回和上面【完全相同】的错误
curl -X POST http://127.0.0.1:8090/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"nobody","password":"错的"}'
```

**最后两条的响应必须一模一样。** 差异（包括响应耗时差异过大）都会泄露用户是否存在。

### Step 6：令牌过滤器与当前用户上下文

**目标**：受保护接口能识别出当前登录人。

**产物**：`AuthInterceptor`、`CurrentUser`、`CurrentUserContext`

**实现顺序**

1. `CurrentUser` 值对象（personId、personNo、personName）
2. `CurrentUserContext`：ThreadLocal 的 `set` / `get` / `clear`
3. `AuthInterceptor`：按 §2.5 A10 的 6 步实现
4. 注册拦截器 + 配置白名单

**白名单**

```
/api/auth/login
/actuator/**
/v3/api-docs/**
/swagger-ui/**
/error
```

**三个必须踩对的点**

1. **拦截器的 `afterCompletion` 里必须 `CurrentUserContext.clear()`。**
   Tomcat 复用线程，不清就会串号——A 用户的请求结束后线程被 B 用户的请求复用，`get()` 拿到的还是 A。
   这和 R01 里 traceId 用 MDC 的坑**是同一个坑**，换了个容器而已。

2. **返回 401 要用统一返回体的格式**，不能直接 `response.sendError(401)`——那样返回的是 Tomcat 的 HTML 错误页，前端解析不了。

3. **白名单用 `excludePathPatterns`，别用 `if (uri.startsWith(...))` 手写判断。** 手写的路径匹配迟早会漏（比如 `/api/auth/login/` 带斜杠、大小写、URL 编码绕过）。

**安全上必须测的一条**：

```
GET /api/system/persons/../auth/login
GET /api/system/persons%2F..%2Fauth%2Flogin
```

如果这些能绕过鉴权，说明路径匹配写错了。**这是真实的鉴权绕过漏洞，不是理论风险。**

**完成的标志**

```bash
# 不带令牌 → 401
curl -s -w "\nHTTP=%{http_code}\n" http://127.0.0.1:8090/api/system/persons

# 带令牌 → 200
TOKEN=$(curl -s -X POST http://127.0.0.1:8090/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"初始密码"}' | grep -o '"token":"[^"]*"' | cut -d'"' -f4)

curl -s -w "\nHTTP=%{http_code}\n" http://127.0.0.1:8090/api/system/persons \
  -H "Authorization: Bearer $TOKEN"

# 当前登录人
curl -s http://127.0.0.1:8090/api/auth/me -H "Authorization: Bearer $TOKEN"
```

### Step 7：端到端验收

把 §1.3 逐条走一遍。**重点验证 A11（下线）**——这条是 R02 的核心：

```bash
# 1. 登录拿令牌
TOKEN=$(curl -s -X POST http://127.0.0.1:8090/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"初始密码"}' | grep -o '"token":"[^"]*"' | cut -d'"' -f4)

# 2. 带着它访问，应该 200
curl -s -o /dev/null -w "before=%{http_code}\n" \
  http://127.0.0.1:8090/api/system/persons -H "Authorization: Bearer $TOKEN"

# 3. 把这个人置为离职（用另一个管理员的令牌，或者直接改数据库）
docker exec mysql mysql -uroot -p123456 oa \
  -e "UPDATE sys_person SET status=0 WHERE id=1;"

# 4. 用【同一个令牌】再访问
curl -s -o /dev/null -w "after=%{http_code}\n" \
  http://127.0.0.1:8090/api/system/persons -H "Authorization: Bearer $TOKEN"
```

**期望：`before=200`，`after=401`。**

如果 `after` 还是 200，说明 A10 第 5 步（双保险校验）或者 A11（删令牌）没做对。

**注意第 3 步是直接改数据库**，绕过了你的 `changeStatus` 接口——这正是要测的：**即使有人直接改库，令牌也必须失效。** 这验证的是 A10 的第 5 步，不是 A11。

然后再用接口正常走一遍离职流程，验证 A11（令牌行真的被删了）：

```bash
docker exec mysql mysql -uroot -p123456 oa \
  -e "SELECT COUNT(*) FROM sys_token WHERE person_id=1;"   # 应该是 0
```
