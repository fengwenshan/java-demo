# R04 数据权限落地

> **前置**：[R00 组织与权限模型](R00-组织与权限模型.md)（**§4.3 是本文档的核心，必须吃透**）、[R01](R01-部门管理.md)、[R02](R02-人员与账号.md)、[R03](R03-任职与角色.md)。

---

## 0. 为什么第四个需求是它

R03 把 `data_scope` 存进了数据库，但**它至今只是一个字符串**。一个"研发部主管"打开部门列表，看到的仍然是全公司的部门。

R04 把它变成真的：**同一次查询，不同的人看到不同的行。**

这是整个 OA 里**技术难度最高、出错代价最大**的一份。前面写错了，功能不对，用户会来报 bug。R04 写错了，是**数据泄露**——用户不会来报 bug，因为他不觉得自己看到了不该看的东西。

所以这份文档比前面几份都更强调"**默认应该是什么**"。

---

## 1. 业务需求

### 1.1 业务背景

R03 之后，系统已经知道张三有三段任职：

```
1) 技术中心（公司）        × 财务经理   × 本节点及以下
2) 华东分公司/研发部       × 研发部主管 × 本节点及以下
3) 技术中心/研发部/前端组  × 组员       × 仅自己
```

但打开部门列表，他看到的还是**全部**部门——包括他无权查看的那些。

### 1.2 需求描述

1. 部门的树形列表，只展示调用者有权查看的节点
2. 人员列表，只展示调用者有权查看的人员
3. 详情接口（按 id 查）同样要拦——**不能通过直接猜 id 绕过列表**
4. 分页的总数也必须是过滤后的数字
5. **多段任职取并集**：上面张三应该同时看到「技术中心下属」和「华东分公司/研发部」两块
6. `ALL` 范围和超级管理员不受限
7. **没有任何有效任职的人，看到零条数据**（不是看到全部）

### 1.3 验收标准

用 §1.1 的张三做基准，各部门 id 假设为：

```
1  技术中心（公司）
 ├─ 2  研发部
 │   ├─ 5  前端组
 │   └─ 6  后端组
 └─ 3  测试部
10 华东分公司（公司）
 └─ 11 研发部
99 别的公司
```

- [ ] 张三查部门树 → 看到 **1、2、5、6、11** 及它们的层级关系
- [ ] 张三查部门树 → **看不到 3（测试部）和 99（别的公司）**
- [ ] 张三查人员列表 → 看到任职在 1/2/5/6/11 的人，**加上张三自己**
- [ ] 张三查人员列表 → **看不到**任职在 3 或 99 的人
- [ ] 张三直接 `GET /api/system/persons/{无权查看的人的id}` → **拒绝，不是返回数据**
- [ ] 张三查人员列表的总数 = 过滤后的真实条数
- [ ] 换成**没有任何任职**的账号 → 部门树返回 `[]`，人员列表返回 0 条
- [ ] 换成有 `ALL` 范围的角色 → 全部可见
- [ ] 上面每一条都有自动化测试

## 2. 需求解构

### 2.1 核心难点：条件不在同一列上

R00 §4.3 说过，这里必须再强调一次——**这是整份需求里最容易写错的地方**。

张三三段任职产生的条件：

| 任职 | 范围 | 生成的条件 | 作用在哪个列 |
|---|---|---|---|
| 财务经理 | `SUBTREE` | `org_id IN (1,2,3,5,6)` | `org_id` |
| 研发部主管 | `SUBTREE` | `org_id IN (11)` | `org_id` |
| 组员 | `SELF` | `create_by = 1001` | **`create_by`** |

**正确写法**：

```sql
WHERE ( org_id IN (1,2,3,5,6)
     OR org_id IN (11)
     OR create_by = 1001 )
```

**错误写法**（很多人会这么写）：

```sql
WHERE org_id IN (1,2,3,5,6,11) OR create_by = 1001   -- 把两个 SUBTREE 合并了，这个还好
WHERE org_id IN (1,2,3,5,6,11)                        -- 丢了 SELF
WHERE org_id IN (1,2,3,5,6,11) AND create_by = 1001   -- 变成"且"，范围反而更小
```

第一、三条是**语义错误**，第二条是**权限放大**。三种都不会报错，只会静默地给错数据。

**必须记住：每一段任职生成一个独立的条件，最后 OR 拼接。**

---

### 2.2 三种模式

同样是"数据权限"，作用在不同形态的表上时，条件长什么样是不一样的。给 `@DataScopeRequired` 声明用哪种模式：

#### 模式 A：`CREATOR` —— 业务单据

适用：请假单、报销单、考勤记录这类**有 `org_id` 和 `create_by` 的业务表**。

| 范围 | 条件 |
|---|---|
| `SELF` | `create_by = :me` |
| `NODE` | `org_id = :node` |
| `SUBTREE` | `org_id IN (:subtreeIds)` |
| `ALL` | 不产生条件 |

#### 模式 B：`ORG_TREE` —— 组织树本身

适用：`sys_dept`。它没有 `org_id` 列——**它自己就是组织**。

| 范围 | 条件 |
|---|---|
| `SELF` | 视为"我任职所在的节点"，即 `id = :node` |
| `NODE` | `id = :node` |
| `SUBTREE` | `id IN (:subtreeIds)` |
| `ALL` | 不产生条件 |

> **为什么 `SELF` 在这里等于 `NODE`？** 因为"我创建的部门"没有业务含义——部门是组织架构，不是谁创建的。
> 但用户总得能看到自己所在的部门（否则下拉框里连自己部门都没有）。所以 `SELF` 在这里解释为"我任职的节点"。
> **这个不等价必须写进注释**，否则下一个人看到会以为是 bug。

#### 模式 C：`SUBJECT` —— 通过任职归属的主体表

适用：`sys_person`。R02 刻意**没有**给它加 `org_id`（一个人能跨多个部门，单个 `org_id` 表达不了）。

一个人"属于"某个组织，是通过**任职记录**表达的。所以要用 `EXISTS` 子查询：

| 范围 | 条件 |
|---|---|
| `SELF` | `p.id = :me` |
| `NODE` | `EXISTS (SELECT 1 FROM sys_appointment a WHERE a.person_id = p.id AND a.org_id = :node AND a 有效)` |
| `SUBTREE` | 同上，把 `a.org_id = :node` 换成 `a.org_id IN (:subtreeIds)` |
| `ALL` | 不产生条件 |

> **`EXISTS` 里的任职也必须带"当前有效"条件**（R03 §2.1 的半开区间），否则一个去年离职的部门主管，今年还会出现在别人的可见列表里。

### 2.3 两个技术选型

#### 选型一：为什么不用 MyBatis 拦截器改写 SQL

主流做法是写一个 MyBatis `Interceptor`，在 SQL 执行前用 JSqlParser 解析并追加 `WHERE` 条件。**本系统不用。**

| | 拦截器 + JSqlParser | 显式 `<sql>` 片段（采纳） |
|---|---|---|
| 业务代码侵入 | 零，加个注解就行 | 每个查询方法要带上 `scope` 参数 |
| 出问题时 | **最终执行的 SQL 你看不见**，要开 debug 日志、或者反编译 | SQL 就在 XML 里，一眼能看到 |
| 依赖 | 多一个 SQL 解析器，且版本兼容是持续的坑 | 零 |
| 拼错 WHERE 位置 | `ORDER BY`、`LIMIT`、子查询里都会踩 | 不存在 |

**决定性理由是第二条。** 数据权限出问题的时候，你需要在几分钟内回答"这条查询到底加了什么条件"。拦截器把答案藏在运行时，显式片段把答案写在代码里。

代价是"可能漏传参数"——这个问题用 §2.6 的 C12 结构性测试兜住。

#### 选型二：为什么给 `sys_dept` 加 `ancestors` 列

需求是"`SUBTREE` 要知道某节点的**所有后代 id**"。三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| `ancestors` 冗余列 | 存 `"0,1,2"` 这样的祖级路径，查子树用 `LIKE` | **每次移动节点都要递归更新整棵子树**；一旦失同步，权限静默出错 |
| 递归 CTE | `WITH RECURSIVE` 查子树 | 无 schema 变更，但 SQL 复杂度高，且每个条件一个 CTE |
| **Java 侧计算（采纳）** | 一次查全表，内存里算子树 id | 每个请求多一次全表查询（几百行） |

**采纳 Java 侧计算**，理由：

1. **组织表很小**——几百到几千行，全表查询是微秒级
2. **组织树很少变**——组织调整是低频事件，缓存价值不大
3. **`ancestors` 失同步的后果是权限错误且不报错**，这对权限系统是不可接受的失败模式
4. 逻辑全在 Java 里，**可以纯单元测试**，不需要连数据库

> 当组织节点达到几千个、或者组织调整极其频繁时，再换成递归 CTE（不需要改表），或者加 `ancestors`（需要改表 + 改 R01 的写路径）。
> **现在不做。**

### 2.4 树形数据的一个先天问题

部门树按数据权限过滤后，会出现**父节点不可见**的情况：

```
张三可见：1（技术中心）、2（研发部）、5（前端组）、6（后端组）、11（华东分公司/研发部）

问题：11 的父节点 10（华东分公司）不在可见集合里
```

如果直接用 SQL 过滤，返回的扁平结果里 11 的 `parent_id = 10` 指向一个不存在的节点——**组装树的时候它接不上去，会凭空消失**。

这不是小事：**用户会发现自己明明有华东分公司/研发部的任职，部门树里却看不到那个部门。**

两个解法：

| 解法 | 结果 | 问题 |
|---|---|---|
| 把不可见的祖先也查出来当"容器" | 树形完整 | 用户看到了无权查看的节点（哪怕只是当容器），且前端要区分"容器"和"可操作节点" |
| **裁剪后把父节点不可见的节点提升为根（采纳）** | 用户看到合法的森林 | 树的形状和完整视图不同（研发部变成了顶级） |

**采纳第二种**：不展示任何用户无权查看的节点。前端拿到的一定是一棵合法的森林，不需要处理"灰色容器"这种特殊状态。

实现上分两步，**不要试图在 SQL 里做**：

```
1. 按普通查询把完整部门列表查出来（不加数据权限条件）
2. 组装成完整的树
3. 递归裁剪：不可见的节点被"折叠"——它的可见子节点被提升到它的位置
```

**为什么连 SQL 条件都不加？** 因为组装树需要完整信息。给树形查询加 SQL 过滤，会同时得到"节点消失"和"数量对不上"两个问题。**组织表小，全量查出再裁剪是最简单也最不容易错的。**

> **注意**：这**不是**说树形数据可以不做权限。裁剪那一步就是权限，只是它发生在 Java 而不是 SQL。**权限做在 Java 里比做在 SQL 里更容易写错**，因为 SQL 不给结果就是不给，Java 忘了写 `if` 就是全给。所以裁剪逻辑必须有测试。

### 2.5 分层与包结构

```
com.wenshan.oa
├── framework/
│   ├── security/
│   │   ├── CurrentUser.java            改：已含 appointments（R03）
│   │   └── ...
│   └── datascope/                      ← 新增
│       ├── DataScope.java              值对象：是否受限 + 条件列表
│       ├── ScopeCondition.java         单段任职产生的条件
│       ├── DataScopeMode.java          枚举：CREATOR / ORG_TREE / SUBJECT
│       ├── DataScopeHelper.java        由 CurrentUser 构建 DataScope
│       ├── DataScopeRequired.java      注解 @DataScopeRequired
│       └── OrgTreeProvider.java        接口：算子树 id（依赖倒置）
└── system/
    ├── dept/
    │   ├── service/impl/DeptOrgTreeProvider.java   实现 OrgTreeProvider
    │   └── ...（树裁剪逻辑写在 Service 层）
    └── person/
        └── ...（列表查询带上 DataScope）
```

**`OrgTreeProvider` 是接口放在 `framework`，实现放在 `system.dept`。**

这是**依赖倒置**：`framework` 需要"算子树"的能力，但它不应该知道 `sys_dept` 这张表。所以定义一个接口，由业务模块实现。将来拆 Maven 模块时，`oa-framework` 不会依赖 `oa-system`。

**依赖方向必须是 `system.* → framework.*`，永远不能反过来。**

**关于 `@DataScopeRequired` 注解**：它标在 Mapper 方法上，但**不参与 SQL 生成**——条件不是靠反射或拦截器注入的，是 XML 里显式 `<include>` 的。

那它干嘛用？**两个用途**：

1. **文档**：打开 Mapper 就知道哪些查询受数据权限约束，不用读 XML
2. **测试**：C12 的覆盖率测试靠它来发现"标了数据权限但参数里没带 `scope`"的方法

> 换句话说，这个注解是**给人看和给测试看的**，不是给框架看的。运行时它什么也不做。
> 明确这一点很重要——否则下一个人会以为"标了注解就自动过滤了"，然后写出一个漏了 `<include>` 的查询。

### 2.6 接口契约与核心类

#### `DataScope` 值对象

```
DataScope
├── Long personId                  当前登录人
├── boolean restricted             是否受限。false = 不加任何条件
└── List<ScopeCondition> conditions 每段有效任职产生一个
```

```
ScopeCondition
├── List<Long> orgIds              可见的组织节点 id；selfOnly 为 true 时无意义
└── boolean selfOnly               true = "只看和我个人相关的数据"
```

**每个 `ScopeCondition` 二选一**：要么是一组 `orgIds`，要么是 `selfOnly`。因为每段任职只有一个 `data_scope`。

#### `DataScopeHelper` 契约

```
// 从 CurrentUserContext 构建当前请求的数据范围
static DataScope current()

// 由一组任职构建（供测试直接调用，不依赖 Web 上下文）
static DataScope from(List<AppointmentScope> appointments)
```

`AppointmentScope` 是构建 `DataScope` 需要的输入：`orgId` + `dataScope` + 是否已停用角色。

#### `OrgTreeProvider` 契约

```
Set<Long> selfAndDescendants(Long orgId);   // 含自己
```

#### Mapper 参数约定

所有需要数据权限的查询参数对象，**必须有一个 `DataScope scope` 字段**。

部门树不走 SQL 权限（§2.4），所以它的查询不需要；人员列表需要。

#### 共享 SQL 片段

```
resources/mapper/fragments/DataScope.xml

<sql id="orgScope">      模式 A / B：作用在 ${orgColumn} 上
<sql id="subjectScope">  模式 C：作用在 EXISTS 子查询上
```

> `${orgColumn}` 里用 `${}` 是**安全的**——它的值来自 XML 里的字面量（`<property name="orgColumn" value="p.id"/>`），不是用户输入。
> **但条件里的每一个值都必须用 `#{}`。** 见 C9。

### 2.7 业务规则

**本需求不新增业务错误码**（数据权限是过滤，不是校验——被过滤掉的数据表现为"不存在"，详情接口返回 1001 人员不存在）。

---

**C1｜并集：每段有效任职生成一个独立条件，最后 OR 拼接**

见 §2.1。

---

**C2｜每段任职只看它自己的 `data_scope`，不能"提级"**

张三有 `SUBTREE`（技术中心）和 `SELF`（前端组）两段。**不能因为"他有 SUBTREE"就把 `SELF` 那段也当成 `SUBTREE`**，也不能反过来把整体降级成 `SELF`。

R00 §4.3 已经说过：**并集只在同一隔离域内生效，不破坏单段任职的边界。**

---

**C3｜有 `ALL` 范围的任职，或持有 `SUPER_ADMIN` 有效任职 → `restricted = false`**

此时**不产生任何条件**，也不应该生成 `1=1` 这种"看起来像条件"的东西——直接跳过 `<if>`。

---

**C4｜★ 条件列表为空时，必须生成恒假条件，绝不能"没有条件就不过滤"**

**这是整份需求里最危险的一条。**

一个没有任何有效任职的用户，`conditions` 是空列表。此时：

```xml
<!-- 错误写法：空列表 → 什么条件都没加 → 用户看到全部数据 -->
<if test="scope != null">
  AND (<foreach collection="scope.conditions" ...>)  <!-- 空 foreach 产生空串 -->
</if>
```

`<foreach>` 对空集合产生**空字符串**，于是 `AND ()` 要么语法错误，要么在某些写法下直接被 `<if>` 跳过——**结果就是完全不过滤**。

**正确做法**：

```xml
<if test="scope != null and scope.restricted">
  AND (
  <choose>
    <when test="scope.conditions.isEmpty()">
      1 = 0
    </when>
    <otherwise>
      <foreach collection="scope.conditions" item="c" separator=" OR "> ... </foreach>
    </otherwise>
  </choose>
  )
</if>
```

**"没有权限"的默认结果必须是"什么都看不到"，不是"什么都看得到"。** 所有权限系统的失败模式都必须是"拒绝"，不能是"放行"。

这一条**必须有专门的测试**：造一个没有任何任职的用户，断言列表返回 0 条、树返回 `[]`。

---

**C5｜COUNT 查询必须和列表查询用完全相同的条件**

否则总数会泄露"你看不到的还有多少条"。更糟的是分页算错——前端算出来 3 页，点第 2 页是空的。

把条件抽成共享 `<sql>` 片段，`selectPage` 和 `countByQuery` 都 `<include>` 同一个片段。**这是用 `<sql>` 片段而不是复制粘贴的决定性理由。**

---

**C6｜详情查询也必须带条件**

`GET /api/system/persons/{id}` 如果不带条件，攻击者可以**从 1 开始遍历 id**，把看不到的数据一条条捞出来。

被过滤掉的数据，详情接口应该返回 **1001 人员不存在**——**不要返回 403**。返回 403 等于确认"这条数据存在，只是你没权限"，那本身就是信息泄露。

---

**C7｜停用角色的任职不参与条件生成**

R03 的 B9：角色停用后不再授予权限。数据范围也属于权限，同样规则。

---

**C8｜已结束 / 未生效的任职不参与条件生成**

严格用 R03 §2.1 的半开区间：

```
start_date <= CURDATE() AND (end_date IS NULL OR end_date > CURDATE())
```

> **这条和 R03 的规则是同一个，但实现位置不同。** R03 里它决定"返回哪些角色"，这里决定"哪些任职参与数据权限"。**两处必须用同一个判定方法**，不能各写一遍 SQL——迟早不一致。

---

**C9｜条件里的值一律用 `#{}`，禁止 `${}` 拼接**

```xml
<!-- 正确 -->
org_id IN <foreach collection="c.orgIds" item="oid" open="(" separator="," close=")">#{oid}</foreach>

<!-- 绝对禁止 -->
org_id IN (${c.orgIdsString})
```

用 `${}` 拼 id 列表看起来"安全"（因为 id 是 `Long`，来自数据库），但**这个理由会随着需求演变化掉**——哪天有人加了个"按名称过滤"顺手也用了 `${}`，注入就成了。

**唯一允许 `${}` 的地方是列名**，且值必须是 XML 里的字面量。

---

**C10｜树形数据用 Java 裁剪，不做 SQL 过滤**

见 §2.4。

---

**C11｜裁剪后，父节点不可见的节点提升为根**

裁剪必须是"折叠"而不是"剔除"：不可见节点的可见子节点要接上来，不能跟着父节点一起消失。

**裁剪逻辑必须单独写单元测试**（输入一棵树 + 可见集合，输出裁剪后的森林），因为这是纯函数，测试成本极低，而写错的后果是"数据凭空消失"——这种 bug 用户会以为系统坏了。

---

**C12｜结构性测试：标了 `@DataScopeRequired` 的查询方法，参数类型必须带 `scope` 字段**

和 R03 的注解覆盖率测试是同一个思路。漏传 `scope` = 那条查询完全不过滤。

测试写法：反射遍历所有标了 `@DataScopeRequired` 的 Mapper 方法，断言其参数类型（或参数类型之一）存在名为 `scope`、类型为 `DataScope` 的字段。

> 这条测试只能保证**参数传进来了**，不能保证 **XML 里真的 `<include>` 了片段**。
> 后者靠行为测试：用一个"只能看自己"的账号，断言列表里没有别人的数据。

---

**C13｜新业务表要参与数据权限，必须带 `org_id` 和 `create_by`**

从这份需求开始，**新建的业务表（请假单、报销单、考勤记录……）在设计时就加这两个列**：

| 列 | 类型 | 说明 |
|---|---|---|
| `org_id` | BIGINT UNSIGNED NOT NULL | 数据归属的组织节点，**写入时由 Service 从当前登录人的任职推导** |
| `create_by` | BIGINT UNSIGNED NOT NULL | 创建人 `person_id` |

**`org_id` 由谁决定？** 这是新需求里必须回答的问题。两种选择：

- 取当前登录人**任职的那个节点**（如果有多段任职，取哪一段？要用户选或者按业务规则定）
- 由用户在表单里**显式选择**（更灵活，但可能选到自己权限外的节点——**必须校验**）

**这份文档不定这个规则**——每种单据的归属逻辑不同。但**必须在对应的需求文档里明确回答**，不能默认"反正 Service 会填"。

---

### 2.8 本需求明确不做的事

- **不做 `ancestors` 列** —— 见 §2.3 选型二
- **不做 MyBatis 拦截器 / JSqlParser** —— 见 §2.3 选型一
- **不做数据权限的缓存** —— 理由同 R03：缓存失效写错的后果是权限不生效，是安全问题
- **不把数据权限推广到全部查询** —— 本需求只落地**部门树**和**人员列表**两个场景，把机制建对。其余表在各自的需求里接入
- **不做"按字段"的数据权限** —— 比如"能看这条数据但不能看它的金额字段"。那是列级权限，模型完全不同
- **不做导出/下载的数据权限** —— 导出走的是另一套查询，容易绕过权限。**记一个待办**：等有导出功能时，必须复用同一套 `DataScope`，不能另写
- **不做数据权限的变更审计** —— 归 R06

## 3. 实现步骤

### Step 1：`DataScope` 与条件生成（纯逻辑，不连库）

**目标**：给定一组任职，能算出正确的条件列表。

**产物**：`framework/datascope/DataScope.java`、`ScopeCondition.java`、`DataScopeMode.java`、`DataScopeHelper.java`

**先把数据结构的语义定死**：

```
DataScope
  personId    当前登录人
  restricted  true = 需要加条件
  conditions  OR 拼接的条件列表

ScopeCondition
  orgIds      可见节点 id 集合（selfOnly=true 时为空）
  selfOnly    true = 只看和我相关的
```

**这一步的所有测试都不需要数据库**，构造任职列表直接调 `DataScopeHelper.from(...)`。

**必须覆盖的用例**：

| 输入 | 期望 |
|---|---|
| 一段 `SUBTREE`（node=1） | `restricted=true`，1 个条件，`orgIds` 是 1 的子树 |
| 一段 `SELF` | `restricted=true`，1 个条件，`selfOnly=true` |
| `SUBTREE` + `SELF` | `restricted=true`，**2 个条件**（不能合并） |
| `SUBTREE` + `SUBTREE` | `restricted=true`，**2 个条件**（不能合并成一个 IN） |
| 一段 `ALL` | `restricted=false` |
| `ALL` + `SUBTREE` | `restricted=false`（ALL 短路） |
| 空列表 | `restricted=true`，**0 个条件**（配合 C4） |
| 停用角色的任职 | 被排除 |
| 已结束的任职 | 被排除 |

**最后两个用例要求这个方法能拿到"当前有效任职"**。为了让它可测，`from(...)` 接受的输入是**已经筛过的** `AppointmentScope` 列表，筛选 SQL 在 Service 层。

> **这个划分很重要**：`DataScopeHelper` 是纯函数（好测），"哪些任职有效"由 SQL 决定（靠集成测试）。
> 不要把两个职责混在一个方法里——那会导致所有数据权限的测试都要连数据库。

**完成的标志**：上面 9 个用例全绿，`mvn test` 跑完不到 2 秒。

---

### Step 2：子树计算

**目标**：`selfAndDescendants(orgId)` 能返回正确的节点集合。

**产物**：`framework/datascope/OrgTreeProvider.java`（接口）、`system/dept/service/impl/DeptOrgTreeProvider.java`（实现）

**实现思路**

```
1. 一次 selectAll() 拿到全部部门（只取 id 和 parent_id 就够）
2. 按 parentId 分组成 Map<Long, List<Long>>
3. 从 nodeId 开始 BFS/DFS，收集全部后代
4. 结果含自己
```

**必须覆盖的用例**

| 场景 | 期望 |
|---|---|
| 叶子节点 | 只返回自己 |
| 中间节点 | 自己 + 全部后代 |
| 根节点 | 整棵树 |
| **不存在的 nodeId** | 返回空集合（**不要抛异常**——数据可能被删了，抛异常会让整个请求 500） |
| **数据里有环**（脏数据） | **不死循环**。用访问标记 |

**第四条和第五条是重点。** 一个不存在或成环的节点会让权限计算整个崩掉——而崩掉的表现是接口 500，用户报障；如果是"死循环"，就是 CPU 打满。

**完成的标志**：5 个用例全绿。

### Step 3：部门树接入（Java 裁剪）

**目标**：部门树按调用者的可见范围裁剪。

**产物**：改 `SysDeptServiceImpl` 的 `tree()` 方法

**实现顺序**

1. 先写**纯函数** `List<DeptTreeNode> prune(List<DeptTreeNode> forest, Set<Long> visibleOrgIds)`
2. 给这个纯函数写单元测试（C11）
3. 在 `tree()` 里：查全量 → 组装完整森林 → `prune`

**`prune` 的语义（用测试钉死）**

```
输入树：            可见集合：{1, 2, 5, 11}
1 技术中心
├─ 2 研发部
│   ├─ 5 前端组
│   └─ 6 后端组       ← 不可见
└─ 3 测试部           ← 不可见
10 华东分公司         ← 不可见
└─ 11 研发部

期望输出：
1 技术中心
├─ 2 研发部
│   └─ 5 前端组
11 研发部             ← 父节点不可见，提升为根
```

**注意 6 被剔除后，5 仍然是 2 的子节点**（因为 2 可见）。只有**父节点不可见**时才提升。

**一个容易忽略的位置**：`visibleOrgIds` 是从哪来的？是 `DataScope.conditions` 里所有 `orgIds` 的并集。而 `SELF` 条件（`selfOnly=true`）**对部门树贡献的是"我任职所在的节点"**（§2.2 模式 B），所以在构建 `DataScope` 时要为 `ORG_TREE` 模式把 `SELF` 展开成对应的 `orgId`。

**实现建议**：`DataScopeHelper` 提供两个方法：

```
DataScope forSqlQuery()     // 模式 A / C：SELF 保持 selfOnly
DataScope forOrgTree()      // 模式 B：SELF 展开成 orgId
```

**不要**在一个方法里用 if 区分调用方——调用方自己说清楚要哪种。

**完成的标志**

```bash
# 用张三的令牌
curl -s "http://127.0.0.1:8090/api/system/depts/tree" \
  -H "Authorization: Bearer $ZHANGSAN_TOKEN" | python3 -m json.tool
# 顶层应该有 2 个根：1（技术中心）和 11（华东分公司/研发部）
```

### Step 4：人员列表接入（SQL 条件注入）

**目标**：人员分页列表按数据权限过滤。

**产物**：`resources/mapper/fragments/DataScope.xml`、改 `SysPersonMapper.xml`、改 `PersonQuery`

**实现顺序**

1. 写共享片段 `DataScope.xml`
2. `PersonQuery` 加 `DataScope scope` 字段
3. `SysPersonServiceImpl.page()` 里填 `scope = DataScopeHelper.forSqlQuery()`
4. XML 的 `selectPage` 和 `countByQuery` **都** `<include>` 同一个片段

**片段长什么样**（模式 C，`SUBJECT`）：

```xml
<sql id="subjectScope">
    <if test="scope != null and scope.restricted">
        AND (
        <choose>
            <when test="scope.conditions.isEmpty()">
                1 = 0
            </when>
            <otherwise>
                <foreach collection="scope.conditions" item="c" separator=" OR ">
                    <choose>
                        <when test="c.selfOnly">
                            p.id = #{scope.personId}
                        </when>
                        <otherwise>
                            EXISTS (
                                SELECT 1 FROM sys_appointment a
                                WHERE a.person_id = p.id
                                  AND a.org_id IN
                                  <foreach collection="c.orgIds" item="oid" open="(" separator="," close=")">#{oid}</foreach>
                                  AND a.start_date &lt;= CURDATE()
                                  AND (a.end_date IS NULL OR a.end_date &gt; CURDATE())
                            )
                        </otherwise>
                    </choose>
                </foreach>
            </otherwise>
        </choose>
        )
    </if>
</sql>
```

**注意三个细节**

1. **`&lt;` 和 `&gt;`** —— XML 里 `<` 必须转义，忘了就是解析报错
2. **`EXISTS` 里的有效性条件不能省** —— 见 §2.2 模式 C 的警告
3. **`1 = 0` 那个分支必须在**（C4）

**`c.orgIds` 为空会怎样？** 理论上不会——`SUBTREE` 至少含自己，`NODE` 是一个单元素集合。但**如果 `orgIds` 真的空了**（比如节点被删了，Step 2 返回空集合），`IN ()` 是 **SQL 语法错误**。

所以 `DataScopeHelper` 在构建时要做保护：**`orgIds` 为空的条件不要生成**。这样它对应的那段任职就不贡献任何可见范围——等价于"这段任职看不到东西"，语义正确。

**完成的标志**

```bash
# 张三应该看到任职在 1/2/5/6/11 的人 + 自己
curl -s "http://127.0.0.1:8090/api/system/persons?pageNum=1&pageSize=20" \
  -H "Authorization: Bearer $ZHANGSAN_TOKEN" | python3 -m json.tool
# data.total 必须等于列表实际能翻到的总条数
```

**并且手工改一下可见集合**（把张三的一段任职结束掉），确认总数跟着变——这验证 C5。

### Step 5：详情与 COUNT 补齐

**目标**：C5、C6 落地。

**产物**：改 `SysPersonServiceImpl.getById()`、`SysDeptServiceImpl.getById()`

**人员详情**：不用 `selectById(id)` 直接返回，而是用带数据权限的查询。

两种写法：

```
写法一：selectById 也带 scope 条件，查不到直接当"不存在"
```

**采纳写法一**：复用同一套 SQL 条件，不给"先查出来再判断"留出错的空间。**写法二的问题是 `getById` 和 `list` 用了两套判定逻辑，迟早不一致。**

### Step 7：端到端验收

按 §1.3 逐条走。**重点是"看不到"这一类断言**——前面几份需求的测试都是"能看到什么"，这份必须反过来测。

**准备数据**（用超管令牌建好 §1.3 的组织和人员）

**逐条验证**

```bash
# ① 张三看部门树
curl -s http://127.0.0.1:8090/api/system/depts/tree -H "Authorization: Bearer $ZS" | python3 -m json.tool
#    期望：能看到 1,2,5,6,11；看不到 3,99

# ② 张三看不到测试部
#    在返回的 JSON 里搜索 "测试部" → 必须搜不到

# ③ 张三看人员列表
curl -s "http://127.0.0.1:8090/api/system/persons?pageNum=1&pageSize=20" -H "Authorization: Bearer $ZS"
#    期望：只含任职在 {1,2,5,6,11} 的人 + 张三自己

# ④ 详情绕过
curl -s "http://127.0.0.1:8090/api/system/persons/{测试部某人}" -H "Authorization: Bearer $ZS"
#    期望：400 + code 1001

# ⑤ 无任职用户
curl -s http://127.0.0.1:8090/api/system/depts/tree -H "Authorization: Bearer $NOBODY"
#    期望：data = []      ← C4 的验收
curl -s "http://127.0.0.1:8090/api/system/persons" -H "Authorization: Bearer $NOBODY"
#    期望：data.total = 0  ← C4 的验收

# ⑥ 超管
#    期望：部门树含全部节点（包括 3 和 99）
```

**第 ⑤ 条必须真的测。** 这是权限系统里唯一一条"失败方向是泄露"的规则，而它恰恰是最容易被"没有条件就不过滤"这个直觉写错的。

**再加两条并集验证**（C1 的核心，这是最容易写错的地方）

**验证 1：两段 `SUBTREE` 必须"相加"**

| 张三的任职 | 部门树应看到 |
|---|---|
| 只有 技术中心(1) `SUBTREE` | 1, 2, 3, 5, 6 |
| 加一段 华东分公司/研发部(11) `SUBTREE` | 1, 2, 3, 5, 6, **11** |
| 再加一段 别的公司(99) `SUBTREE` | 1, 2, 3, 5, 6, 11, **99** |

**每加一段任职，可见范围只能变大，绝不能变小。** 这是判断实现对不对最简单的标准：

- 如果拼接写成了 `AND`（各条件之间用 `AND` 而不是 `OR`），加第二段任职后可见范围**变成空**
- 如果在循环里覆盖了变量（只保留了最后一段任职），加第二段后只剩 `11`

两种错误都很隐蔽——**只测"一段任职"的用例永远是过的**。所以必须测"加第二段之后"。

**验证 2：`SELF` 与 org 条件是 OR，不是 AND —— 这条在 R04 阶段测不到**

必须说清楚为什么：

- `SELF` 在 `ORG_TREE` 模式下被解释成"任职的节点"，不是 `create_by`
- `SELF` 在 `SUBJECT` 模式下是 `p.id = me`
- **`create_by` 那个分支（`CREATOR` 模式）当前没有任何表在用** —— `sys_dept` 和 `sys_person` 都不带 `create_by` 列

所以 `CREATOR` 模式的 SQL 片段会被写出来，**但在第一个业务单据表（请假单/报销单）落地之前，它没有集成测试。**

**这不是可以忽略的事**，处理方式：

1. `DataScopeHelper` 的条件生成逻辑（纯 Java）在 Step 1 就有完整单元测试，**覆盖 `CREATOR` 模式**
2. SQL 片段照写，XML 里加注释 `<!-- 待第一个业务表落地时补集成测试 -->`
3. **写进 §4 自测清单和 README 的待办**，第一个业务表的需求文档必须包含"端到端验证 `CREATOR` 模式"

**不要让没有测试的代码看起来像测过了。** 显式标注，比假装没问题安全得多——半年后你看到这段代码，至少知道该怀疑什么。

## 5. 完成后你会得到什么

**能力上**：你实现了一套**行级数据权限**。这是企业系统里最值钱也最容易出事的一块能力——它的失败模式是静默的，所以你必须学会的不是"怎么让它生效"，而是"**怎么保证它不失效**"：默认拒绝、结构性测试、失败方向永远是拒绝。

你还第一次处理了**树形数据 + 权限的冲突**（父节点不可见），这个坑在任何有层级的数据上都会重复出现（分类树、菜单树、BOM 结构）。

**下一步（R05 项目组与硬隔离）**：

R04 做完，数据权限是"**叠加**"的——你能看的 = 所有任职可见范围的并集。但项目组要的是**硬隔离**：

> 一个跨部门的临时项目组，它的资料**只有组员能看，公司总经理也不行**。

这直接和"并集"冲突。R05 要解决的就是：**哪些数据参与并集，哪些数据是被隔离域圈起来、不参与并集的。** R00 §4.3 结尾那句话（"并集只在同一隔离域内生效"）在那里才会真正落地。

**一个必须记住的待办**：导出/下载功能将来必须复用同一套 `DataScope`。**导出是最容易绕过数据权限的地方**——列表过滤了，导出功能另写一句 SQL 就把全部数据吐出去了。
