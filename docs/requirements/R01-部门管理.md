## 0. 为什么第一个需求是部门管理

不是因为它简单，是因为它是**后面所有需求的地基**：

- 审批流要判断"找谁审批"——按部门找主管
- 数据权限要判断"能看谁的数据"——按部门划分范围
- 考勤统计要按部门汇总
- 员工档案要挂在部门上

先做它，后面每加一个模块都是在它上面长东西。反过来，如果先做报销、请假，回头发现部门模型不对，所有已写的代码都要改。

它同时是**难度刚好**的第一个需求：表只有一张，但是非功能性的坑一个不少——树形结构、成环检测、同级重名、停用级联、并发插入。CRUD 谁都会写，把这些规则写对才是本事。

## 1. 业务需求

### 1.1 业务背景

公司的组织架构是分层的：「技术中心」下面有「研发部」「测试部」，「研发部」下面还可能有「前端组」「后端组」。

目前这套结构维护在 Excel 里，问题很明确：

- 每个系统各存一份，版本对不上
- 部门改名、拆分、合并之后，历史数据里的部门名还是旧的
- 新员工入职时，下拉框里的部门选项是手改的，经常写错（「研发部」写成「研发中心」）

### 1.2 需求描述

给 HR 和行政提供一个维护组织架构的功能：

1. 可以新建组织节点，并指定它的上级（不指定就是顶级）
2. 组织节点分三种类型：**公司**、**部门**、**小组**（见 R00 §2.1）
3. 可以修改名称、编码、负责人、上级
4. 可以给同级节点排序，决定下拉框和报表里的显示顺序
5. 可以停用节点——停用后不再出现在下拉选项里，但历史数据仍然能看到
6. 可以删除节点——但只能删除"干净的"节点
7. 要能按层级看到完整的组织架构树（多公司 → 是**多棵树**，不是一棵）

### 1.3 验收标准（给业务方看的，不是给你看的）

- [ ] 能在「技术中心」下新建「研发部」
- [ ] 能在「华东分公司」下也新建一个「研发部」——**两家公司可以有同名部门**
- [ ] 同一个上级下不能再建一个叫「研发部」的（提示"该上级下已存在同名部门"，**不是**报"系统错误"）
- [ ] 把「研发部」的上级改成「前端组」（它自己的下级）时被拒绝，并提示原因
- [ ] 在「小组」下面挂一个「部门」时被拒绝（层级类型不合法）
- [ ] 「技术中心」下面还有子部门时，删除它会被拒绝
- [ ] 停用一个还有启用子部门的部门时被拒绝
- [ ] 组织架构树能反映出正确的层级嵌套，且**多个公司是并列的多棵树**
- [ ] 上面每一条都有自动化测试

## 2. 需求解构

### 2.1 数据模型

一张表 `sys_dept`，**同时装公司、部门、小组三种节点**（理由见 R00 §2.1）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `parent_id` | BIGINT UNSIGNED NOT NULL DEFAULT 0 | 上级节点 ID，**0 表示顶级**（不用 NULL，比较时少一类分支） |
| `dept_type` | TINYINT NOT NULL | **1 公司 / 2 部门 / 3 小组**，决定层级校验规则与前端渲染 |
| `dept_name` | VARCHAR(50) NOT NULL | 节点名称 |
| `dept_code` | VARCHAR(50) NOT NULL | 节点编码，全局唯一，给外部系统对接用 |
| `leader` | VARCHAR(30) NULL | 负责人姓名（本需求只存名字，将来关联人员表） |
| `sort` | INT NOT NULL DEFAULT 0 | 同级排序，升序 |
| `status` | TINYINT NOT NULL DEFAULT 1 | 1 启用 / 0 停用 |
| `create_time` | DATETIME | 创建时间，数据库默认值 |
| `update_time` | DATETIME | 更新时间，数据库自动维护 |

**约束**

- 主键 `id`
- 唯一键 `uk_sys_dept_code (dept_code)`
- 唯一键 `uk_sys_dept_parent_name (parent_id, dept_name)`
- 普通索引 `idx_sys_dept_parent (parent_id)`

**`uk_sys_dept_parent_name` 的字段组合是关键。** 它约束的是"**同一个上级下**不能同名"，不是"同一层不能同名"。所以：
- 「技术中心/研发部」和「华东分公司/研发部」→ `parent_id` 不同 → **允许**（正确）
- 「技术中心/研发部」再来一个 → `parent_id` 相同 → **拒绝**（正确）

如果 R00 里没把公司建成树上的节点，这两家公司的 `parent_id` 都会是 0，第二个「研发部」会被这条唯一键直接拦掉——**多公司从根上就建不起来**。

**两个设计点，想清楚再动手：**

1. **为什么同级同名的唯一约束要建在数据库上，而不是只在代码里查一下？**
   代码里"先查再插"在并发下会漏——两个人同时提交，都查到"不存在"，然后都插进去。数据库唯一键是最后一道防线。
   代价是：并发插入会抛 `DuplicateKeyException`，你要在全局异常处理里把它翻译成业务错误（`code 1003`），否则用户看到的是 500。

2. **`dept_code` 不复用。** 部门删除后，它的编码不能再给别的部门用。这是有意的——历史上引用过这个编码的单据不能指向另一个部门。代价是编码会越来越长、越来越没规律，接受它。

**不用逻辑删除。** 本需求删除就是物理删除。
理由：逻辑删除是一个**全局性决策**——一旦引入，所有表的查询都要带 `deleted = 0`，漏一处就是数据泄露。它应该由《审计与运维底座》需求统一决策并统一实现，不该由部门管理这一个功能顺手引入。现在没有任何数据引用部门，物理删除是安全的。

### 2.2 分层与包结构

**先做单模块，不要建多模块。** 你现在的代码量撑不起 4 个 Maven 模块，模块边界带来了构建复杂度却没有任何收益。

但**包结构要按未来的模块边界来划分**，这样将来拆模块就是挪目录：

```
com.wenshan.oa
├── OaApplication.java                    启动类
├── common/                               → 未来拆成 oa-common
│   ├── result/Result.java                统一返回体
│   ├── result/ResultCode.java            标准错误码
│   └── exception/BizException.java       业务异常
├── framework/                            → 未来拆成 oa-framework
│   └── web/GlobalExceptionHandler.java   全局异常处理
└── system/                               → 未来拆成 oa-system
    └── dept/
        ├── controller/SysDeptController.java
        ├── service/SysDeptService.java            接口
        ├── service/impl/SysDeptServiceImpl.java   实现
        ├── mapper/SysDeptMapper.java
        ├── entity/SysDept.java                    对应数据库表
        └── dto/
            ├── DeptCreateRequest.java             新增入参
            ├── DeptUpdateRequest.java             修改入参
            ├── DeptVO.java                        对外返回
            └── DeptTreeNode.java                  树节点
```

**每个类的职责，越界就是设计错误：**

| 类 | 只做这些 | 绝不能做这些 |
|---|---|---|
| `Controller` | 接参数、调 Service、包 Result | 写业务判断、碰 Mapper |
| `Service` | 业务规则校验、编排、事务 | 拼 SQL、处理 HTTP |
| `Mapper` | 单表读写，一条 SQL 一件事 | 写业务判断 |
| `Entity` | 对应表结构 | 对外暴露（用 VO 隔开） |

**为什么 Entity 不直接返回给前端？** 因为表结构会变。将来 `sys_dept` 加一个内部用的 `tenant_id`，如果 Entity 直接当返回值，这个字段就泄露给前端了。VO 是"对外契约"，Entity 是"数据库映射"，两者生命周期不同。

### 2.3 接口契约

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/system/depts/tree` | 组织架构树，支持可选参数 `status` 过滤 |
| GET | `/api/system/depts/{id}` | 部门详情 |
| POST | `/api/system/depts` | 新增部门 |
| PUT | `/api/system/depts/{id}` | 修改部门 |
| DELETE | `/api/system/depts/{id}` | 删除部门 |
| PUT | `/api/system/depts/{id}/status` | 启用 / 停用 |

**为什么停用要单独一个接口，而不是塞进修改接口？**
因为它们的风险等级不同。修改接口要求前端把 `dept_name`、`dept_code`、`leader` 等字段全部回传，漏传一个就被覆盖成 null。停用只改一个字段，不存在误覆盖的可能。**能用窄接口就不要用宽接口。**

**统一返回体**（沿用你 04 模块里已经在用的结构）：

```
{ "code": 200, "message": "操作成功", "data": ... }
```

约定：标准错误 `code` 与 HTTP 状态码一致（400/403/404/500），业务错误从 **1000** 起编号。

**Service 的方法签名（契约，不是实现）：**

```
List<DeptTreeNode> tree(Integer status)      // 返回的是"森林"：多个公司并列，status 为 null 时返回全部
DeptVO              getById(Long id)
DeptVO              create(DeptCreateRequest request)
DeptVO              update(Long id, DeptUpdateRequest request)
void                delete(Long id)
void                changeStatus(Long id, Integer status)
```

**注意 `tree` 返回的是 `List`，不是单个根节点。** 多公司意味着组织架构天然是**森林**——一个顶级公司一棵树。返回单根会逼你造一个假的"集团总部"当容器，那是把自己绕进去。

`DeptCreateRequest` / `DeptUpdateRequest` 必须包含 `deptType`；`DeptTreeNode` 必须包含 `deptType`（前端要按类型渲染不同图标和操作），且 `children` 为空时返回 `[]` 而不是 `null`。

**Mapper 的方法签名（契约）：**

```
int          insert(SysDept dept)
int          updateById(SysDept dept)
int          deleteById(Long id)
int          updateStatus(Long id, Integer status)
SysDept      selectById(Long id)
List<SysDept> selectAll(Integer status)
int          countByParentId(Long parentId)                          // 有没有下级
int          countByParentIdAndStatus(Long parentId, Integer status)  // 有没有启用的下级
int          countByParentIdAndName(Long parentId, String deptName, Long excludeId)  // 同级是否重名
```

**`countByParentIdAndName` 的 `excludeId` 是干什么的？**
修改部门时，要排除"自己"再判重名——否则一个部门不改名字直接保存，会被自己挡住。这个参数极其容易漏，漏了就是"改别的字段也报重名"。

### 2.4 业务规则（逐条编号，每条都要有测试）

错误码约定：

| 码 | 含义 |
|---|---|
| 1001 | 部门不存在 |
| 1002 | 部门编码已存在 |
| 1003 | 同级下已存在同名部门 |
| 1004 | 上级部门不存在 |
| 1005 | 上级部门已停用 |
| 1006 | 不能将部门设置为自己的上级 |
| 1007 | 不能将部门移动到自己的下级部门中 |
| 1008 | 存在下级部门，无法删除 |
| 1009 | 存在启用的下级部门，无法停用 |
| 1010 | 层级类型不合法 |

---

**R1｜部门编码全局唯一**

新增和修改时都要校验。修改时如果编码没变，必须放行。

**R2｜同级部门名称不重复**

同一个 `parent_id` 下 `dept_name` 唯一，不同上级下可以同名（「研发部」可以在「技术中心」下，也可以在「华东分公司」下）。

**R3｜上级部门必须存在**

`parent_id != 0` 时，必须能查到该部门，否则报 1004。

**R4｜不能在已停用的部门下新增子部门**

否则会出现"挂在停用部门下的活部门"，下拉框里选了父级看不到子级，数据就脏了。报 1005。

**R5｜上级不能是自己**

把部门的 `parent_id` 设成它自己的 `id`。报 1006。

**R6｜上级不能是自己的后代**

比 R5 更隐蔽：把「技术中心」的上级改成「前端组」，而「前端组」是「技术中心」的下级。这样树里就出现了一个环，**任何递归遍历都会死循环**。

**判断方法（关键思路）**：不需要递归整棵树。从"新上级"出发，沿着 `parent_id` 一路往上走，如果中途遇到"被修改的部门自己"，就说明成环。

```
新上级 = 前端组
  → 前端组.parent_id = 研发部
  → 研发部.parent_id = 技术中心
  → 技术中心.id == 被修改的部门 → 成环，拒绝
```

沿着父链往上走是线性的，比递归子树简单得多。**记得加一个最大层数上限（比如 50），防止已有脏数据导致死循环。**

**R7｜有下级部门的部门不能删除**

报 1008。

**R8｜有启用下级部门的部门不能停用**

报 1009。提示用户先停用下级。

**注意这里的设计选择**：另一种做法是"停用父部门时级联停用所有下级"。我没选它，因为：
- 级联停用有破坏性，用户点一次可能影响几十个部门
- 恢复时不能自动级联恢复（哪些是本来就停用的、哪些是被连带停用的，分不清）
- 拒绝操作 + 明确提示，用户能理解、能控制

**R9｜删除不存在的部门**

报 1001，不是静默成功。**"删除成功"但什么都没删，是最难排查的一类 bug。**

---

**R10｜层级类型必须合法**

规则见 R00 §2.2：

| 节点类型 | 上级允许是 |
|---|---|
| 公司 | 只能是 0 |
| 部门 | 公司 或 部门 |
| 小组 | 部门 或 小组 |

违反时报 1010。具体要拦下这几种：

- 把「公司」挂到别的节点下面（公司只能顶级）
- 在「小组」下面挂一个「部门」或「公司」
- 修改节点类型时造成层级非法（比如把一个下面还挂着部门的「部门」改成「小组」）

**最后一条最容易漏。** 改类型时不能只看它自己的新上级，还要检查它**已有的下级**是否还兼容。

> **术语说明**：本文档里"部门"有时泛指组织节点，有时特指 `dept_type=2`。看上下文，涉及类型校验时是后者。

---

**关于并发**：R1、R2 在代码里"先查再写"存在竞态。数据库唯一键是兜底。所以你还需要在全局异常处理里捕获 `DuplicateKeyException`，按约束名翻译成 1002 或 1003。**这一步不做，并发下用户会看到 500。**

### 2.5 本需求明确不做的事

- **不做数据的逻辑删除** —— 由《审计与运维底座》统一决策
- **不做人员的关联校验** —— 人员表还不存在，"有在职人员不能删"这条规则等 R02 做完再加
- **不做人员、账号、登录、任职、角色、数据权限** —— 见 R00 §6 的分工表。
  本需求只把"坐标系"建对：树的形状、节点的类型、上下级关系。
  **但树的形状必须能承载它们**——这就是加 `dept_type` 和返回森林的原因
- **不做 `ancestors`（祖级路径）字段** —— `SUBTREE` 数据范围将来需要它，
  但那属于 R04。现在加是过早优化，等有真实查询压力再评估
- **不做部门移动历史记录** —— 由审计需求统一处理
- **不做批量导入导出** —— 等单条维护跑通再说
- **不做前端页面** —— 先用 curl / Apifox 验证接口
- **不建多模块 Maven 工程** —— 包结构先按模块边界划分，代码量够了再拆

### Step 2：统一返回体与全局异常处理

**目标**：所有接口返回同一个结构，所有异常都能被翻译成有意义的提示。

**为什么必须在写业务之前做？**
因为后面每个 Controller 都要返回 `Result`，每个 Service 都要抛 `BizException`。这事后补，等于把所有接口重写一遍。

**产物**

- `common/result/Result.java`、`common/result/ResultCode.java`
- `common/exception/BizException.java` —— 携带业务码，业务错误从 1000 起
- `framework/web/GlobalExceptionHandler.java` —— 处理四类：
  1. `BizException` → HTTP 400 + 业务码
  2. 参数校验失败 → HTTP 400 + `code 400` + 具体是哪个字段
  3. `DuplicateKeyException` → 按约束名翻译成 1002 / 1003（**别漏了这条**）
  4. 其他未知异常 → HTTP 500 + 通用文案（**绝不能把堆栈或原始异常消息返回给前端**）

**一个已经踩过的坑**：`@ExceptionHandler(Exception.class)` 会连 Spring 自己的 `NoResourceFoundException` 一起吞掉，把**404 变成 500**。必须单独处理它并返回 404。

**完成的标志**

写一个临时的测试接口，抛 `new BizException(1001, "部门不存在")`，然后：

```bash
curl -s -w "\nHTTP=%{http_code}\n" http://127.0.0.1:8090/api/test/biz
# 期望：{"code":1001,"message":"部门不存在"} 且 HTTP=400

curl -s -w "\nHTTP=%{http_code}\n" http://127.0.0.1:8090/api/not-exists
# 期望：HTTP=404（不能是 500）

curl -s -w "\nHTTP=%{http_code}\n" http://127.0.0.1:8090/api/test/boom
# 期望：HTTP=500 且 message 是通用文案，看不到堆栈
```

验证完把测试接口删掉。

### Step 4：Entity 与 Mapper

**目标**：能用 Java 代码完成对 `sys_dept` 的单表读写。

**产物**

- `system/dept/entity/SysDept.java` —— 字段和表一一对应，用普通类 + getter/setter（**不用 record**，MyBatis 需要无参构造）
- `system/dept/mapper/SysDeptMapper.java` —— 按 §2.3 的契约实现 9 个方法，标 `@Mapper` 注解 + `@Select`/`@Insert`/`@Update`/`@Delete`

**三个必须踩对的点**

1. **列名到驼峰**：`dept_name` → `deptName`。靠 `mybatis.configuration.map-underscore-to-camel-case: true`，写在 `application.yml` 里。
2. **`@Mapper` 而不是 `@MapperScan`**：`@MapperScan("com.wenshan.oa")` 会把包下**所有**接口（包括 Service 接口）都注册成 Mapper，直接启动失败。
3. **`selectById` 查不到时的返回值**：MyBatis 直接返回实体时，查不到得到 `null`。返回 `null` 是可以的，但**调用方必须判空**——最好让 Service 层统一处理，不要每个调用点各判一次。

**完成的标志**

写一个 `@SpringBootTest`（用 `oa_test` 库），至少覆盖：

- 插入一条，能从数据库读回来，且 `deptName` 映射正确（证明驼峰配置生效）
- 按 `parent_id` 统计数量返回正确的数字
- 插入重复的 `dept_code` 时抛出 `DuplicateKeyException`（证明唯一键生效）

**卡住了看什么**：字段读出来是 `null`，先检查驼峰配置；插入报字段找不到，检查 `@Insert` 里的列名和 `#{}` 里的属性名是否对得上。

### Step 5：Service（本需求的主战场）

**目标**：§2.4 的 9 条业务规则全部实现。

**为什么这是最难的一步？** 因为 Mapper 是体力活，Controller 是接线，**只有 Service 是真正的业务**。这里的每一条规则都对应一种用户会真实踩到的错误操作。

**实现顺序建议**（从简单到复杂，每做完一条就跑一次测试）：

1. `getById` —— 查不到抛 1001（先把最简单的一条做通，把链路跑起来）
2. `tree` —— 一次查全表，在 Java 里组装**森林**（见下）
3. `create` —— R1、R2、R3、R4、R10
4. `update` —— R1、R2、R3、R4、R5、R6、R10（注意 `excludeId`；**R4 在这里容易被漏**——不只是"在停用节点下新建"，"把节点移动到停用节点下"同样要拦）
5. `delete` —— R7、R9
6. `changeStatus` —— R8

**树形组装的正确做法**

**不要**对每个节点查一次子节点（N+1 查询，1000 个部门就是 1000 次查询）。

正确做法是**一次查出全部**，然后在内存里分组组装：

```
1. selectAll() 拿到全部部门（扁平列表）
2. 按 parentId 分组成 Map<Long, List<SysDept>>
3. 从 parentId = 0 开始，递归取出 children 挂上去
```

时间复杂度 O(n)。注意两个边界：

- **孤儿节点**：某条数据的 `parent_id` 指向一个不存在的部门，它永远不会被挂到树上，会凭空消失。要么启动时校验数据，要么在组装时把孤儿挂到根并打警告日志
- **已经有环的脏数据**：即使 R6 拦住了新产生的环，历史数据可能已经有环。组装时加访问标记，防止死循环

**事务**

`create`、`update`、`delete`、`changeStatus` 都要加 `@Transactional`。本需求里每个方法都只操作一张表，事务看起来"没必要"——但这是习惯，等到 `delete` 需要同时删除关联数据时，漏加就是数据不一致。

**注意**：`private` 方法、同类内部调用的方法上标 `@Transactional` **不生效**（Spring AOP 代理机制决定的）。这是最常见的自坑点之一。

**完成的标志**

针对 §2.4 的 10 条规则，每条至少一个测试用例。测试要断言**具体的错误码**（1003），而不是只断言"抛异常了"——只断言抛异常的话，抛的是 1004 你也不知道。

### Step 6：Controller

**目标**：6 个接口都能通过 HTTP 访问。

**产物**：`system/dept/controller/SysDeptController.java` + 4 个 DTO

**四个必须注意的点**

1. **入参用 DTO，不要用 Entity**。`DeptCreateRequest` 里只放前端允许传的字段。如果直接用 Entity 接参，前端就能传 `id`、`createTime`，可以伪造创建时间。
2. **加 `@Valid`**。`dept_name` 加 `@NotBlank`、`@Size(max = 50)`，`dept_code` 加 `@NotBlank` + `@Pattern`。校验交给框架，Service 只做业务规则。
3. **VO 里不要有 `createBy`、`deleted` 之类的内部字段**。
4. **`DeptTreeNode` 要能正确序列化成嵌套 JSON**，`children` 为空数组时返回 `[]` 而不是 `null`（前端少一层判空）。

**完成的标志**

```bash
# 建第一家公司
curl -X POST http://127.0.0.1:8090/api/system/depts \
  -H 'Content-Type: application/json' \
  -d '{"parentId":0,"deptType":1,"deptName":"技术中心","deptCode":"TECH","sort":1}'

# 建第二家公司
curl -X POST http://127.0.0.1:8090/api/system/depts \
  -H 'Content-Type: application/json' \
  -d '{"parentId":0,"deptType":1,"deptName":"华东分公司","deptCode":"EAST","sort":2}'

# 两家公司下各建一个同名部门：都应该成功
curl -X POST http://127.0.0.1:8090/api/system/depts \
  -H 'Content-Type: application/json' \
  -d '{"parentId":1,"deptType":2,"deptName":"研发部","deptCode":"TECH_RD","sort":1}'

curl -X POST http://127.0.0.1:8090/api/system/depts \
  -H 'Content-Type: application/json' \
  -d '{"parentId":2,"deptType":2,"deptName":"研发部","deptCode":"EAST_RD","sort":1}'

# 看组织架构森林：应该有两个根节点
curl http://127.0.0.1:8090/api/system/depts/tree
```

**返回的 JSON 顶层必须是长度为 2 的数组**（两家公司并列），且各自下面是嵌套的 `children`。如果返回的是单个对象，说明树接口还在按"单根"写，回去改。

### Step 7：端到端验收

**用手工 HTTP 请求把 §1.3 的每一条验收标准都走一遍**，一条一条打勾。特别确认这几条：

| 要验证的 | 命令要点 | 期望 |
|---|---|---|
| **跨公司同名** | 两家公司下各建一个「研发部」 | **都成功** |

## 5. 完成后你会得到什么

**能力上**：把"业务规则 → 数据模型 → 分层 → 接口 → 测试"这条完整链路走通了一遍。这就是后端开发的主循环，后面 8 个业务域都是重复这个循环，只是规则更复杂。

**下一步（R02）**：人员与账号。它会引入两个新东西——**关联查询**（人员挂在组织节点上）和**多表事务**，难度刚好比 R01 高一级。做完 R02，你就有"组织 + 人员 + 登录"这套底子了，那时再考虑拆 Maven 模块才有意义。
