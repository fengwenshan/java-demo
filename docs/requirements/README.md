# OA 需求文档

这个目录里是 OA 系统的需求文档。**顺序就是实现顺序**，每份都依赖前一份的产出。

---

## 1. 怎么用

1. **从下往上找第一份状态是「待实现」的**，从它的 §3 第一步开始做
2. 做完一份，回来把状态改成「已实现」，再开下一份
3. **不要跳着做**。每份文档的 §2.1 数据模型都建立在前面几份的表之上，跳着做会反复改表

每份文档的结构是固定的：

| 章节 | 内容 | 给谁看 |
|---|---|---|
| §0 | 为什么是这个顺序位置 | 你，理解动机 |
| §1 | 业务需求 + 验收标准 | 业务方，也用来验收 |
| §2 | 需求解构：数据模型、接口契约、业务规则、**不做什么** | 你，写代码前先读透 |
| §3 | 实现步骤（每步有"完成的标志"） | 你，照着做 |
| §4 | 自测清单 | 你，交付前逐条确认 |
| §5 | 完成后你会得到什么 + 下一份是什么 | 你，看进度 |

**文档里没有实现代码。** 它只回答"要什么"和"边界在哪"，代码是你的事。

## 4. 一条现在就该启动的并行工作

**移动平台集成（钉钉 / 企业微信 / 飞书）的审批流程，现在就去找 IT 或行政启动。**

原因是它有**外部依赖**，而且不在你的控制范围内：

- 需要创建企业自建应用，走内部审批
- 需要拿到 `AppKey` / `AppSecret`
- 需要配置可信域名、回调地址（**需要外网可访问的域名**，内网开发机不行）
- 如果要同步通讯录，还需要管理员的通讯录权限授权

这些走完可能几周。代码等凭证到了再写，但**流程现在就该跑起来**，别等到考勤做完了才发现卡在拿不到密钥。

选哪家（钉钉/企微/飞书）也需要现在就定——三家的接口模型差别很大，改起来不是换个 SDK 的事。

## 7. 登录和权限分别在哪份文档实现

**「认证」（你是谁）和「授权」（你能干什么）是两件事，分在两份文档里。**

| 能力 | 回答什么问题 | 在哪 |
|---|---|---|
| 人员档案 | 公司有哪些人 | R02 Step 3 |
| 账号与密码哈希 | 谁能登录、密码怎么存 | R02 Step 4 |
| **签发令牌（登录接口）** | **证明你是你** | **R02 Step 5** |
| **令牌校验过滤器** | **每个请求识别出是谁** | **R02 Step 6** |
| 角色定义 | 有哪些角色、各自能看多远 | R03 Step 3 |
| 任职 | 你在哪个组织节点上是什么角色 | R03 Step 4 |
| 登录返回角色与权限 | 我有哪些角色、能干什么 | R03 Step 5 |
| 接口权限校验 | 这个接口你能调吗 | R03 Step 6 |
| 数据权限 | 这些数据你能看吗 | R04 |

**登录不是独立环节。** 它必须建立在「人员表 + 账号表」之上——所以在 R02 内部，
登录排在第 5 步，前面必须先做完人员档案、账号和密码哈希。没有账号表，登录接口无从校验。

**登录里最容易写错的三处**（详见 R02 §2.5）：

- A6：用户名不存在和密码错误必须返回**完全相同**的响应，否则能筛出真实账号
- A7：账号停用的提示只能出现在**密码验证通过之后**
- A11：离职 / 停用账号 / 重置密码，三者都必须删除该人的全部令牌

## 8. 新业务表必须遵守的约定

### 8.1 归属列：`org_id` / `project_group_id` / `create_by`

**R04 定过"带 `org_id` 和 `create_by`"，R05 修正为三列：**

| 列 | 类型 | 说明 |
|---|---|---|
| `org_id` | BIGINT UNSIGNED **NULL** | 组织域归属节点。项目组域数据为 NULL |
| `project_group_id` | BIGINT UNSIGNED **NULL** | 项目组域归属。组织域数据为 NULL |
| `create_by` | BIGINT UNSIGNED NOT NULL | 创建人的 `person_id` |

**能跨隔离域的表，必须加 CHECK 约束**（R05 §2.4）：

```sql
CONSTRAINT ck_xxx_domain CHECK ((org_id IS NULL) <> (project_group_id IS NULL))
```

**只属于单一域的表不要硬加这两列** —— `sys_project_doc` 只有 `project_group_id NOT NULL`，
再加个永远为 NULL 的 `org_id` 是噪音。

- 少了 `org_id`，"本节点 / 本节点及以下"没有作用对象
- 少了 `create_by`，"仅本人"无从判断
- **`org_id` 由谁决定，是每份需求文档必须回答的问题**，不能默认"Service 会填"

### 8.2 删除策略（R06 §2.1）

**先归类，再决定有没有删除接口。判定标准：删掉之后，会不会永久丢失一个业务问题的答案？**

| 类别 | 策略 | 例子 |
|---|---|---|
| **审计与日志** | **只增**，不写 update / delete 的 Mapper 方法 | `sys_operation_log`、`sys_login_log` |
| **有业务历史的** | **永不删除**，用状态或时间区间 | `sys_person`、`sys_appointment`、`sys_project_member` |
| **纯配置的** | **物理删除**，删前校验没有活引用 | `sys_dept`、`sys_role` |

**不引入全局 `deleted` 字段。** 代价是每条查询都要记得加 `deleted = 0`，漏一条就是静默的数据泄露。

**需要"回收站"这类产品功能时**（用户能自己删自己写的东西），用 `deleted_at DATETIME NULL`
加生成列维护唯一键，不要用布尔值——时间戳能回答"什么时候删的"。

### 8.3 审计日志（R06 §E1）

**所有 `POST` / `PUT` / `DELETE` 接口必须同时有 `@RequiresPermission` 和 `@AuditLog`。**
覆盖率测试会抓漏。
