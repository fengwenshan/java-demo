# R05 项目组与硬隔离

> **前置**：[R00 §2.4 与 §4.3](R00-组织与权限模型.md)（**本文档就是在落地那两节**）、[R03 任职与角色](R03-任职与角色.md)、[R04 数据权限落地](R04-数据权限落地.md)。

---

## 0. 为什么第五个需求是它

R04 做完，数据权限的规则是"**并集**"：你的任职越多，能看到的数据越多；有 `ALL` 范围的人看到全部。

现在来一个需求，它和这条规则**直接对立**：

> 一个跨部门的临时项目组，组里的资料**只有组员能看。分管副总也不行——哪怕他的数据范围是 `ALL`。**

`ALL` 的意思是"**全部组织节点**"。而项目组**不在组织树里**。所以 `ALL` 天然覆盖不到它——这句话是 R05 的全部要害。

R05 要建立的不是"再多个过滤条件"，而是一个概念：**隔离域**。数据分属不同的域，**并集只在同一个域内生效，跨域之间不能互相放大。**

---

## 1. 业务需求

### 1.1 业务背景

公司要做"星火计划"，从研发部、测试部、市场部各抽几个人，组一个为期半年的临时项目组。

这个组要做的事情：

- 讨论还没定稿的方案（**不能提前泄露给其他部门**）
- 存放客户提供的原始资料（**合同约定只能项目成员接触**）
- 记录进展和问题（**内部吐槽，被别的部门看到很尴尬**）

**但公司的组织架构里没有"星火计划"这个部门。** 半年后它就解散了，成员回各自的部门。

### 1.2 需求描述

1. 能创建项目组，指定名称、负责人、起止日期
2. 能把**任意部门**的人加进项目组，能指定组内角色（组长/组员/观察员）
3. 组员能离开项目组（**不是删除成员记录**，是记录离开日期）
4. 项目组下的资料，**只有有效成员能看**
5. **有 `ALL` 范围的人、超级管理员，如果不在组里，也看不到**
6. 项目组的管理（建组、加人）**和**组内数据的可见**是**两件事**——有人能建组但看不到组里的资料
7. 项目组和"小组"是**两个不同的东西**，不能混

### 1.3 验收标准

设置：

```
组织树：
1 技术中心
 ├─ 2 研发部
 ├─ 3 测试部
 └─ 4 市场部

人员：张三（研发部）、李四（测试部）、王五（市场部）、赵总（超管，ALL）

项目组：星火计划（id=100），成员：张三（组长）、李四（组员）
```

- [ ] 张三查「星火计划」的资料列表 → 看到全部
- [ ] 李四查 → 看到全部
- [ ] **王五查 → 看到 0 条**（不在组里，哪怕他是市场部的）
- [ ] **赵总（超管，`ALL`）查 → 看到 0 条** ★ 这条是硬隔离的核心
- [ ] 赵总调"项目管理"接口 → **可以**（他有 `project:group:*` 权限码）
- [ ] 把李四的离开日期设为今天 → 李四再查 → **0 条**（立即生效）
- [ ] 把李四加回来（新建一条成员记录）→ 又能看到了
- [ ] 一个既不在组织树有任何任职、也不在任何项目组的人 → **什么都看不到**
- [ ] 上面每一条都有自动化测试

## 2. 需求解构

### 2.1 先分清"小组"和"项目组"

R00 §2.4 定过，这里展开，因为**这是最容易在实现时搞混的地方**：

| | 小组 | 项目组 |
|---|---|---|
| 英文 | team | project group |
| 存哪 | `sys_dept`，`dept_type = 3` | **独立表** `sys_project_group` |
| 性质 | **常设**组织层级 | **临时**集合 |
| 能跨部门吗 | **不能**（R00 §7 决策 1） | **就是为此而生** |
| 有下级吗 | 有（是树的一部分） | **没有**（是扁平集合） |
| 跟着谁 | 公司/部门 | 一个目标 |
| 生命周期 | 长期 | 有明确起止 |
| 数据权限 | 走**组织域**并集（R04） | **硬隔离**（本文档） |

**为什么必须是两张表？**

如果拿 `sys_dept` 加个 `dept_type = 4` 来表示项目组，立刻出现三个问题：

1. **树结构坏了**——项目组的 `parent_id` 填什么？填它挂靠的部门？那它就成了那个部门的下级，会被 `SUBTREE` 范围包含进去，**硬隔离当场失效**
2. **跨部门表达不了**——一个项目组横跨研发部、测试部、市场部，在树里只能挂一个
3. **生命周期不同**——部门不会"解散"，项目组会

**一句话：项目组不是组织，是组织之外的协作单元。**

---

### 2.2 隔离域

**概念：每条数据属于一个、且仅一个隔离域。**

| 隔离域 | 判定 | 可见规则 |
|---|---|---|
| **组织域** | `project_group_id IS NULL` | R04 的并集规则（任职 + `data_scope`） |
| **项目组域** | `project_group_id IS NOT NULL` | **只有该组的有效成员** |

**并集只在同一个域内生效。** 这是 R00 §4.3 那句话的完整落地。

#### 要害：`ALL` 是组织域的概念

`ALL` 的定义是"**全部组织节点的数据**"——R00 §4.2 就是这么写的。

项目组不在组织树里，**所以 `ALL` 覆盖不到它**。这不是特例，是定义的自然结果。

反过来如果实现时把项目组条件也塞进 R04 的 `conditions` 列表里一起 OR：

```java
// 错误做法
conditions.addAll(orgConditions);
conditions.add(projectGroupCondition);   // ← 这一加，ALL 的人就全看见了
```

因为 R04 的 `DataScope.restricted` 在遇到 `ALL` 时会变成 `false`（C3），**整个条件块被跳过**，项目组条件跟着一起被跳过——**硬隔离静默失效，没有任何报错**。

**这是本需求最危险的实现错误。** 所以 R04 的 `DataScope` 在 R05 必须**拆成两个独立的字段**，而不是一个列表：

```
DataScope
  personId
  orgRestricted        组织域是否受限（R04 的 restricted 改名）
  orgConditions        组织域条件列表
  projectGroupIds      我参与的项目组 id 集合
```

**两个字段各有各的"是否受限"，互不影响。** `赵总` 的 `orgRestricted = false`，但 `projectGroupIds = []`——他看不到任何项目组数据。

### 2.3 数据模型

两张表，加**一个用来验证隔离的最小实体**。

#### `sys_project_group` 项目组

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `group_code` | VARCHAR(50) NOT NULL | 编码，全局唯一 |
| `group_name` | VARCHAR(100) NOT NULL | 名称，全局唯一 |
| `description` | VARCHAR(500) NULL | 说明 |
| `leader_id` | BIGINT UNSIGNED NULL | 组长 `person_id`，仅用于显示和通知 |
| `start_date` | DATE NOT NULL | 开始日期 |
| `end_date` | DATE NULL | 结束日期，NULL = 长期 |
| `status` | TINYINT NOT NULL DEFAULT 1 | 1 进行中 / 0 已归档 |
| `create_by` | BIGINT UNSIGNED NOT NULL | 创建人（**项目组本身是管理数据，不隔离**） |
| `create_time` / `update_time` | DATETIME | 同前 |

唯一键：`uk_sys_pg_code (group_code)`、`uk_sys_pg_name (group_name)`
索引：`idx_sys_pg_leader (leader_id)`

**★ 故意不加 `org_id`。**

项目组是"跨组织的临时集合"，给它一个归属节点会让**"项目组数据算不算组织域数据"**这个问题变得暧昧——而这正是本文档最需要说清楚的边界。

保持它完全在组织树之外，规则最简单：**项目组数据永远不走组织域的那套并集。**

> 代价：没法表达"这是技术中心的项目组"。**记一个待办**——如果将来需要按公司隔离项目组列表，
> 那是一个独立需求（"项目组的归属与可见范围"），不要在这里顺手加个 `org_id` 了事。

#### `sys_project_member` 项目组成员

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `group_id` | BIGINT UNSIGNED NOT NULL | 项目组 |
| `person_id` | BIGINT UNSIGNED NOT NULL | 成员 |
| `member_role` | VARCHAR(20) NOT NULL DEFAULT 'MEMBER' | `LEADER` / `MEMBER` / `OBSERVER` |
| `join_date` | DATE NOT NULL | 加入日期 |
| `leave_date` | DATE NULL | **离开日期，NULL = 在组** |
| `create_time` / `update_time` | DATETIME | 同前 |

唯一键：`uk_sys_pm_group_person (group_id, person_id, join_date)`

索引：`idx_sys_pm_person (person_id)`、`idx_sys_pm_group (group_id)`

**时间区间沿用 R03 §2.1 的半开区间 `[join_date, leave_date)`**，判定公式一字不差：

```
join_date <= CURDATE() AND (leave_date IS NULL OR leave_date > CURDATE())
```

**★ 离开项目组 ≠ 删除成员记录。** 同 R03 的任职：历史要留得住（"2024 年 3 月到 8 月，李四在星火计划"）。

**★ 唯一键里那个 `join_date` 是刻意的。**

`(group_id, person_id)` 加唯一键看起来更自然，但那意味着**一个人在同一组只能有一条记录**——"张三 3 月加入、6 月离开、9 月又回来"就存不下了。

带上 `join_date` 后：

- 同一天重复加入 → 被唯一键挡住（这确实是个错误操作）
- 不同时间段的多次加入 → 允许多条记录，历史完整

> 这个"要不要带上日期"的取舍，和 R03 里"任职不加唯一键"是同一类判断：
> **唯一键挡的应该是"真的错了"的情况，不是"看起来重复"的情况。**

**复用 R03 的判定方法而不是重写**：`isEffective(startDate, endDate)` 这类方法只能有一处实现。
R03 的 C8 已经强调过一遍——**同一个判定散落两处，迟早不一致**。

#### `sys_project_doc` 项目资料（验证用的最小实体）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `project_group_id` | BIGINT UNSIGNED **NOT NULL** | 归属项目组 |
| `title` | VARCHAR(200) NOT NULL | 标题 |
| `content` | TEXT NULL | 内容 |
| `create_by` | BIGINT UNSIGNED NOT NULL | 创建人 |
| `create_time` / `update_time` | DATETIME | 同前 |

索引：`idx_sys_pd_group (project_group_id)`

> **这不是"文档协作"需求。** 真正的文档协作（版本、附件、协同编辑、全文检索）是后面的业务域。
> 这张表存在的唯一目的是**让硬隔离能端到端验证**——没有一张带 `project_group_id` 的业务表，
> 本文档的核心规则就只能停留在纸面上。
>
> 这也是吸取 R04 的教训：`CREATOR` 模式的 SQL 片段因为没有可用的表，至今没有集成测试。

### 2.4 表结构约定（对 R04 §C13 的修正）

R04 定过："参与数据权限的业务表必须带 `org_id` 和 `create_by`"。**R05 要修正它**：

**每个参与数据权限的业务表，必须带这三列：**

| 列 | 类型 | 说明 |
|---|---|---|
| `org_id` | BIGINT UNSIGNED **NULL** | 组织域归属节点。项目组域数据为 NULL |
| `project_group_id` | BIGINT UNSIGNED **NULL** | 项目组域归属。组织域数据为 NULL |
| `create_by` | BIGINT UNSIGNED NOT NULL | 创建人 `person_id` |

**且必须满足：两个归属列有且只有一个非空。**

```sql
CONSTRAINT ck_xxx_domain CHECK ((org_id IS NULL) <> (project_group_id IS NULL))
```

**这条 CHECK 约束是"每条数据属于一个且仅一个隔离域"在数据库层的表达。** 不要只靠 Service 校验——忘了校验的行会变成"两个域都算"或者"两个域都不算"，而这两种情况的表现都是**权限错误且不报错**。

> **注意这里改了 R04 的约定**（`org_id` 从 `NOT NULL` 变成 `NULL`）。
> 现在改是免费的——**因为一张业务表都还没建**。这就是"先做权限地基"的价值：
> 规则还没被任何代码依赖，改起来没有迁移成本。

**`sys_project_doc` 为什么两列都不加？** 因为它**只可能**属于项目组域，`project_group_id NOT NULL` 就够表达，加 `org_id` 反而是噪音。

规则是"**能跨域的才需要两列 + CHECK**"，纯单域的表用非空约束表达更清楚。

### 2.6 接口契约

#### 项目组管理

| 方法 | 路径 | 权限码 |
|---|---|---|
| GET | `/api/system/project-groups` | `project:group:list` |
| GET | `/api/system/project-groups/{id}` | `project:group:list` |
| POST | `/api/system/project-groups` | `project:group:create` |
| PUT | `/api/system/project-groups/{id}` | `project:group:update` |
| PUT | `/api/system/project-groups/{id}/status` | `project:group:update` |

#### 成员管理

| 方法 | 路径 | 权限码 |
|---|---|---|
| GET | `/api/system/project-groups/{id}/members` | `project:group:list` |
| POST | `/api/system/project-groups/{id}/members` | `project:member:manage` |
| PUT | `/api/system/project-members/{id}/leave` | `project:member:manage` |

#### 项目资料

| 方法 | 路径 | 权限码 |
|---|---|---|
| GET | `/api/system/project-docs?projectGroupId={id}` | `project:doc:list` |
| GET | `/api/system/project-docs/{id}` | `project:doc:list` |
| POST | `/api/system/project-docs` | `project:doc:create` |
| PUT | `/api/system/project-docs/{id}` | `project:doc:update` |

**★ 关键在于：`project:doc:list` 这个权限码只能保证"你能调这个接口"，能不能看到数据由数据权限决定。**

所以：**赵总（超管）调 `GET /api/system/project-docs?projectGroupId=100` → HTTP 200，`data.total = 0`。** 不是 403。

**为什么不是 403？** 因为 403 会泄露"这个项目组存在，只是你没权限"。而且更实际的是：**他确实有权调这个接口，只是这条数据不在他的可见范围内**。数据权限的语义是"过滤"，不是"拒绝"——和 R04 的 C6 一致（详情返回 1001 而不是 403）。

#### 新增权限码（加到 R03 的 `Permission` 枚举）

```
project:group:list / create / update
project:member:manage
project:doc:list / create / update
```

**`project:group:list` 和 `project:doc:list` 是分开的两个码。** 这是"管理权与可见权分离"在权限码上的体现：

- 有 `project:group:list` → 能看**有哪些项目组**（组织架构信息，不该保密）
- 有 `project:doc:list` **且是成员** → 才能看**组里的资料**

**项目组的名单要不要保密？** 本文档的答案是**不保密**——"公司有哪些项目组、成员有谁"属于组织信息，和"组里在讨论什么"是两回事。如果贵司要求连名单都保密，那是另一个需求（改 `project:group:list` 的可见规则），**不要顺手把它做进数据权限里**。

### 2.7 业务规则

错误码：**1400 段**。

| 码 | 含义 | HTTP |
|---|---|---|
| 1401 | 项目组不存在 | 400 |
| 1402 | 项目组编码已存在 | 400 |
| 1403 | 项目组名称已存在 | 400 |
| 1404 | 成员记录不存在 | 400 |
| 1405 | 该人员已在此项目组中（同一加入日期） | 400 |
| 1406 | 成员已离开，不能重复离开 | 400 |
| 1407 | 加入日期不能晚于离开日期 | 400 |
| 1408 | 项目组已归档，不能修改成员 | 400 |
| 1409 | 人员不存在或已离职 | 400 |
| 1410 | 资料不存在或不属于该项目组 | 400 |

---

**D1｜★ 项目组数据只有有效成员可见，`ALL` 范围和超级管理员也不行**

见 §2.2。这是本文档的全部要点。

---

**D2｜每条数据属于一个且仅一个隔离域**

用 CHECK 约束在数据库层表达（§2.4）。Service 层也要校验，给友好提示。

---

**D3｜两个隔离域的条件必须分开计算，不能合并到一个条件列表里**

见 §2.2 的"错误做法"。**这是最容易犯、也最难发现的实现错误**——因为它只在"当事人有 `ALL` 范围"时才暴露，而平时的测试账号通常没有 `ALL`。

**必须专门测**：用超管账号查项目资料，断言 0 条。

---

**D4｜项目组的管理权与组内数据的可见权是两件事**

- 建组、改成员 → 靠权限码 `project:group:*` / `project:member:manage`
- 看组内资料 → 靠成员身份

**一个持有 `project:member:manage` 的人，可以把任何人（包括自己）加进项目组**。

**这意味着硬隔离防的是"无意间看到"，不是"恶意管理员"。** 一个能改成员名单的人，总能看到他想看的东西——这必须有**审计日志**兜着（谁在什么时候把谁加进了哪个组）。

> 这条写出来是为了不让它成为"以为防住了其实没防住"的安全假象。**R06 审计必须优先覆盖项目组成员变更。**

---

**D5｜成员有效性沿用 R03 的半开区间**

`join_date <= CURDATE() AND (leave_date IS NULL OR leave_date > CURDATE())`

**复用 R03 的判定方法，不要重写一个 SQL。** 和 R04 的 C8 是同一条纪律。

---

**D6｜项目组归档（`status = 0`）后不能改成员，但组内资料仍然按成员身份可见**

归档是"这个组不再运作了"，不是"资料删了"。历史资料该能查还得能查——**只要还在成员的可见范围内**。

**归档不等于把成员全部清空。** 别顺手去写 `leave_date`。

---

**D7｜离开项目组的判定要和"成员的可见范围"完全一致**

一个校验、一个过滤，两处必须用同一个判定。**这是 R04 的 C5 和 R03 的 C8 反复出现的同一个坑**。

具体的失败场景：`leave` 接口用 `leave_date >= CURDATE()`（闭区间）判定"已经离开"，而数据权限用 `leave_date > CURDATE()`（半开区间）。于是**今天刚离开的人，数据权限还认为他在组里，但系统提示他"你已经离开了"**。

---

**D8｜项目组域的表只用一个片段，不要套 R04 的组织域条件**

`sys_project_doc` 的查询条件就是：

```
project_group_id IN (:myGroupIds)      -- myGroupIds 为空 → 1 = 0
```

**不要把 R04 的 `orgConditions` 也 OR 进来。** 那会让"研发部主管（`SUBTREE` 覆盖研发部）"看到组里的资料——因为他的组织域条件命中了。而 `sys_project_doc` **根本没有 `org_id` 列**，这个条件在 SQL 里会直接报错。

**报错反而是好事**——它会立刻暴露你套错了片段。真正危险的是**那些既能跨域、又在两个域都有列的表**，套错了不会报错，只会静默泄露。

---

**D9｜跨域的查询必须显式写出两个域，用一个"域列"区分**

等真的出现一张能跨域的表（比如"任务"，既可能挂在部门下，也可能挂在项目组下），查询条件必须是：

```sql
AND (
    ( project_group_id IS NULL AND (<组织域条件>) )
    OR
    ( project_group_id IN (:myGroupIds) )
)
```

**不要写成**：

```sql
AND ( <组织域条件> OR project_group_id IN (:myGroupIds) )
```

第二种写法下，一条属于项目组的行只要**恰好**满足组织域条件（比如 `create_by` 是当前用户），就会被露出去——绕过成员校验。

**`project_group_id IS NULL` 这个"域守卫"不能省。** 它是"数据只在它自己的域里被判定"的机械保证。

> **R05 不实现这个片段**，因为现在还没有能跨域的表（`sys_project_doc` 是纯项目组域）。
> **记进 README 待办**：第一张跨域表出现时，必须同时实现这个片段和它的端到端测试。

---

**D10｜项目组列表不参与硬隔离，但也不参与组织域并集**

`GET /api/system/project-groups` 返回**全部**项目组（只要有 `project:group:list` 权限码）。

这是刻意的：**"公司有哪些项目组"是组织信息，不是项目资料。** 把项目组列表也隔离起来，会让人连"我怎么申请加入"都做不到。

`sys_project_group` 表**不参与数据权限**——它的 Mapper 不带 `DataScope` 参数，因此也不会出现在 C12 的覆盖率测试里。

---

### 2.8 本需求明确不做的事

- **不做"项目组归属某公司"** —— 见 §2.3 的说明和待办
- **不做项目组的可见范围控制** —— 见 D10。名单默认公开
- **不做跨域表的查询片段** —— 见 D9 的待办
- **不做成员变更的审批流** —— 现在是"有权限码就能加人"。审批加入项目组是后面的事
- **不做项目组级别的角色** —— 组内的 `member_role`（组长/组员/观察员）**现在只用于显示，不参与任何权限判定**。想让"组长能删资料、组员不能"，那需要"项目实施权限"，是独立需求
- **不做项目组的文件上传** —— `sys_project_doc` 只有文本字段。附件、版本、协同编辑属于文档协作需求
- **不做定时自动归档** —— `end_date` 到了不会自动改 `status`。要不要自动归档、归档后做什么，需要业务确认
- **不做项目组成员的批量导入** —— 归到"组织调整"类需求

### Step 2：改造 `DataScope`（对 R04 的修改）

**目标**：把组织域和项目组域拆成互不影响的两个字段。

**产物**：改 `framework/datascope/DataScope.java`、`DataScopeHelper.java`

**改造前后**

```
改造前（R04）
  personId
  restricted          一个开关管全部
  conditions          一个列表装全部

改造后（R05）
  personId
  orgRestricted       只组织域
  orgConditions       只组织域
  projectGroupIds     我参与的项目组，独立字段
```

**★ 为什么必须拆成两个字段而不是两个列表**

因为它们**各自有各自的"是否受限"**：

- 超管：`orgRestricted = false`（看全部组织数据）、`projectGroupIds = []`（看不到任何项目组数据）
- 如果一个开关管全部，超管的开关一关，项目组条件也跟着没了
- 如果两个条件塞进一个列表，`ALL` 短路时（R04 的 C3）整个列表被跳过，同样泄露

**这一步做完，跑一遍 R04 的全部测试，必须全绿。** 改造不能改变组织域的行为。

**完成的标志**

### Step 3：`ProjectMembershipProvider`

**目标**：能查出"当前登录人现在在哪些项目组里"。

**产物**：`framework/datascope/ProjectMembershipProvider.java`、`system/project/ProjectMemberProvider.java`

**实现要点**

- SQL 必须带 D5 的有效性条件
- **只返回 `status = 1` 的项目组**？—— 不。归档的项目组资料**仍然可见**（D6），所以**不加 `status` 条件**
- 结果用 `Set<Long>` 返回，Service 层不再处理

**必须写的测试**

| 场景 | 期望 |
|---|---|
| 在组，`leave_date` 为 NULL | 返回该组 id |
| 在组，`leave_date` 是明天 | **返回该组 id**（半开区间，明天才失效） |
| 已离开，`leave_date` 是今天 | **不返回**（今天就是失效日，不含） |
| 已离开，`leave_date` 是昨天 | 不返回 |
| `join_date` 是明天 | **不返回**（还没加入） |
| 一个人在多组 | 全部返回 |
| 一个人反复加入同一个组两次（历史 + 当前） | **只返回一次**（用 `Set`） |

**第 3 条和第 5 条是重点。** 前者是"今天离开的今天就没权限"，后者是"明天加入的今天还没权限"——两个方向都容易写成闭区间。

### Step 5：项目资料接入硬隔离

**目标**：`sys_project_doc` 的列表、详情、总数都按成员身份过滤。

**产物**：`ProjectDocMapper.xml`、`ProjectDocServiceImpl`、共享片段 `projectScopeOnly`

**片段长什么样**

```xml
<sql id="projectScopeOnly">
    <choose>
        <when test="scope == null or scope.projectGroupIds.isEmpty()">
            AND 1 = 0
        </when>
        <otherwise>
            AND d.project_group_id IN
            <foreach collection="scope.projectGroupIds" item="g" open="(" separator="," close=")">#{g}</foreach>
        </otherwise>
    </choose>
</sql>
```

**★ 注意这里没有 `<if test="scope.restricted">`。**

R04 的片段用 `restricted` 做总开关，**这里不能有**——因为 `projectGroupIds` 为空的正确行为是"什么都看不到"（`1 = 0`），不是"不过滤"。

**这正是 R04 的 C4 在另一个域的体现**：默认必须拒绝。如果这里也套一个 `restricted` 开关，那么"没有任何项目组的人"和"超管"会被同等对待——**超管就看到了全部项目资料**。

**`1 = 0` 必须真的出现在 SQL 里。** 不要依赖"`IN` 空集合会报错所以没关系"——报错会让接口 500，而正确行为是安静地返回 0 条。

**查询参数**

`ProjectDocQuery` 带 `projectGroupId`（用户想看哪个组）+ `DataScope scope`。
**用户传的 `projectGroupId` 和 `scope.projectGroupIds` 是 AND 关系**——他想看 A 组，但他只在 B 组，应该返回 0 条。

**完成的标志**

```bash
# 张三（组员）
curl -s "http://127.0.0.1:8090/api/system/project-docs?projectGroupId=100" -H "Authorization: Bearer $ZS"
#    期望：能看全
curl -s "http://127.0.0.1:8090/api/system/project-docs?projectGroupId=100" -H "Authorization: Bearer $LEE"
#    期望：能看全
curl -s "http://127.0.0.1:8090/api/system/project-docs?projectGroupId=100" -H "Authorization: Bearer $WANG"
#    期望：data.total = 0，HTTP 200
curl -s "http://127.0.0.1:8090/api/system/project-docs?projectGroupId=100" -H "Authorization: Bearer $ZHAO"
#    期望：data.total = 0，HTTP 200   ★ 超管，这条是核心验收
```

**第 4 条必须真的测，而且要用真的超管账号。** 平时开发用的管理员账号通常也顺手加了项目组，所以"超管看不到"这个现象很容易在本地测不出来。

### Step 7：端到端验收

按 §1.3 逐条走。**重点还是"看不到"那一类。**

```bash
# ① 张三（组员）能看到
# ② 李四（组员）能看到
# ③ 王五（不在组）看不到，HTTP 200 + total=0
# ④ 赵总（超管）看不到，HTTP 200 + total=0        ★
# ⑤ 赵总能列项目组、能加成员（管理权独立于可见权）
# ⑥ 李四离开 → 立刻看不到
curl -X PUT http://127.0.0.1:8090/api/system/project-members/2/leave -H "Authorization: Bearer $ADMIN"
curl -s "http://127.0.0.1:8090/api/system/project-docs?projectGroupId=100" -H "Authorization: Bearer $LEE"
#    期望：total = 0        ← 不用重新登录
# ⑦ 李四重新加入 → 又能看到
# ⑧ 归档项目组 → 成员仍然能看到资料（D6）
```

**第 ⑥ 条要连着做，中间不要重新登录。** 因为成员判定是每个请求实时查的（R03/R04 都没加缓存），离开应当**立即**生效。

如果第 ⑥ 条失败（离开后还能看到），**不要急着加缓存失效逻辑**——先确认你查成员时用的是 D5 的半开区间，而不是把 `leave_date` 的判定写成了 `>=`。

**再加一条并集/隔离的交叉验证**（D3 的核心）

```
给赵总（超管，ALL）的账号加一段"技术中心 SUBTREE"任职
→ 赵总看部门树：全部可见（组织域不受限）
→ 赵总看项目资料：仍然 0 条（项目组域不受影响）

再把赵总加进星火计划
→ 赵总看项目资料：能看到了（因为他是成员了，不是因为他是超管）
→ 把赵总移出星火计划
→ 又看不到了
```

**这个"加了又能看、移出又看不到"的循环，是证明"可见性来自成员身份而不是超管身份"的唯一办法。** 只测一次"超管看不到"不够——因为如果实现是"项目组条件根本没写"，超管也看不到，测试照样过。

## 5. 完成后你会得到什么

**能力上**：你处理了权限系统里最微妙的一类问题——**两套对立的规则共存**。

R04 是"越多任职看越多"，R05 是"不在组里什么都看不到"。它们不是谁覆盖谁，而是**作用在数据的不同部分**。让它们各管各的、互不放大，靠的是**把"是否受限"拆成两个独立的开关**，而不是想办法把两套条件揉进一个列表。

这个思路——**"当两个规则互相冲突时，先看它们是否作用于不同的集合，如果是，就不要试图统一它们"**——在你后面做任何权限、状态机、审批流时都会用到。

**你还第一次遇到了"防御对象不是攻击者"的情况**：D4 明说了硬隔离防的是"无意间看到"，不是"恶意管理员"。**承认边界在哪，比假装防住了更安全**——因为后者会让人放松对审计的要求。

**下一步（R06 审计与运维底座）**：

现在系统里有几笔明确记着的欠账，全都指向同一件事：**"发生了什么"没有被记录下来**。

- R03：权限变更没有留痕（谁给谁加了什么角色）
- R05：项目组成员变更没有留痕（谁能加自己进组）
- R04：导出功能将来必须复用数据权限，否则会绕过

R06 会把这些一起解决，并且处理另一个被反复推迟的决策：**逻辑删除还是物理删除**。
