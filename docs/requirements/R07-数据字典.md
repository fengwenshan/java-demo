## 0. 为什么第一份实现的是它

R01 把组织节点类型写死在代码里：`dept_type` 是 `TINYINT`，1=公司、2=部门、3=小组，还配了一张层级校验表。

要加一个「事业部」，就得改代码、发版、改那张表。

**而且类型本该由业务自己维护**——组织架构的层级叫法各公司不一样。有的叫"事业部"，有的叫"中心"，有的把"小组"叫"科室"。这些不该是程序员的决定。

顺带，字典是**通用能力**：请假类型、公告分类、资产类别、离职原因……全都要它。先把它建好，后面每个业务模块省一次。

**所以这是第一份要动手的需求，也是唯一一份"回头改前面文档"的需求。**

## 1. 业务需求

### 1.1 业务背景

公司的组织层级是：

```
集团 → 区域公司 → 分公司 → 事业部 → 部门 → 科室
```

六层。而 R01 只认三种类型。硬要往三种里塞，就会出现"分公司也叫部门"这种别扭事——而**数据权限、报表、审批人规则全都要按类型区分**，叫错了就全错。

同时，行政要能自己维护这些类型的名字，不用每次找开发。

### 1.2 需求描述

1. 能定义**字典类型**（一本字典，比如"组织节点类型"）
2. 能往字典里加**字典项**（公司、事业部、部门、科室……），每项有名称和排序
3. 所有需要下拉选项的地方，都从字典取
4. **被业务数据引用的字典项不能消失**——历史数据要能一直显示出来
5. 字典要能停用（停用后不出现在新增下拉框，但历史数据照常显示）
6. 先只建一本：`dept_type`（组织节点类型）

### 1.3 验收标准

- [ ] 能查 `dept_type` 这本字典的全部启用项，返回 `itemKey` / `itemLabel` / `sort`
- [ ] 能新增一个字典项 `BU` / "事业部"，排序 15
- [ ] 新增后，R01 建节点时的类型下拉框里**立刻**能选到"事业部"
- [ ] 能新增一个**字典类型**，比如 `leave_type`（请假类型）
- [ ] **没有删除接口**——字典项和字典类型都只能停用
- [ ] 停用一个字典项后：新增下拉框里没有它，**但已有的节点详情里照常显示它的名称**
- [ ] 用 `itemKey = 'BU'` 建一个部门节点 → 成功
- [ ] 用 `itemKey = 'NOT_EXIST'` 建一个部门节点 → **拒绝，报 1010**
- [ ] 上面每一条都有自动化测试

## 2. 需求解构

### 2.1 ★ 核心原则：字典能配标签，配不了行为

**这条决定了什么东西可以进字典，什么东西不可以。**

| | `dept_type`（组织节点类型） | `data_scope`（数据范围，R03） |
|---|---|---|
| 值 | `COMPANY` / `BU` / `DEPT` / `TEAM` | `SELF` / `NODE` / `SUBTREE` / `ALL` |
| 加一个新值会怎样 | 只是多一个标签，**行为不变** | **需要一段新的 SQL 生成逻辑**（R04 §2.2） |
| 能进字典吗 | **能** | **不能** |

**为什么 `dept_type` 是纯标签？** 因为 R07 同时**删掉了 R01 的层级校验**（原 R10 那条规则，见 §2.2）。

在删掉它之前，`dept_type` 是有行为的——它决定"这个节点能挂在谁下面"。那时候把它放进字典，等于**把组织模型的规则交给一个下拉框**。

删掉它之后，`dept_type` 只剩两件事：前端渲染什么图标、列表上显示什么名字。**纯展示**。所以可以进字典。

**判断标准**：

> **加一个新值，需要改代码吗？**
> 需要 → 它是有行为的，不能进字典（或者进了字典也只是个壳，真正的规则还在代码里）。
> 不需要 → 它是标签，可以进字典。

**这条标准后面每次想加字典时都要问一遍。** 把有行为的枚举塞进字典，会造出一个"看起来能配、实际配了没用"的假配置——比不支持配置更糟。

### 2.2 连带后果：R01 的层级校验被删除

R00 §2.2 现在有这么一张表：

| 节点类型 | 上级允许是 |
|---|---|
| 公司 | 只能是 0（顶级） |
| 部门 | 公司 或 部门 |
| 小组 | 部门 或 小组 |

**类型开放之后这张表就没法维护了**——你加一个"事业部"，表里没有它，校验逻辑不知道该拦还是该放。

所以：**R01 的 R10 改写**——原来的"层级类型必须合法"整段删掉，编号保留，改成"节点类型必须存在且启用"；
错误码 **1010 保留但改含义**（见 §2.5）。

**规则编号不变是为了不动 R01 的其余交叉引用。** 改成 R11 会让所有"见 R10"的引用失效，不值当。

**建节点时不做任何位置校验。** 事业部想挂在"前端组"下面也随你。

#### 什么被删了，什么必须留着

| 规则 | 去处 |
|---|---|
| R3 上级必须存在 | **留** —— 不然就是孤儿 |
| R4 不能挂在已停用的节点下 | **留** —— 同原有理由 |
| R5 上级不能是自己 | **留** |
| **R6 上级不能是自己的后代** | **留** —— 成环会让 R04 的子树计算死循环 |
| **R10 里的层级校验** | **删除**，编号保留，改为"节点类型必须存在且启用" |

前四条不是业务规则，是**树的完整性**。它们保证"这仍然是一棵树"。层级校验才是业务规则，删掉它，树还是树。

> **术语要跟着改**：R01 原来的注释说 `dept_type` "决定层级校验规则与前端渲染"。
> 现在只剩后半句。

### 2.3 数据模型

#### `sys_dict_type` 字典类型

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `dict_type` | VARCHAR(50) NOT NULL | 字典码，全局唯一，**代码里引用的就是它** |
| `type_name` | VARCHAR(50) NOT NULL | 名称，如"组织节点类型" |
| `status` | TINYINT NOT NULL DEFAULT 1 | 1 启用 / 0 停用 |
| `remark` | VARCHAR(200) NULL | 备注 |
| `create_time` / `update_time` | DATETIME | 同前 |

唯一键：`uk_sys_dict_type_code (dict_type)`

#### `sys_dict_item` 字典项

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `dict_type` | VARCHAR(50) NOT NULL | 属于哪本字典 |
| `item_key` | VARCHAR(50) NOT NULL | **组内唯一键**，业务数据引用的值 |
| `item_label` | VARCHAR(50) NOT NULL | 名称，界面上显示的 |
| `sort` | INT NOT NULL DEFAULT 0 | 排序 |
| `status` | TINYINT NOT NULL DEFAULT 1 | 1 启用 / 0 停用 |
| `remark` | VARCHAR(200) NULL | 备注 |
| `create_time` / `update_time` | DATETIME | 同前 |

唯一键：`uk_sys_dict_item (dict_type, item_key)`
索引：`idx_sys_dict_item_type (dict_type, sort)`

**`uk_sys_dict_item (dict_type, item_key)` 就是你说的"这个键名在当前一组字典内不能重名"。**

#### ★ 为什么业务数据存 `item_key` 而不是字典项的 `id`

`sys_dept.dept_type` 里存的是 `'COMPANY'`，不是 `3`。

| | 存 `id` | 存 `item_key`（采纳） |
|---|---|---|
| **跨环境** | 开发环境字典项 id=3、生产 id=7。**同一份初始化 SQL 在两边插出来的数据含义不同** | 到哪都是 `'COMPANY'` |
| **可读性** | `dept_type = 1` 要查字典才知道是什么 | `dept_type = 'COMPANY'` 一眼懂 |
| **备份/导出** | 数据脱离字典就失去语义 | 自带语义 |
| **代价** | id 随便变 | **`item_key` 一旦被引用就不能改** |

第一行是决定性的。数据库迁移、多环境部署、把生产数据导到测试环境排查问题——**这些场景下 id 都会错位**，而 `item_key` 不会。

那个代价，用下面这条规则兜住。

#### ★ 为什么只提供停用，不提供删除

**因为字典是通用的——`sys_dict_item` 不知道谁在引用它。**

`sys_dept.dept_type = 'BU'` 引用了字典项 `BU`。但字典表不知道这件事，也没法做"被引用就不能删"的检查。这是通用字典的固有代价。

如果允许删除，后果是：

```
1. 管理员删掉字典项 'BU'
2. sys_dept 里 dept_type = 'BU' 的节点还在
3. 前端拿到 'BU' 去字典里查名称 → 查不到
4. 界面上显示空白
```

**注意第 4 步——它不报错。** 一个空白的部门类型，没有任何错误日志，只能靠人肉发现。

所以：**字典类型和字典项都只能停用，不能删除。** 建错了就停用，它在界面上的效果和删掉一样，但历史数据不会失去名称。

**那 `dict_type` 和 `item_key` 拼错了怎么办？** 停用，重新建一条。被停用的那条永远留在表里——这是**刻意的**，因为它是历史数据的锚点。

### 2.4 分层与包结构

```
com.wenshan.oa
├── framework/
│   └── dict/                          ← 新增
│       └── DictItemProvider.java       接口：按 dictType 取启用项
└── system/dict/                       ← 新增

    ├── service/SysDictService.java + impl
    ├── mapper/SysDictTypeMapper.java、SysDictItemMapper.java
    ├── entity/SysDictType.java、SysDictItem.java
    └── dto/ DictItemVO / DictItemRequest / DictTypeVO / DictTypeRequest
```

**`DictItemProvider` 接口放在 `framework`，实现放在 `system.dict`** —— 和 R04 的 `OrgTreeProvider`、R05 的 `ProjectMembershipProvider` 同一个套路。

R01 要用它校验"节点类型是否存在"：

```
// framework/dict
interface DictItemProvider {
    boolean existsEnabled(String dictType, String itemKey);
    List<DictItemVO> listEnabled(String dictType);
}
```

**为什么不让 R01 直接查 `sys_dict_item`？** 依赖方向必须是 `system.dept → framework`，不能是 `system.dept → system.dict`。业务模块之间禁止直接依赖，这条规则在 [总体设计文档 §3.2](../oa-system-design.md) 里定过。

### 2.5 接口契约

#### 查询（**登录即可，不需要权限码**）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/system/dicts/{dictType}/items` | 取一本字典的字典项 |
| GET | `/api/system/dicts` | 字典类型列表 |

`/items` 支持 `?includeDisabled=false`（默认 false）。

**为什么查询不需要权限码？**

字典是**公共参照数据**——它是下拉框的内容。你在界面上本来就会看到，把它锁起来没有安全价值，只会让每个角色的权限配置都多一行。

> **代价**：任何登录用户能读任何字典。如果将来某本字典含敏感内容（比如"离职原因"里的细节），需要单独控制。
> **记进 README 待办。**

响应：

```json
{
  "code": 200,
  "data": [
    { "itemKey": "COMPANY", "itemLabel": "公司",   "sort": 10, "status": 1 },
    { "itemKey": "BU",      "itemLabel": "事业部", "sort": 15, "status": 1 },
    { "itemKey": "DEPT",    "itemLabel": "部门",   "sort": 20, "status": 1 },
    { "itemKey": "TEAM",    "itemLabel": "科室",   "sort": 30, "status": 1 }
  ]
}
```

**注意 R07 预置的数据把"小组"叫"科室"** —— 这正是要字典的原因：**叫法由业务定，不由代码定**。

#### 管理（需要权限码）

| 方法 | 路径 | 权限码 |
|---|---|---|
| POST | `/api/system/dicts` | `system:dict:manage` |
| PUT | `/api/system/dicts/{id}` | `system:dict:manage` |
| PUT | `/api/system/dicts/{id}/status` | `system:dict:manage` |
| POST | `/api/system/dicts/{dictType}/items` | `system:dict:manage` |
| PUT | `/api/system/dict-items/{id}` | `system:dict:manage` |
| PUT | `/api/system/dict-items/{id}/status` | `system:dict:manage` |

**没有 `DELETE`。** 见 §2.3。

**★ 权限码机制在 R03 才建好，所以这些接口在 R07 阶段只能校验"登录"。**

R03 的 Step 6 里会有一张"给已有接口补 `@RequiresPermission`"的清单，**R07 的这 6 个接口要加进那张清单**。在那之前，任何登录用户都能改字典配置——这是**已知的临时缺口**，和 R01/R02 的 11 个接口情况相同。

### 2.6 业务规则

错误码：**1500 段**（按文档编号分段：R01=1000、R02=1100、R03=1200、R05=1400、R07=1500。
**1300 段是空的**——R04 不新增错误码，数据权限是过滤不是校验）。

| 码 | 含义 | HTTP |
|---|---|---|
| 1501 | 字典类型不存在 | 400 |
| 1502 | 字典码已存在 | 400 |
| 1503 | 字典项不存在 | 400 |
| 1504 | 字典项键在当前字典内已存在 | 400 |
| 1505 | 字典项键格式非法 | 400 |
| 1506 | 字典项名称在当前字典内已存在 | 400 |
| 1507 | 字典类型下已有字典项，不能停用 | 400 |

---

**F1｜字典类型和字典项都只能停用，不能删除**

见 §2.3。**代码上不写 `delete` 的 Mapper 方法** —— 没有方法，就没有人会不小心调用它。

和 R06 §E4 的"日志表只增"是同一条纪律。

---

**F2｜`item_key` 只含大写字母、数字、下划线，长度 1–50**（1505）

正则：`^[A-Z][A-Z0-9_]{0,49}$`

**为什么不用数字或中文当 key？**

- 数字：可读性差，而且和"存 id"的坑只差一步
- 中文：编码问题、URL 传参麻烦、某些数据库排序规则下会有诡异行为

**为什么必须大写字母开头？** 因为 `item_key` 会出现在代码里（`"COMPANY"`）和 SQL 里。统一的格式让 grep 有效。

**用测试钉死格式**（和 R03 的权限码格式测试同一个思路）：

```
断言：所有已存在的 item_key 都匹配 ^[A-Z][A-Z0-9_]{0,49}$
断言：新增时传 "company"（小写）→ 1505
断言：新增时传 "1COMPANY"（数字开头）→ 1505
```

**格式是契约。** 前端、字典表、业务表、代码常量，四处都引用它。格式失控会变成一团乱麻，而且**是静默的**——`'company'` 和 `'COMPANY'` 是两个不同的 key，查不到但也不报错。

---

**F3｜引用方存 `item_key`，不存字典项的 `id`**

见 §2.3。

**这条要在 R01 里落实**：`sys_dept.dept_type` 是 `VARCHAR(30)`，存 `'COMPANY'`。

---

**F4｜只有"纯标签"才能进字典**

见 §2.1。判断标准：**加一个新值，需要改代码吗？**

**每次想加一本字典时都要问一遍。** 这一条比它的表述听起来重要——它防的是"假配置"：界面上能配，配了不生效，而且没人知道。

---

**F5｜停用的字典项，历史数据仍然要能显示**

`GET /items?includeDisabled=true` 要能返回停用项。

**前端怎么用**：

- **新增/编辑表单的下拉框** → `includeDisabled=false`
- **详情页展示已有数据** → `includeDisabled=true`（或者先按 key 查名称）

**如果前端两种都用了 `false`**，症状是：停用一个类型后，历史节点的类型显示成空白。**这不报错**，只能靠人发现。

---

**F6｜引用方必须校验 `item_key` 存在且启用**

R01 建节点 / 改节点类型时，必须校验 `dept_type` 字典里有这个 key 且 `status = 1`。不存在报 **1010**（沿用 R01 原错误码，含义从"层级类型不合法"改为"节点类型不存在或已停用"）。

**为什么不是数据库外键？** R06 §2.1 定过：全系统不用外键。而且 `sys_dict_item` 的唯一键是 `(dict_type, item_key)`，`sys_dept` 只存了 `dept_type` 的值，**没有存 dict_type**——外键根本建不起来（除非给每张表都加一个"我的类型字段引用哪本字典"的列，那不值得）。

**所以校验只能在 Service 层，而且必须有测试。**

---

**F7｜字典不加服务端缓存**

和 R03/R04 的理由一致：**缓存失效逻辑写错的代价大于它省下的查询**。

但这里有个区别值得说清楚：**字典失效的后果很轻**——停用一个类型后界面暂时还能选到它，用户最多建错一个节点。**权限失效是数据泄露。** 两者的风险等级不同。

所以：

- **服务端不加缓存**（保持一致性简单）
- **前端可以做本地缓存**（字典极少变，一次会话拉一次就够）——改字典后前端刷新页面即可

**不要因为"字典读得多"就急着上缓存。** 等真的成为瓶颈再说。

---

**F8｜字典不参与数据权限**

字典是全局配置，不带 `org_id` / `project_group_id`，也不标 `@DataScopeRequired`。

**所以它不会出现在 R04 的覆盖率测试里**，这是对的。

---

### 2.7 本需求明确不做的事

- **不做字典项的"被引用检查"** —— 通用字典做不到。靠 F1（只能停用）规避
- **不做字典值的类型校验** —— `item_key` 都是字符串。要 `INT` 或 `DATE` 类型的话，是另一个需求
- **不做字典分组/树形字典** —— 如果哪天要"请假类型 → 子类型"这种层级字典，是另一个需求。**别用逗号分隔的 key 硬凑**
- **不做多语言** —— `item_label` 只有一份。要 i18n 的话，加一张 `sys_dict_item_i18n` 表
- **不做字典的版本管理** —— 改了就是改了，没有历史。**变更留痕靠 R06 的 `@AuditLog`**
- **不做"某些字典仅管理员可见"** —— 见 §2.5 的说明，记为待办
- **不做前端下拉框组件** —— 那是前端的事，本文档只定接口契约
- **不预置除 `dept_type` 之外的字典** —— 请假类型等，各自的需求文档里加

## 3. 实现步骤

### Step 0：环境与工程骨架（**别跳过**）

### Step 1：两张表 + 预置 `dept_type`

**目标**：表建好，`dept_type` 字典有初始数据。

**产物**：`V1__init_dict.sql`

**表结构**见 §2.3。**注意：R07 的迁移脚本编号是 V1**——它现在是第一份实现。

**预置数据**

```sql
INSERT INTO sys_dict_type (dict_type, type_name, remark)
VALUES ('dept_type', '组织节点类型', '用于 sys_dept.dept_type，R01 依赖');

INSERT INTO sys_dict_item (dict_type, item_key, item_label, sort) VALUES
('dept_type', 'COMPANY', '公司',   10),
('dept_type', 'DEPT',    '部门',   20),
('dept_type', 'TEAM',    '小组',   30);
```

**★ 这里有个决定要留意**：R00/R01 原来叫"小组"，我建议预置成"小组"，让业务自己改成"科室"或别的。
**不要在迁移脚本里替业务做命名决定**——那正是要字典的原因。

**手工验证**

```sql
-- 1. 同一个 key 在同一个字典里重复：必须失败
INSERT INTO sys_dict_item (dict_type, item_key, item_label, sort) VALUES ('dept_type', 'DEPT', '重复', 1);

-- 2. 不同字典里同一个 key：必须成功（key 只在组内唯一）
INSERT INTO sys_dict_type (dict_type, type_name) VALUES ('leave_type', '请假类型');
INSERT INTO sys_dict_item (dict_type, item_key, item_label, sort) VALUES ('leave_type', 'DEPT', '部门', 1);
```

**第 2 条是重点。** 它验证的是"组内唯一"而不是"全局唯一"。搞错了会导致**不同字典不能有同名 key**，那字典就没法用了（`DEPT` 在组织字典和请假字典里都可能出现）。

**完成的标志**：上面 3 条 SQL，2 成功 1 失败。

### Step 2：查询接口

**目标**：前端能拿到下拉选项。

**产物**：`DictItemProvider` 接口 + `SysDictServiceImpl.listItems` + `SysDictController`

**实现要点**

- `includeDisabled` 默认 `false`
- **排序**：先按 `sort`，`sort` 相同按 `id`。**不要只按 `sort`** —— 两条 sort 都是 0 时顺序不稳定，前端每次刷新顺序都可能变，看起来像 bug
- **`item_key` 格式校验在写入时做**（F2），查询时不做
- 查不存在的 `dictType` → **返回空数组，不报错**（1501 只在管理接口用）

**最后一条的理由**：前端渲染一个下拉框，字典为空时应该显示"暂无选项"，而不是弹一个错误。**查询接口对"没有数据"要宽容，管理接口对"引用不存在"要严格。**

**完成的标志**

```bash
curl -s http://127.0.0.1:8090/api/system/dicts/dept_type/items \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
# 期望：3 条，按 sort 排序
```

### Step 3：管理接口

**目标**：能增改字典类型和字典项。

**产物**：`SysDictController` 的管理部分 + Service

**实现要点**

- **不写 `delete` 的 Mapper 方法**（F1）
- 唯一键冲突靠数据库兜底，`DuplicateKeyException` 映射表加 `uk_sys_dict_type_code`、`uk_sys_dict_item`
- **`item_key` 格式校验**用 F2 的正则，报 1505
- **`item_key` 已存在时不能修改** —— 修改只允许改 `item_label`、`sort`、`remark`。改 `item_key` 等于"换一个 key"，那会让引用它的历史数据失去名称（F3）
- **停用字典类型时，如果它下面还有启用的字典项，要不要拦？** → **拦**（1507）。理由同 R01 的 R8：停用一本字典会让下面所有项失去意义，需要用户显式逐个处理
- R03 做完前，这些接口只校验登录（见 §2.5）

**`item_key` 不能改，那改错了怎么办？** 停用旧项，新建一条。**这是刻意的**——历史数据要能一直查到旧 key 的名称。

**完成的标志**

```bash
# 加一条
curl -X POST http://127.0.0.1:8090/api/system/dicts/dept_type/items \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"itemKey":"BU","itemLabel":"事业部","sort":15}'

# 小写的 key → 必须 1505
curl -X POST http://127.0.0.1:8090/api/system/dicts/dept_type/items \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"itemKey":"bu","itemLabel":"事业部","sort":15}'

# 尝试改 itemKey → 必须被忽略或拒绝
# 尝试 DELETE → 接口不存在（404）
```

### Step 4：契约测试

**目标**：把"格式"和"引用有效性"钉住。

**产物**：`DictContractTest`

**三条测试**

```
1. 所有已存在的 item_key 都匹配 ^[A-Z][A-Z0-9_]{0,49}$
2. 所有 sys_dict_item.dict_type 都能在 sys_dict_type 里找到
   —— 验证没有人手工往数据库插了野数据
3. 每条 sys_dept.dept_type 都能在 dept_type 字典里找到（R01 实现后加）
```

**第 2 条是"孤儿字典项"体检**——R06 的 `DataIntegrityChecker` 里也要加这一项。

**为什么要有第 2 条？** 因为 `sys_dict_item.dict_type` 没有外键（F6 说明了原因）。手工插数据、迁移脚本写错，都会产生孤儿。**没有外键，就要有体检。**

**完成的标志**：故意手工插一条 `dict_type = 'not_exist'` 的字典项，第 2 条测试必须失败。

### Step 5：端到端验收

按 §1.3 逐条走。

```bash
# ① 查字典
curl -s http://127.0.0.1:8090/api/system/dicts/dept_type/items -H "Authorization: Bearer $T"

# ② 加一个"事业部"

  -H "Authorization: Bearer $T" -H 'Content-Type: application/json' -d '{"status":0}'

# ④ 默认查询：不应该有"事业部"
curl -s http://127.0.0.1:8090/api/system/dicts/dept_type/items -H "Authorization: Bearer $T"
```

**第 ④ 和第 ⑤ 条必须一起测。** 只测一条说明不了 F5 做对了——第 ⑤ 条是"历史数据还能显示"的机械保证。

## 5. 完成后你会得到什么

**能力上**：你第一次做了"**把配置权交出去**"这件事，而且是在想清楚边界之后交的。

**边界就是 F4 那条**：字典能配标签，配不了行为。有行为的枚举（`data_scope`）留在代码里，不是因为懒，是因为**把有行为的东西放进字典会造出"假配置"**——界面上能改，改完不生效，而且没人知道。

这个判断在你后面做任何"要不要做成可配置"的决定时都会用到。

**你还处理了"通用能力的固有代价"**：字典是通用的，所以它不知道谁在引用它，所以它不能提供删除。**这不是设计缺陷，是通用性的必然结果**——认下这个代价，然后用"只能停用"把风险关掉。

**下一步（R01 部门管理）**：有了字典，R01 要改三处——

1. `dept_type` 从 `TINYINT` 改成 `VARCHAR(30)`，存字典项的 `item_key`
2. **R10 里的层级校验删掉**，改成"类型在字典里存在且启用"
3. 建节点 / 改类型时调用 `DictItemProvider.existsEnabled("dept_type", ...)`

其余不动——树、唯一键、环检测（R6）、森林返回，全部照旧。
