# R03 任职与角色

> **前置**：[R00 组织与权限模型](R00-组织与权限模型.md)（§3、§4 必读）、[R01 部门管理](R01-部门管理.md)、[R02 人员与账号](R02-人员与账号.md)。

---

## 0. 为什么第三个需求是它

R01 建了组织树，R02 建了人和账号——**但人和组织之间还是断开的**。一个人的账号能登录，系统却不知道他在哪个部门、能干什么。

R03 就是那根线。做完之后回答这些问题：

- 张三是谁？→ R02
- 张三是哪个部门的？→ **R03**
- 张三能看/能改什么？→ **R03**
- 张三同时在三家公司任职，各自什么角色？→ **R03**

**这也是补安全漏洞的一份。** R02 只校验了"登录了没有"，没校验"能不能干这个"。现在任何一个能登录的人，都能调用删除部门的接口。R03 把每个接口挂上权限码。

---

## 1. 业务需求

### 1.1 业务背景

公司里常见这几类人，用"一个部门一个角色"的模型全都表达不了：

| 人 | 情况 |
|---|---|
| 财务经理 | 在技术中心（公司）任职，要看整个技术中心及下属部门的财务数据 |
| 研发部主管 | 同时挂华东分公司/研发部，还要管技术中心/研发部的技术线 |
| 普通组员 | 只在技术中心/研发部/前端组，只看自己的数据 |
| 行政专员 | 需要维护人员档案和部门，但不该看到业务数据 |
| 系统管理员 | 什么都能干，包括改别人的角色 |

### 1.2 需求描述

1. 能定义角色：角色名、编码、**数据范围**（看多远）、能调用哪些接口
2. 能把角色授予某人**在某个组织节点上**——这叫一段**任职**
3. 一个人可以有**任意多段**任职，可以跨公司、跨部门、跨小组
4. 任职有**开始日期和结束日期**，能查到"他去年是哪个部门的"
5. 登录后能拿到**全部角色、全部任职、全部权限**
6. 每个接口要校验调用者有没有对应权限
7. 系统必须**始终至少有一个可用的超级管理员**，不能把自己锁在外面

### 1.3 验收标准（业务方看得懂的）

- [ ] 能建一个"研发部主管"角色，数据范围设为"本节点及以下"
- [ ] 能把"研发部主管"授予张三，**指定在华东分公司/研发部这个节点上**
- [ ] 张三登录后，能看到自己的**全部**角色和任职
- [ ] 张三调用"删除部门"接口 → **403 拒绝**（他没这个权限）
- [ ] 给"研发部主管"角色勾上"部门新增"权限后，张三**立刻**就能调用了，**不用重新登录**
- [ ] 结束张三的一段任职后，他的角色和权限**立刻**少了那一个
- [ ] 想停用最后一个超级管理员账号时 → 被拒绝，提示原因
- [ ] 想删掉一个下面还挂着任职记录的组织节点 → 被拒绝
- [ ] 上面每一条都有自动化测试

## 2. 需求解构

### 2.1 数据模型

三张新表。

#### `sys_role` 角色

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `role_code` | VARCHAR(50) NOT NULL | 角色编码，全局唯一，给代码和审计引用 |
| `role_name` | VARCHAR(50) NOT NULL | 角色名称，全局唯一 |
| `data_scope` | VARCHAR(20) NOT NULL | `SELF` / `NODE` / `SUBTREE` / `ALL`（R00 §4.2） |
| `is_global` | TINYINT NOT NULL DEFAULT 0 | 1 = 全局角色，任职不绑组织节点 |
| `sort` | INT NOT NULL DEFAULT 0 | 列表排序 |
| `status` | TINYINT NOT NULL DEFAULT 1 | 1 启用 / 0 停用 |
| `remark` | VARCHAR(200) NULL | 备注 |
| `create_time` / `update_time` | DATETIME | 同前 |

唯一键：`uk_sys_role_code (role_code)`、`uk_sys_role_name (role_name)`

**`data_scope` 用字符串而不是数字**：数据库里 `SUBTREE` 一眼能读懂，`3` 要翻代码。为此付的代价是拼错的可能——所以 **Service 层必须校验取值**，或者给列加 CHECK 约束（MySQL 8.0.16+ 真的会执行）：

```sql
CONSTRAINT ck_sys_role_data_scope CHECK (data_scope IN ('SELF','NODE','SUBTREE','ALL'))
```

**`is_global` 是干什么的？** 见 §2.6 的 B3/B4。简单说：超管这种角色不属于任何一个部门，它的任职不能绑到某个节点上。

#### `sys_appointment` 任职

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `person_id` | BIGINT UNSIGNED NOT NULL | 谁 |
| `org_id` | BIGINT UNSIGNED NOT NULL | 挂在哪个组织节点，**0 表示全局** |
| `role_id` | BIGINT UNSIGNED NOT NULL | 什么角色 |
| `position` | VARCHAR(50) NULL | 岗位名称（"财务经理"），**仅用于显示** |
| `start_date` | DATE NOT NULL | 任职开始日 |
| `end_date` | DATE NULL | 任职结束日，NULL = 仍然有效 |
| `remark` | VARCHAR(200) NULL | 备注 |
| `create_time` / `update_time` | DATETIME | 同前 |

索引：`idx_sys_appt_person (person_id)`、`idx_sys_appt_org (org_id)`、`idx_sys_appt_role (role_id)`

**★ 时间区间是半开区间 `[start_date, end_date)`**

这是最容易写出 off-by-one 的地方，现在定死：

| 表达式 | 含义 |
|---|---|
| `start_date` | 任职的**第一天**（含） |
| `end_date` | 任职的**失效日**（**不含**）。NULL 表示至今仍有效 |
| 某天 `D` 是否有效 | `start_date <= D AND (end_date IS NULL OR end_date > D)` |
| 当前有效 | `start_date <= CURDATE() AND (end_date IS NULL OR end_date > CURDATE())` |
| **结束任职** | `end_date = CURDATE()` → **今天立刻失效** |

**为什么用半开区间？** 因为"结束任职"要立即生效。如果用闭区间（`end_date` 是最后一天），今天结束的任职今天还算有效，用户会看到"我都点结束了，权限还在"——然后你去排查半天，发现是日期比较写成了 `>=`。

**没有 `status` 字段。** 有效性由时间推导，不引人第二条真相。多一个 `status` 就多一处可能不一致的地方（`status=1` 但 `end_date` 是去年）。

**结束任职 ≠ 删除任职。** 这是本需求的核心原则之一：**任职记录永不删除**。人事数据要能回答"他 2024 年在哪个部门"，删了就答不上来。

**不加数据库唯一键，这是刻意的**（与 R01/R02 的做法不同）：

- 在 R01/R02 里，重复数据会造成**真实损坏**：两个部门用同一个编码 → 外部系统对接错乱；两个账号用同一个用户名 → 谁登得进去说不清
- 在这里，重复任职的后果是**列表里同一个角色显示两遍**——难看，但功能没坏（并集算出来一样）

判断标准是：**重复会不会造成数据损坏或安全问题。** 会，就上数据库唯一键兜底；只是难看，就 Service 层校验、给个友好提示。

> 如果将来发现重复任职真的造成困扰，MySQL 8 可以用**生成列 + 唯一索引**在数据库层精确约束"只能有一条有效任职"，而不影响历史数据：
> ```sql
> active_key VARCHAR(64) GENERATED ALWAYS AS
>     (IF(end_date IS NULL, CONCAT(person_id,'-',org_id,'-',role_id), NULL)) STORED,
> UNIQUE KEY uk_sys_appt_active (active_key)
> ```
> `NULL` 在唯一索引里不参与去重，所以已结束的任职（`active_key` 为 NULL）可以有多条。**现在不做，记下这个工具。**

#### `sys_role_permission` 角色权限

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED 自增 | 主键 |
| `role_id` | BIGINT UNSIGNED NOT NULL | 角色 |
| `permission_code` | VARCHAR(100) NOT NULL | 权限码，如 `system:dept:create` |
| `create_time` | DATETIME | 创建时间 |

唯一键：`uk_sys_role_perm (role_id, permission_code)`

**★ 权限码的"真值"在代码里，不在这张表里。**

表里只存**引用**。权限码的完整清单来自代码中的 `Permission` 枚举：

```java
public enum Permission {
    DEPT_LIST("system:dept:list", "部门查询"),
    DEPT_CREATE("system:dept:create", "部门新增"),
    ...
}
```

**为什么不建一张 `sys_permission` 表来存权限清单？**

因为那样会出现"数据库里有 200 行权限记录，但没人知道哪行对应哪个接口"，而且接口删了权限记录还在。**权限码必须和代码同生共死**——枚举里删掉一个常量，编译器立刻告诉你哪里还在用。

代价：角色勾选权限时，前端需要拿到权限码清单。提供一个接口从**枚举**读出全部权限码（`GET /api/system/permissions`），不查数据库。

#### 关于外键

**本系统所有表都不加外键约束。** 这是一个全局决定，现在明确：

| 理由 | 说明 |
|---|---|
| 写入加锁 | 每次插入任职，数据库要去 `sys_person` 加共享锁校验——高并发下是额外争用 |
| 挡住数据迁移 | 分批迁移、按公司拆表时，外键会让你动不了 |
| 与逻辑删除冲突 | 外键和"标记删除"天然打架 |

代价是可能出现**孤儿数据**（任职指向一个不存在的人员），所以：

1. 应用层必须校验（本需求的规则里都写了）
2. **需要一个定期体检任务**：扫描孤儿数据。放到 R06 审计与运维底座

**不加外键不等于可以不管完整性**，只是把责任从数据库挪到了应用层——那就要写测试去保证它。

### 2.3 接口契约

#### 权限码目录

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/system/permissions` | 返回全部权限码（来自枚举，**不查库**） |

响应：

```json
{
  "code": 200,
  "data": [
    { "code": "system:dept:list",   "description": "部门查询", "module": "system:dept" },
    { "code": "system:dept:create", "description": "部门新增", "module": "system:dept" }
  ]
}
```

`module` 由 code 的前两段推导（`system:dept`），前端按它分组渲染。

#### 角色管理

| 方法 | 路径 | 权限码 |
|---|---|---|
| GET | `/api/system/roles` | `system:role:list` |
| GET | `/api/system/roles/{id}` | `system:role:list` |
| POST | `/api/system/roles` | `system:role:create` |
| PUT | `/api/system/roles/{id}` | `system:role:update` |
| PUT | `/api/system/roles/{id}/status` | `system:role:update` |
| PUT | `/api/system/roles/{id}/permissions` | `system:role:assign` |
| GET | `/api/system/roles/{id}/permissions` | `system:role:list` |

`PUT .../permissions` 是**全量覆盖**（传什么就是什么），不是增量。语义清晰，避免"取消了哪个勾"说不清。

#### 任职管理

| 方法 | 路径 | 权限码 |
|---|---|---|
| GET | `/api/system/persons/{personId}/appointments` | `system:appointment:list` |
| POST | `/api/system/appointments` | `system:appointment:create` |
| PUT | `/api/system/appointments/{id}` | `system:appointment:update` |
| PUT | `/api/system/appointments/{id}/end` | `system:appointment:update` |

**`POST` 和 `PUT` 的入参里没有"结束日期"。** 结束任职只能走 `/end` 接口——因为"结束"是个有业务含义的动作（要校验、要记时间、要影响权限），不能被顺手塞进一个普通更新里。

`/end` 也不接受日期参数，就是"从今天起失效"。需要指定日期的场景（补录历史）放到数据导入，不开接口。

### 2.4 权限校验怎么工作

一次请求的完整链路：

```
1. AuthInterceptor 校验令牌 → 拿到 personId          （R02 已有）
2. 查该人的全部有效任职
3. 由任职 → 角色 → 权限码，算出权限并集
4. 判定：该人是否有 SUPER_ADMIN 的有效任职？
      有 → 全部放行
      没有 → 看 handler 方法上的 @RequiresPermission
              注解要求的码在并集里 → 放行
              不在 → 403
5. 把 CurrentUser（含 permissions）放进 CurrentUserContext
6. 请求结束，clear()
```

**用法**：

```java
@PostMapping
@RequiresPermission(Permission.DEPT_CREATE)
public Result<DeptVO> create(@Valid @RequestBody DeptCreateRequest request) { ... }
```

**没有注解 = 只要登录就能调。** 这是个**默认放行**的设计，必须清醒地知道它的风险：**新写的接口如果忘了加注解，就是敞开的。**

对此加一道保险：**写一个测试，扫描所有 Controller 方法，要求每个映射方法要么带 `@RequiresPermission`，要么在显式的白名单里。** 漏加注解 → 测试失败。这条测试放在 Step 6。

#### 关于缓存

**每次请求都查数据库拿角色和权限，不做缓存。**

听起来很浪费，但想清楚：加缓存就必须处理失效——改了角色权限、结束了任职、停用了人员，缓存都得清。**失效逻辑写错的后果是权限不生效**，这是安全问题，不是性能问题。

在当前规模（内部 OA，几百人）下，多两次主键查询完全可以接受。等真的成为瓶颈，再上带失效通知的缓存（Redis pub/sub 或 Caffeine + 版本号），**那时你已经有测试能保证改对了**。

顺带一个好处：**改完角色权限，用户下一个请求就生效，不用重新登录**（§1.3 的验收标准之一）。

### 2.6 业务规则（逐条编号）

| 1202 | 角色编码已存在 | 400 |
| 1203 | 角色名称已存在 | 400 |
| 1204 | 任职不存在 | 400 |

| 1213 | 内置角色不允许此操作 | 400 |
| 1214 | 该组织节点下存在有效任职，无法删除 | 400 |
| 403 | 已登录，但没有该接口的权限 | **403** |

---

**B1｜角色编码唯一**（1202）／**B2｜角色名称唯一**（1203）

靠数据库唯一键兜底，`DuplicateKeyException` 映射表加 `uk_sys_role_code`、`uk_sys_role_name`。

---

**B3｜全局角色必须配全局任职**（1207）

`is_global = 1` 的角色，任职的 `org_id` 必须为 `0`。

**B4｜非全局角色必须绑定具体组织节点**（1208）

`is_global = 0` 的角色，任职的 `org_id` 必须 `!= 0`，且该节点存在、启用（否则 1209）。

**为什么要有 `is_global`？** 因为"超级管理员属于哪个部门"这个问题没有答案。

R00 §4.2 说 `ALL` 范围"仅限超管"。如果超管也必须绑一个部门，就出现两种荒谬情况：绑在技术中心，那华东分公司是不是就管不了？或者给每个公司都建一个超管任职，那一改密码要改 N 次。

**全局任职（`org_id = 0`）就是给这类"不属于任何组织节点"的角色准备的。** 它不参与数据范围的并集计算——`data_scope = ALL` 本身就是"不加条件"。

**约束**：`is_global = 1` 的角色，`data_scope` 必须是 `ALL`。全局角色配 `SELF` 没有意义（"全局地只看自己"是什么？）。这条在 Service 里校验。

---

**B5｜组织节点必须存在且启用**（1209）

给离职人员、停用节点建任职都要拦。**和 R01 的 R4 是同一个道理**：不能让数据挂在已经停用的节点上。

---

**B6｜同一人 + 同一节点 + 同一角色，不能有重复的有效任职**（1206）

Service 层校验。查重时的条件必须带上 §2.1 的有效性判定：

```sql
SELECT COUNT(*) FROM sys_appointment
WHERE person_id = ? AND org_id = ? AND role_id = ?
  AND start_date <= CURDATE() AND (end_date IS NULL OR end_date > CURDATE())
```

**注意：已结束的任职不算冲突。** 一个人可以在 2023 年当过研发部主管，2025 年又当回来——这是两段任职，都合法。查重时必须排除已结束的。

---

**B7｜开始日期不能晚于结束日期**（1210）

`start_date >= end_date` 时拒绝。

**注意这是唯一需要校验日期的地方**——`end_date` 为 NULL 是合法的，别写成 `if (end_date == null || ...)` 把正常情况也拦了。

---

**B8｜已结束的任职不能再结束**（1205）

`end_date != null` 时调用 `/end` → 1205。

**为什么这条重要？** "结束成功"但把 `end_date` 从 `2024-06-30` 改成了 `2024-08-15`，会**静默地改变历史**。历史数据被悄悄改写是最难发现的一类 bug。

---

**B9｜角色停用立即生效，但不影响已有任职记录**

- 角色 `status = 0` 后，该角色下的任职**仍然存在**（历史要保留），但**不再授予任何权限**
- 计算权限并集时，跳过已停用角色的任职
- **允许停用还有有效任职的角色**（与 R01 的 R8 相反）

**为什么和 R01 的 R8 不一样？** 因为两者破坏的东西不同：

| 操作 | 影响 | 处理 |
|---|---|---|
| 停用组织节点（R01 R8） | 影响下级节点的**连续性**——一个公司停用了，下面的部门还在正常运作，数据挂在了一个"不存在的公司"下 | 拒绝，要求逐个确认 |
| 停用角色（R03 B9） | 只是**不再授予权限**，任职记录和历史完全不受影响，而且可逆 | 允许，立即生效 |

组织节点是**数据的归属**，角色是**权限的授予**。前者要谨慎，后者本来就该能随时开关。

---

**B10｜系统必须始终至少有一个"可用的超级管理员"**（1211）

**这是整份需求里最重要的一条**：防止把自己锁在外面。

定义"可用超管"要同时满足：

```
1. 人员 status = 1（在职）
2. 账号 status = 1（未停用）
3. 持有一段 SUPER_ADMIN 的有效任职（未结束）
4. SUPER_ADMIN 角色 status = 1
```

**任何操作如果会导致上面这个集合变成空，就拒绝**，并在错误信息里说清"这是最后一个可用的超级管理员"：

| 操作 | 检查 |
|---|---|
| 停用人员 | 该人是不是最后一个可用超管 |
| 停用账号 | 同上 |
| 结束任职 | 这段任职是不是最后一个超管的有效任职 |
| 停用角色 | `SUPER_ADMIN` 直接禁止停用（1213） |

**为什么这条规则这么重要？** 因为触发它的操作看起来都很正常——"我要离职了，把自己的账号停用一下吧"，然后整个系统没有管理员了，只能去数据库里手工改。这个坑一旦踩上，恢复成本极高（要有人能连生产库）。

**实现建议**：把判定写成一个独立方法 `boolean isLastAvailableSuperAdmin(Long personId)`，四个入口都调它。**不要每个入口各写一遍** —— 复制四遍的判断逻辑，改规则时必漏。

---

**B11｜组织节点下有有效任职时不能删除**（1214）

补上 R01 遗漏的规则。判定条件和 B6 一致——**只算有效任职**。

> 注意 R01 原本写的是"有在职人员不能删部门"。有了任职表后才精确：不是"有人在职"，而是"**有人正被授予这个节点的角色**"。
> 一个刚入职还没分配角色的人，不应该挡住部门删除。

---

**B12｜权限码必须存在于 `Permission` 枚举中**（1212）

`assignPermissions` 时逐个校验。**这条防止的是"给了个不存在的权限码，用户以为配好了，实际没生效"。**

对应的测试（Step 2 写）：

```java
// 数据库里出现的每个权限码，都必须在枚举里能找到
@Test
void allAssignedPermissionCodesExistInEnum() { ... }
```

**这条测试是真正兜底的**：Service 层校验只挡新数据，这条挡所有数据。

---

**B13｜内置角色不可修改编码、不可停用**（1213）

`SUPER_ADMIN` 的 `role_code`、`is_global`、`data_scope` 不可改，不可停用。名称和备注可以改。

**为什么？** 因为代码里靠 `role_code = 'SUPER_ADMIN'` 做全局放行（§2.4 第 4 步）。把它改了，放行逻辑失效 → 系统锁死。

---

**B14｜给角色分配权限时，全量覆盖要有事务**

先 `deleteByRoleId` 再批量 `insert`。**必须在同一个事务里**——中间失败会导致角色权限被清空，那比不生效更危险（有人会突然失去权限）。

### 2.7 本需求明确不做的事

- **不做数据权限的 SQL 落地** —— `data_scope` 这一列**本需求只定义和存储，不生效**。让 `SUBTREE` 真的能过滤数据是 R04 的事
- **不做菜单和前端路由权限** —— 权限码目前只控制**后端接口**。菜单树要等有前端了再做
- **不做"谁能创建角色"的分级管理** —— 现在有 `system:role:create` 的人能创建任何角色。角色的分级授权（"部门管理员只能创建本 department 的角色"）是更后面的事
- **不做权限缓存** —— 见 §2.4
- **不做角色的数据权限细分到按钮** —— 比如"能看但不能导出"，属于数据权限的延伸
- **不做操作日志** —— 谁给谁加了角色，由 R06 审计统一处理。**但请注意这是本需求的一个真实缺口**：权限变更没有留痕，上线前应尽快补
- **不做批量导入任职** —— 组织调整时常常一次要改几十个人的任职，那是独立的"组织调整"需求
- **不做外部数据源的组织同步** —— 钉钉/企微通讯录同步属于移动平台集成

### Step 1：三张表

**目标**：`sys_role`、`sys_appointment`、`sys_role_permission` 建好，约束生效。

**产物**：`V3__init_role_appointment.sql`

**手工验证这几条**：

```sql
-- 1. 全局角色 + 全局任职：成功
INSERT INTO sys_role (role_code, role_name, data_scope, is_global) VALUES ('SUPER_ADMIN', '超级管理员', 'ALL', 1);
INSERT INTO sys_appointment (person_id, org_id, role_id, start_date) VALUES (1, 0, 1, '2024-01-01');

-- 2. 角色编码重复：必须失败

-- 3. 同一角色权限重复：必须失败
INSERT INTO sys_role_permission (role_id, permission_code) VALUES (1, 'system:dept:list');
INSERT INTO sys_role_permission (role_id, permission_code) VALUES (1, 'system:dept:list');

-- 4. data_scope 拼错：如果加了 CHECK 约束，这条必须失败
INSERT INTO sys_role (role_code, role_name, data_scope) VALUES ('X', 'X角色', 'SUBTREE_X');
```

**第 4 条是检验你加没加 CHECK 约束的。** 没加的话它会成功——那就等于承认"数据库里可以有拼错的数据范围值"，将来写 R04 的时候会踩到。

### Step 2：权限码枚举与目录接口

**目标**：权限码有了唯一真值来源，并且能列出来。

**产物**：`common/permission/Permission.java`、`GET /api/system/permissions`

**`Permission` 枚举要包含前面几份需求的全部接口**：

```
system:dept:list / create / update / delete
system:person:list / create / update
system:account:update / reset-password
system:role:list / create / update / assign
system:appointment:list / create / update
```

**枚举的写法要点**：

- 每个常量带 `code` 和 `description`
- 提供一个 `fromCode(String)` 静态方法，找不到抛异常（**不要返回 null**——返回 null 会让调用方漏判）
- 提供一个 `catalog()` 返回列表，供接口使用
- **提供一个推导 `module` 的方法**：取 code 的前两段

**必须写的测试**：

1. **所有 `code` 全局唯一**（枚举里抄错一个就重复了）
2. **所有 `code` 格式合法**（至少三段，用 `:` 分隔，只含小写字母和 `:`）
3. **`fromCode` 对不存在的码抛异常**

第 2 条测试的价值：权限码是**契约**，前端和数据库都引用它。格式失控（一会儿 `system-dept-list`、一会儿 `system.dept.list`）会让权限系统变成一团乱麻。**用测试把格式钉死。**

**完成的标志**：`curl http://127.0.0.1:8090/api/system/permissions`（带令牌）返回全部权限码。

### Step 3：角色管理

**目标**：角色的增删改查 + 权限分配。

**产物**：`system/role/` 全套

**实现顺序**

1. `SysRoleMapper` + `SysRolePermissionMapper`
2. `SysRoleService.create/update/changeStatus`
3. `assignPermissions`（**全量覆盖 + 事务**，见 B14）
4. `SysRoleController`

**容易写错的地方**

- `assignPermissions` 的 `deleteByRoleId` 和批量 `insert` **必须在同一个 `@Transactional` 方法里**
- 批量 insert 用 `<foreach>` 拼接，**空列表要短路返回**——`INSERT ... VALUES` 后面跟空列表是 SQL 语法错误
- B13 的内置角色保护：**`SUPER_ADMIN` 的判断不要写死在多个地方**，抽一个 `boolean isBuiltinRole(String roleCode)` 
- 停用角色时不做任何级联（B9）——**别顺手去结束别人的任职**，那是在替用户做决定

```bash
# 建角色
curl -X POST http://127.0.0.1:8090/api/system/roles \

# 分配权限（全量覆盖）
curl -X PUT http://127.0.0.1:8090/api/system/roles/2/permissions \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '["system:dept:list","system:person:list"]'

# 传一个不存在的权限码 → 必须 400 + code 1212
```

### Step 4：任职管理

**目标**：能把角色授予某人在某个节点上，能结束任职。

**产物**：`system/appointment/` 全套

**实现顺序**

1. `SysAppointmentMapper`（含"查某人的有效任职""查冲突任职""统计某节点下的有效任职"）
2. `SysAppointmentService.create` —— B3、B4、B5、B6、B7
3. `SysAppointmentService.end` —— B8、B10
4. `SysAppointmentService.update` —— 只能改 `position`、`role_id`、`remark`，**不能改 `person_id` 和 `org_id`**
5. Controller

**`update` 不能改 `person_id` 和 `org_id`** —— 改这两个等于"把这段任职换个人/换个地方"，那是完全不同的两段任职。**要换就结束旧的、建新的**，这样历史才留得住。

**B10 的实现**：抽一个方法，四个入口共用：

```
boolean isLastAvailableSuperAdmin(Long personId)
```

在 `SysPersonService.changeStatus`（停用人员）、`SysAccountService.changeStatus`（停用账号）、`SysAppointmentService.end`（结束任职）三处调用。**这三处分别在 R02 和本需求的代码里**，所以 R02 的两个方法要**回头加这个检查**——这是 §2.5 表格之外的一个改动，别漏。

**完成的标志**

```bash
# 给张三在「研发部」（id=2）授予「部门主管」
curl -X POST http://127.0.0.1:8090/api/system/appointments \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"personId":1,"orgId":2,"roleId":2,"position":"研发部主管","startDate":"2024-01-01"}'

# 重复授予同一人同一节点同一角色 → 400 + code 1206
# 把全局角色的 orgId 传成 2 → 400 + code 1207
# 结束一个已结束的任职 → 400 + code 1205
```

### Step 5：登录返回角色与权限

**目标**：登录和 `/me` 返回 `roles` / `appointments` / `permissions`。

**产物**：改 `AuthServiceImpl`、`CurrentUser`、`LoginResponse`

**实现要点**

- 查任职时必须带**有效性条件**（§2.1 的半开区间），别写成 `WHERE person_id = ?` 就把历史任职也捞进来了
- `roles` 由 `appointments` 按 `roleId` 去重得到，**不要在 Java 里用 `equals/hashCode` 去重实体**——用 `LinkedHashMap<Long, ...>` 按 id 去重，保证顺序稳定
- `orgPath` 需要从组织树算出来（"技术中心/研发部/前端组"）。**不要每个任职都去递归查父节点**，把 R01 的 `selectAll()` 拿一次，在内存里查表算路径
- `permissions` 是并集：遍历有效任职 → 角色（跳过停用的）→ 权限码，用 `Set` 去重
- **有 `SUPER_ADMIN` 有效任职时，`permissions` 要返回全部权限码**（与 §2.4 第 4 步的放行逻辑保持一致）

**最后一条特别容易忘。** 放行逻辑里超管是"全通过"，但如果登录响应里 `permissions` 是空的，前端会把所有按钮都灰掉——用户是超管却什么都点不了，只能靠直接调接口。**判定逻辑和展示数据必须来自同一个方法**，否则迟早不一致。

建议抽成一个方法：

```
CurrentUser buildCurrentUser(Long personId)   // 任职、角色、权限全在这里算
```

拦截器和登录接口都调它。

**完成的标志**

```bash
curl -s -X POST http://127.0.0.1:8090/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"..."}' | python3 -m json.tool
```

响应里能看到 `roles`、`appointments`、`permissions` 三个数组，且 `appointments` 里**只有当前有效的**。

**测一条历史数据**：手工插一段 `end_date = '2024-06-30'` 的任职，重新登录，它**不应该**出现在 `appointments` 里。

### Step 6：权限拦截与接口补注解

**目标**：每个接口都受权限保护，漏加注解会被测试抓出来。

**产物**：`RequiresPermission`、`PermissionChecker`、`AuthInterceptor` 改造、给 R01/R02 的 13 个接口补注解

**实现顺序**

1. `@RequiresPermission(Permission...)` 注解（**`@Retention(RUNTIME)`，`@Target(METHOD)`**）
2. `PermissionChecker.hasPermission(CurrentUser, Permission)` 
3. `AuthInterceptor.preHandle` 里做判定
4. 给已有接口补注解
5. **写"注解覆盖率"测试**

**无权限时返回 403**，用统一返回体：

```json
{ "code": 403, "message": "没有该操作的权限" }
```

**不要**在错误信息里写"缺少权限 system:dept:delete"。那等于告诉攻击者你的权限码命名规则和系统结构。**提示给用户看，细节进日志。**

**"注解覆盖率"测试怎么写**（这条是本 Step 的核心）：

```
1. 从 Spring 容器里拿到所有 @RestController 的 Bean
2. 遍历它们的每个方法，找出所有带 @RequestMapping/@GetMapping/@PostMapping/... 的
3. 对每个方法断言：要么带 @RequiresPermission，要么在显式白名单里
4. 白名单只放：/api/auth/login、/api/auth/me、/api/system/permissions
```

**为什么这条测试值得写？** 因为"权限漏加"是本需求最可能出的安全事故，而且**测试覆盖率再高也测不出来**——你写的是"有权限能调通"的测试，漏加注解的接口恰好也"能调通"。只有这条结构性测试能抓住它。

**路径穿越要再测一遍**（R02 测过，现在有了权限校验，再确认一次）：

```bash
# 用一个无权限的账号
curl -s -o /dev/null -w "%{http_code}\n" \
  -X DELETE http://127.0.0.1:8090/api/system/depts/999 \
  -H "Authorization: Bearer $NORMAL_USER_TOKEN"          # 必须 403

curl -s -o /dev/null -w "%{http_code}\n" \
  "http://127.0.0.1:8090/api/system/persons/../depts/999" \
  -H "Authorization: Bearer $NORMAL_USER_TOKEN"          # 必须 403 或 404，绝不能是 200
```

**完成的标志**：用一个只有 `system:dept:list` 权限的账号，能查部门（200），不能删部门（403）。

### Step 7：引导超管 + 端到端验收

**目标**：系统有一个可用的超管，且 §1.3 全部走通。

**先解决鸡生蛋问题。** 你现在没有任何角色、没有任何任职，所有接口都需要权限——**但第一个超管的权限从哪来？**

答案：**手工 SQL 引导，只在初始化时做一次**。

```sql
-- 1. 超管角色（如果 V3 迁移里没预置）
INSERT INTO sys_role (role_code, role_name, data_scope, is_global, remark)
VALUES ('SUPER_ADMIN', '超级管理员', 'ALL', 1, '系统内置，不可停用');

-- 2. 确认人员已存在（R02 建的人员）
SELECT id, person_no, person_name FROM sys_person WHERE person_no = 'E001';

-- 3. 确认账号已存在
SELECT id, person_id, username FROM sys_account WHERE person_id = 1;

-- 4. 建全局任职（org_id = 0）
INSERT INTO sys_appointment (person_id, org_id, role_id, position, start_date, remark)
VALUES (1, 0, (SELECT id FROM sys_role WHERE role_code = 'SUPER_ADMIN'), '系统管理员', CURDATE(), '初始管理员');

-- 5. 验证：应该能查到 1 条有效任职
SELECT a.id, p.person_name, r.role_name, a.start_date, a.end_date
FROM sys_appointment a
JOIN sys_person p ON p.id = a.person_id
JOIN sys_role   r ON r.id = a.role_id
WHERE a.start_date <= CURDATE() AND (a.end_date IS NULL OR a.end_date > CURDATE());
```

**然后重新登录**，响应里应该出现 `SUPER_ADMIN` 和全部权限码。

## 5. 完成后你会得到什么
